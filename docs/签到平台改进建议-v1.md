# 签到平台改进建议 v1

日期：2026-10-30。状态：供确认的设计，未实施。

配套资料：[方案评估与现成方案对比](../research/方案评估与现成方案对比-2026-10-30.md)、[本地检查记录](../research/evidence/方案评估-2026-10-30/本地检查记录.md)。本设计中的新表、新状态和验收标准均为提议，不表示已有功能。

## 1. 决策与技术选型

保留 Node/TypeScript、Midscene Android、YAML 配置、SQLite 和现有面板。先收敛执行闭环，再决定是否替换执行层。把“低人工、真实兑换价值、可迁移流程”作为优化目标。

| 层 | 建议 | 暂不采用的替代及原因 |
|---|---|---|
| 手机动作与视觉 | adb/可读控件树处理确定动作，Midscene 负责截图理解、视觉定位与受限探索 | 不立即全迁移 Appium/Maestro；它们可改善编排，但不会自动让 Canvas/不可访问控件可读 |
| 工作流 | 复用现有 @midscene/test 运行器，保留一套活动调度；逐步归并重复的 flow/engine 执行语义 | 不新造第三套 DSL；也不以无约束自然语言大循环代替已验证任务 |
| 学习与复用 | 记录真实成功轨迹，形成有前后条件的版本化配方；官方报告结构化解析 | 不把任务名正则、行号、截图坐标直接当作跨日任务身份 |
| 编排 | 普通 Node 逻辑负责队列、预算、生命周期；LLM 用于未知页面/未知任务解释 | 不要求每天 Claude Agent SDK→平台→Midscene 双层规划；SDK 可保留为人工交互入口 |
| 调度 | 一台手机一个 worker，SQLite 持久队列，显式设备锁 | 不在 HTTP 进程内直接跑手机任务；不为单机引入分布式平台 |
| 存储 | 沿用 SQLite；补 job/run/observation/recipe 的关联与事实字段 | 不迁移远程数据库；不把收益拆分估计当已收到账 |
| UI | 沿用面板，展示完成度、观测质量、余额、实际兑换、现金支出与维护耗时 | 不先重做页面；数据口径比视觉重构更优先 |

## 2. 系统架构与进程边界

```text
浏览器 / 可选对话入口
          │ 查询 / 入队
          ▼
panel/API 进程 ── SQLite job、run、观测、账本 ── worker 进程
          ▲                                        │
          │                                  独占设备锁
       只读结果                                     │
                                             adb / Midscene
                                                   │
                                                  手机

现有 meter 代理：接收模型请求、转发供应商、按 run/step 归集使用量。
```

- panel/API 只校验请求、入队和查询；worker 原子领取 job 后执行，结束写结果。这里“只读”指对手机与执行结果，不妨碍 API 写 job。
- worker 独占设备；API、手工命令、调度入口共用同一把锁。并发提交最多产生排队，不允许两个执行器一起点手机。
- 不需要为学习单独起常驻进程；同一 worker 切换探索/验证/复用模式即可。
- worker 崩溃后，由租约/心跳识别过期 job；重新进入时先观测现状，避免重领、重复消费配额。恢复会话不直接重放上一条有副作用的动作。
- meter 与 worker 可以独立失败；模型不可用时保留已确认事实、标阻塞，不伪造成功与零成本。暂不新增复杂代理链。

## 3. 数据模型与面板口径

下面为逻辑模型，实施时通过迁移添加或复用字段，不要求把现有表推倒。

| 对象 | 必要字段/约束 | 解决的问题 |
|---|---|---|
| account | id, device_id, package, android_user_id | 主实例与双开实例显式区分；同包名不代表同账号 |
| job | id, kind, status, account_id, activity_id, run_id, lease_owner, lease_until, heartbeat_at, request_key | job.id 与 run.id 分开；重复请求去重，崩溃可恢复 |
| run | id, job_id, execution_status, observation_status, completion_status, stop_reason, started_at, finished_at, recipe_version | 部分收益与完整完成分别表达，失败记录不因余额上涨而消失 |
| observation | id, run_id, step_id, timestamp, page_kind, method, raw_value, parsed_value, metric_id, validity, evidence_path | 未知值用 null/unknown；记录从哪里、何时读到哪个数 |
| inventory | id, account_id, activity_id, observed_at, page/session_signature, completeness, evidence_path | 单屏清单不自动代表全部清单；同日重进也可能变化 |
| task_instance | id, inventory_id, display_name, instruction, quota_done, quota_total, reward, target_reference, learned_recipe_id | 名称仅用于显示和当前清单关联；跨日复用依赖内容和成功轨迹 |
| recipe | id, version, scope, precondition, actions, postcondition, source_run_id, validation_count, last_verified_at, state | candidate→validated→stale；所有晋升有真实验证依据 |
| asset_snapshot | 现有字段 + metric_id, observation_id | `(account_id, asset_id, metric_id)` 是余额口径；不能把总余额与今日获得相减 |
| valuation_rule | asset_id, effective_at, nominal_rate, rule_url, checked_at | 估值规则带生效版本，汇率更新不静默改写历史事实 |
| redemption_event | account_id, asset_id, units_spent, actual_discount_cny, date, evidence | 记录真实抵扣，避免把账面金币等同现金 |
| model_call/cost | run_id, step_id, model, input/output/cache_tokens, actual_charge, reference_charge, price_version | 订阅边际支出与参考API费用分开；未采集保持未知 |

面板数字的查询原则：

1. 余额：每个账号/资产/指标取最后一个有效观测，再按资产合计；不能每种资产只取一条最新记录。
2. 余额净变化：同一口径两次有效快照相减；注明含消费、过期、其他入账的可能影响。执行窗口余额差是观测到的净变化，未必等于单条任务发奖。
3. 自动化确认所得：以任务计数、奖励到账记录、关联余额读数建立证据；无法拆分的差额记未归因，不硬拆任务/档位/bonus。
4. 实际省钱：汇总 redemption_event 的真实抵扣；不要与未消费资产存量重复相加。
5. 成本：现金支出与参考API费用分列；输入、缓存、输出分别计价。没有实际账单时不展示为实际成本。
6. 完成率：按 completion_status 计算；某次有余额增长仍可 PARTIAL。历史 OK 不追溯升级为完整成功。
7. 日期：保存 UTC 时间戳，日汇总明确 Asia/Shanghai；跨日任务重新收集和判断。

## 4. 执行流程与中止点

```text
领取 job / 获取设备锁
→ 设备、账号实例与时间窗检查
→ 进入活动，确认活动页面
→ 收集当前可见清单，滚动补全；标注完整性
→ 本地计算预算、配额与档位，选择已验证配方
→ 验证前置条件 → 执行动作 → 验证任务结果
→ 页面恢复到已确认状态
→ 领取当前确实可领取的奖励
→ 回同一余额口径读数、记账、释放锁
```

**观察：** 控件树可用时直接解析，不可用或结论有歧义时把截图和解析摘要交给模型。不能根据一个空 dump 宣称整个平台不可读；Activity 只证明容器，不能证明具体页面。视觉判断也需要独立后验，不能模型说成功就完成。

**首次学习：** 提供页面截图、完整任务说明、当前按钮/配额/奖励、进入后的页面，以及允许动作范围。模型提出小段动作，每段有页面前提；执行并观察实际计数/到账结果。只把经验证成功的链写入候选配方。跨日名称变化不能自动沿用旧动作，先校验前提。

**复用：** 先验证适用上下文，再定位当前目标。语义目标或局部视觉目标优先；坐标只在已确认页面、尺寸、布局条件下使用。归一化坐标只适配尺寸，不能抵抗布局变化；行号只在当前清单版本内有效。

**恢复：** 优先确认当前页面再做最小返回；局部恢复失败才重走入口。每段恢复有次数、墙钟时间、模型调用预算。不要让每轮都冷启动变成默认正常路径。

**未知状态：** 不能转成0/0或没有任务；暂缓动作，重新观测，有限恢复后标阻塞。可以尝试只读结算，保留已经确认的收益；不要继续盲点。部分步骤失败后能否继续，取决于下一步前置条件是否仍成立，不应统一“永远继续”或“立即放弃”。

**完成与结束：** 已验证的任务计数增长、已验证的领取状态、余额读数质量各自记录。硬预算到期/模型不可用/页面未知也允许结束，但不能标成全部完成。验证码、登录缺失、系统需要人工处理时记录证据并暂停对应活动。

**缓存：** 保留 Midscene 规划缓存；成功路径才晋升、版本变化失效。配方库与官方缓存职责不同：前者保存业务动作及结果契约，后者减少规划开销。不要宣传 Android 日常必然零调用。

## 5. 开发计划与可证伪验收

本轮没有执行这些阶段；需用户确认方案后实施。先处理A，不要求一次实现所有建议表。

| 阶段 | 范围 | 验收标准（提议） |
|---|---|---|
| A 结果可信 | 未知状态、状态拆分、job→run、节点schema/注册契约 | 离线重放近期失败样本，不再出现未知→无任务/全部完成；无动作执行的 YAML 合同校验能发现缺失节点与参数；接口成本能关联实际run |
| B 单任务闭环 | 一条可重复任务，页面观察、执行和恢复 | 人工监督至少3次机会内，每次都能区分计数增长、无效果、读数失败；每次动作前确认页面；不使用假设收益代替证据 |
| C 学一次再复用 | 真实轨迹→candidate→validated；与Unify-Sign对照 | 已验证配方独立重入后再执行至少2次；任务变更或页面不符时拒绝错用；记录调用量、耗时、人工介入及每次实际计数变化 |
| D 单设备队列 | panel入队、worker、设备锁、恢复租约 | 两个同时请求仅一个持锁；杀死worker后面板仍响应，重启能将未完成job识别并从观测恢复；不直接重做未知是否已生效的操作 |
| E 持续人工验收 | 连续多日，含清单变化、已签过与登录失败 | 建议至少连续7天观察，逐日核对任务/余额/成本，错误无假成功、未知值不写零、人工介入次数有记录；真实兑换至少记录一次，未兑换不声称现金收益 |
| F 无人值守 | 仅在用户人工确认后启用调度 | 用户确认验收记录后才启用；有可见的暂停/异常入口与每日结果 |

最小对照实验只选一条任务，先比较“当前栈修好闭环”与“Mobilerun动作录制/回放”。后者的前置状态匹配、AI接管和修复后轨迹更新并非完整业务闭环，必须挂接同样的结果验证。Unify-Sign先核实指定运行时和当前活动路径，匹配才加入现成脚本对照。保留相同手机、账号和相近配额条件，记录实际任务差异。不要在当天已耗尽配额后继续用无增长评价框架质量，也不要凭三次成功外推长期成功率。

决定是否迁移执行层的依据：在同等验证要求下，哪条路线需要更少人工修正、能完整输出证据并稳定回传账本。开源项目的支持列表、星数、演示视频不代替该实验。
