手机每日签到平台 · 最终技术方案

版本：v1.1 · 2026-10-29
工作空间：/Users/mater/Project/android-checkin
设备：Xiaomi 12S Pro（HyperOS 3.0.2.0 / Android 15）· adb serial 3d8a7934
主机：Mac（Apple M6 / 24GB 统一内存）· Mac 常开 · 手机专用

0. 一句话方案

签到路径学一次、固化成确定性配方，之后每天用 adb 回放（0 模型调用、秒级完成）。
收益按「积分 → 人民币」逐笔记账，Web 面板看状态、收益、连续天数、漏签损失。

1. 技术选型结论

1.1 执行层：uiautomator2 + adb（自建轻引擎）

不引入任何 AI 手机 Agent 产品，理由：

候选 为什么不选
肉包 Roubao（2.4k★）/ ApkClaw（800★）/ Andclaw（514★） 面向终端用户对话，拿不到结构化中间数据（动作序列、界面读数），接不上记账
Open-AutoGLM（26.5k★）/ AutoGLM-GUI 模型「限时免费」，可持续性不成立
Midscene.js（15.4k★） 见 1.2
青龙面板 + 脚本库 纯 Cookie 派；淘宝带设备签名，抓不到

uiautomator2 已在本机实测通过：点击（点「显示与亮度」成功跳 .SubSettings，界面确认变化）、长按 0.95s、滑动 1.57s、读屏、截图全部可用。

1.2 学习层：P0 由我识图，Midscene 列为预留

关键事实：日常执行不需要 AI。 配方跑起来后每天 0 调用。AI 只在两个低频时刻出场——新活动接入、活动改版导致配方失效。

维度 我直接识图（P0 采用） Midscene（预留）
依赖 已有（adb + 读屏 + 点击） Node + @midscene/android + 模型 API Key
一次性成本 3~5 张截图进上下文，几分钟 装环境 20~30 分钟 + ¥0.03
定位精度 中（截图缩放到 540×1200，靠验证兜底） 高（专用 grounding 模型）
无人值守重学 ❌ 需要会话 ✅ 脚本可 cron 触发
每步验证 我做（点完看界面变没变） 自带 aiAssert

引入 Midscene 的触发条件（满足任一）：
1. 配方失效频率 ≥ 每月 2 次
2. 活动数量扩到 15 个以上
3. 要求完全脱离会话自动自愈

若将来引入，它的正确定位：不是日常执行引擎，而是「一次性教学工具」——跑一次产出带 Locate center 坐标的 HTML 报告，用 report-tool --action split 导出 *.execution.json，我们解析后固化成配方。
注意：它在 Android 上的元素定位缓存不生效（XPath 缓存仅 Web），所以不能靠它做日常零成本执行。

1.3 记账层：自建（唯一没有现成方案的部分）

调研结论：市面上（GitHub / Google / X / 应用商店）没有任何项目做「签到收益记账」。所有工具只记「成功/失败」日志，没有「积分 → 人民币、按账号/活动/时间汇总、有效期管理」。

这层必须自己写，也是本方案的差异点。

2. 总体架构

┌──────────────────────────────────────────────────────────────┐
│ L1 学习层（一次性，低频）                                      │
│   实现：我识图（P0）/ Midscene（预留）                         │
│   输出：recipes/<account>_<activity>.json                     │
│   时机：新活动接入、配方失效                                   │
├──────────────────────────────────────────────────────────────┤
│ L2 执行层（每日，0 模型调用）                                  │
│   uiautomator2 + adb，按配方回放                               │
│   每步验证：UI 文本 diff + 验证词                              │
│   产出：ledger 记账 + evidence 截图                            │
├──────────────────────────────────────────────────────────────┤
│ L3 兜底层                                                     │
│   a) 升回 L1 重学（限 1 次/天/活动）                           │
│   b) 仍失败 → 推送截图，标 NEEDS_HUMAN                         │
├──────────────────────────────────────────────────────────────┤
│ 数据层：accounts / activities / recipes / ledger（纯文件）      │
│ 展示层：Web 面板（读账本；只读 + 两个写操作）                   │
└──────────────────────────────────────────────────────────────┘

为什么这么分：
- AI 的强项是「看得见就能点」，抗改版，但每步都推理，日常跑不划算
- 脚本的强项是「0 成本、快、可验证」，但路径写死，改版失效
- 组合起来：用 AI 的适应力生成脚本，用脚本的低成本日常执行

3. 数据模型

四张表 + 一条账本。全文本、可 git 版本管理。

3.1 账号表 accounts/accounts.yaml

accounts:
  - id: tb_main
    app: taobao
    package: com.taobao.taobao
    user_id: 0            # 0=主空间 / 999=应用双开
    login: cookie         # cookie | sms | manual
    enabled: true
    note: 主账号

  - id: tb_dual
    app: taobao
    package: com.taobao.taobao
    user_id: 999          # 双开实例，包名相同
    login: sms
    enabled: false
字段 说明
id 全局唯一，账本主键
app 逻辑名，对应 activities/<app>.yaml
package Android 包名（主空间与双开相同）
user_id 双开实例的唯一区分依据：0 主空间 / 999 双开
login cookie 持久登录 / sms 需短信码 / manual 每次人工
enabled 是否参与调度

双开启动方式（已实测）：

adb shell am start --user 999 -n com.taobao.taobao/<Activity>

启动后前台为 u999，am get-current-user 仍为 0，u2 的 dump_hierarchy / click 正常。
注意：d.app_start() 只作用于当前用户，双开必须走 adb 形式。

3.2 活动表 activities/<app>.yaml

app: taobao
account: tb_main
activities:
  - id: tb_redpacket
    name: 红包签到
    entry: [首页, 红包签到]
    verify_any: [已签到, 签到成功, 明日再来]
    absent_ok: false
    window: "09:00-13:00"
    reward:
      unit: 红包
      amount: 0.5
      cny_per_unit: 1.0
    forbidden: [翻倍, 立即翻倍]
    enabled: true
    state: pending          # active | pending | dead

  - id: tb_coin
    name: 淘金币签到
    entry: [领淘金币, 每日签到]
    verify_any: [已签到, 领取成功]
    window: "09:00-21:00"
    reward:
      unit: 淘金币
      amount: 50
      cny_per_unit: 0.01    # 100 淘金币 = ¥1
    enabled: true
    state: pending
字段 作用
verify_any 成功判定词，任意命中即成功
absent_ok 入口消失是否算成功（有些 App 签完隐藏入口）
window 允许执行时段，实际执行在窗口内随机偏移
cny_per_unit 积分→人民币唯一折算入口，改汇率只改这一行
forbidden 黑名单按钮，出现即中断（淘宝「翻倍」是价值陷阱：翻倍后红包只能指定专区用，实际价值大幅缩水）
state active 正常 / pending 待验证 / dead 活动结束

3.3 配方 recipes/<account>_<activity>.json

L1 学完固化，L2 执行。混合定位：文本锚点 + 归一化坐标双保险。

{
  "account": "tb_main",
  "activity": "tb_redpacket",
  "created": "2026-10-29T23:40:00",
  "source": "agent",
  "hits": 0,
  "fails": 0,
  "steps": [
    {"do": "launch", "package": "com.taobao.taobao", "user_id": 0, "wait": 9},
    {"do": "dismiss", "until_stable": true},
    {"do": "tap", "text": "红包签到", "xy": [0.42, 0.31], "after": 2.5},
    {"do": "forbid", "any": ["翻倍", "立即翻倍"]},
    {"do": "verify", "any": ["已签到", "签到成功", "明日再来"]},
    {"do": "read", "field": "balance", "regex": "(\\d+)\\s*淘金币"}
  ]
}

step 类型全表

do 参数 说明
launch package / user_id / wait 启动（双开走 am start --user）
tap text / xy(归一化) / exact / timeout / after 先按文本找，找不到用坐标
long_press text 或 xy，duration 长按（实测 0.95s）
swipe from/to（归一化 [x,y]），duration 滑动（实测 1.57s）
watch_video max_sec，skip_after 等视频 + 轮询跳过按钮
input text 输入（中文走 yadb）
back / home — 导航键
dismiss until_stable 跑 watcher 清弹窗（0 调用）
forbid any 命中黑名单立刻中断报错
verify any / absent_ok 成功判定
read field / regex 读界面数值（余额/积分），用于记账

坐标一律归一化（0~1），不写像素 —— 换机型、换分辨率配方仍有效。

混合定位执行顺序：文本找 → 坐标点 → 两者都失败记 NOT_FOUND 并触发重学。
这样比纯坐标或纯文本都稳：文案变了但位置没变能中，位置挪了但文案没变也能中。

3.4 账本 ledger/YYYY-MM-DD.jsonl

{"ts":"2026-10-29T09:12:03","account":"tb_main","activity":"tb_redpacket",
 "status":"OK","layer":"L2",
 "reward":{"unit":"红包","amount":0.5},
 "face_value_cny":0.5,"usable_cny":0.5,"cash_cny":0.0,
 "expires_at":"2026-11-13",
 "balance_before":1234,"balance_after":1284,
 "ms":3870,"evidence":"evidence/2026-10-29-tb_main-tb_redpacket.png"}

三个金额字段必须分开

字段 含义 说明
face_value_cny 账面价值 按官方汇率折算的名义金额
usable_cny 可用价值 受抵扣上限约束（京豆单笔最高抵 50%）
cash_cny 真现金 签到场景基本为 0

签到收益几乎全是账面价值、不可提现。混成一个数字会自欺。

3.5 状态机

status 含义 计收益 后续
OK 成功 + 验证通过 ✅ —
ALREADY 今日已签 ❌ 结束
NO_EFFECT 点了无变化 ❌ 累计 3 次 → 重学
NOT_FOUND 找不到入口 ❌ 重学
NEEDS_LOGIN 掉登录 / 被挤下线 ❌ 推送，不重试
NEEDS_HUMAN 滑块/验证码/权限弹窗 ❌ 推送截图
LAUNCH_FAILED App 没起来 ❌ 重试 1 次
DEAD 活动结束 ❌ 自动停跑
FORBIDDEN_HIT 命中黑名单 ❌ 中断报错

4. 每日运行流程

cron 触发（Hermes cron 或 launchd）
│
├─ 0. 环境自检
│     adb 连接 / 屏幕唤醒 / 免锁屏 / 电量
│     失败 → 推送「设备离线」
│
├─ 1. 读 tasks，筛出当天在时间窗内的活动
│
├─ 2. 登录体检（L0）
│     掉登录（*Login* Activity）→ NEEDS_LOGIN
│     被挤下线（信息流在 + 模态框）→ NEEDS_LOGIN
│     → 汇总一次推送，不逐个打扰
│
├─ 3. 串行执行（一台机同时只能操作一个 App）
│     for each activity:
│       ├─ L2 跑配方
│       │    每步验证 → 全通过 → 读余额 → 落账 OK
│       │    任一步失败 → NO_EFFECT / NOT_FOUND
│       ├─ 失败且今日未重学 → L1 重学
│       │    成功 → 覆盖配方 → 重跑 L2 验证 → 落账
│       │    失败 → NEEDS_HUMAN + 截图
│       └─ 随机 sleep 2~8s
│
├─ 4. 汇总：成功 X / 已签 Y / 失败 Z / 需登录 W / 今日账面 ¥N
│     → 飞书一条消息
│
└─ 5. 落盘：ledger + evidence + recipes

时间窗随机化：避开签到入口的时段限制；避免「所有 App 同一分钟集中点击」的机器特征。

  • P0（我识图）：0（算在会话成本里，且是低频一次性）
  • 若改用 Midscene：一次签到约 15 步 × 2K tokens ≈ 30K tokens ≈ ¥0.03/次

项 成本
L2 日常 8 活动 × 365 天 ¥0

6. 失败处理矩阵

现象 检测方式 处理
屏幕黑着 d.info["screenOn"] == False svc power stayon true + KEYCODE_WAKEUP
dump 只有 ~20 节点 节点数 < 30 且包名 systemui 判熄屏/通知栏遮挡，处理后再读
App 没起来 连续两次采样包名 ≠ 目标 app_stop 后重试，最多 3 次
selector 匹配不到但 XML 有 exists 假 + 文本在 XML 中 解析 bounds → 中心 click(x,y)
点了没反应 前后 UI 文本集合完全相同 NO_EFFECT，重试 1 次后转 L1
弹窗挡路 命中噪音词 设备端 watcher 自动点（0 调用）
掉登录 Activity 含 Login / 「验证码登录」 NEEDS_LOGIN，推送，不重试
被挤下线 信息流在 + 「账号下线通知」模态框 NEEDS_LOGIN；必须先识别，否则后续点击全落弹窗、会误报成功
滑块验证码 「请拖动滑块」 NEEDS_HUMAN，不硬过（硬过加重风控）
命中「翻倍」 黑名单词出现 FORBIDDEN_HIT，中断
活动结束 连续 3 天 NOT_FOUND 且重学也找不到 标 DEAD 停跑

误报比失败更危险 —— 失败会重试，误报没人管。所以每步必须验证。

7. Web 面板

Mac 本地，读 ledger/ accounts/ activities/，不写业务数据。
技术：单进程（FastAPI 或 Node）+ 静态前端，localhost:8080，局域网可访问。

② 收益

区块 内容

③ 连续与漏签

区块 内容
连续天数 每活动当前连续 / 历史最长
漏签 最近 30 天漏签日期
漏签损失 按 amount × cny_per_unit 估算「因为没签少赚多少」

淘金币宝箱有容量上限（满了不累积）、京豆 2026 新规有效期最长 180 天（过期作废）——这两项让「漏签损失」和「即将过期」成为必需指标，不是可选项。

10. 风险与对策

风险 影响 对策
平台风控升级 点击无效 / 奖励缩水 / 限权 时间窗随机化、每日只跑一次、不硬过滑块、控制活动数（5~8 个）
账号被封 收益归零 优先小号 / 双开号；核心账号不多设备并发
活动频繁改版 配方失效 自动重学；fails 计数告警；接受「每月几次重学」是常态
手机长期插电 电池鼓包 充电上限 80%、通风处
手机离线/断连 当日全失败 环境自检 + 离线告警
淘宝检测自动化 奖励降低 不高频、不批量、只做单账号日常签到
合规 违反用户协议 仅自用；不对外提供服务；不集成进任何产品
