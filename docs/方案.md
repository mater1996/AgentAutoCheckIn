## 0. 一句话方案

**手机端跑一个「配方引擎」：签到流程写成声明式 YAML 配方，正常情况纯本地回放（0 token），
失败时才升级到 LLM 现场决策（1 次低分辨率截图 + 结构文本），成功后自动把新路径写回配方。
所有账号、活动、签到状态、收益折算落在本地账本。**

平台化 = 三张表 + 一个引擎 + 一条账本：

| 组件 | 文件 | 作用 |
|---|---|---|
| 账号表 | `accounts/accounts.yaml` | 谁、在哪个 App、哪个用户空间、登录态、登录方式 |
| 活动表 | `activities/*.yaml` | 每个账号签什么、什么时间窗、验证词、收益规则 |
| 配方表 | `recipes/*.json` | 怎么点（语义步骤，不写死坐标） |
| 账本 | `ledger/*.jsonl` | 每次执行的结果、截图路径、赚了多少、折合人民币 |
| 引擎 | `runner/checkin.py` | 体检 → 回放 → 升级 → 落账 |

## 1. 你的四个问题的直接回答

### Q1 多开账号 —— ✅ 可以，我实测推翻了之前的错误结论

**我一开始说错了。** 早先测到 `am switch-user 999` 报错，就下了「adb 碰不到分身」的结论。
实测发现真正的机制是：`am start --user 999` 可以直接把双开空间的 App 拉到前台，**不需要切用户**，
而且 u2 能正常 dump 和点击。

| 步骤 | 前台 | dump 节点 | 点击 |
|---|---|---|---|
| 主用户启动淘宝 | `u0 com.taobao.taobao` | 275 | ✅ |
| 启动双开美团（`--user 999`） | `u999 com.sankuai.meituan` | 80 | ✅ |
| 再回主用户淘宝 | `u0 com.taobao.taobao` | 277 | ✅ |

**双开的真实形态**：
- 小米「应用双开」= 把 App 装进 **user 999** 这个 profile
- 包名不变，靠 **userId 区分实例**；每个 user 有独立数据目录（独立登录）
- 所以账号表用 **`(package, user_id)` 二元组**标识实例

**我能不能自己点开双开** —— ✅ 实测走通：
```
设置 → 下滑 → 应用设置 → 应用双开 → 双开设置
```
- 「应用设置」在首屏看不到，需 swipe 一次
- 列表行的文字节点 `clickable=false`，要点它的可点祖先容器（中心 `(540,1248)`）
- 点已双开的行 → 弹「删除双开应用」确认框，证明开关可正常操作
- **坑**：设置里的搜索框找不到 EditText，`set_text` 报错 → 只能走列表导航，不能走搜索

**注意**：美团已经处于双开状态（我点它弹出的是「删除双开应用」）。

### Q2 平台化：记录每个账号签什么、签到状态、收益、积分折人民币

三张表的形状（示例见 `accounts/accounts.example.yaml`、`activities/jingdong.example.yaml`）：

**账号表**
```yaml
accounts:
  - id: jd_main
    app: jingdong
    package: com.jingdong.app.mall
    space: main              # main | dual
    login: cookie            # cookie | sms | manual
    note: 主账号
```

**活动表**（一个账号可以有多条活动）
```yaml
account: jd_main
activities:
  - id: jd_signin
    name: 京豆每日签到
    entry: [我的, 京豆]        # 语义路径，不是坐标
    verify_any: [已签到, 已领取]
    window: "08:00-12:00"
    reward:
      unit: 京豆
      amount: 7              # 每次签到约得
      cny_per_unit: 0.01     # 100 京豆 = 1 元
    enabled: true
```

**账本**（JSONL，每天追加，不覆盖）
```json
{"date":"2026-10-29","account":"jd_main","activity":"jd_signin","status":"OK",
 "reward":{"unit":"京豆","amount":7},"cny":0.07,"evidence":"evidence/xxx.png","ms":1834}
```

**积分折算**统一走 `activities/*.yaml` 里的 `reward.cny_per_unit`，账本只记原始单位和数量，折算在汇总时算 —— 这样兑换比例变了只改一处，历史记录不用重算。

### Q3 长按、滑动、看视频怎么自动化

实测能力（`probes/token_cost2.json`）：

| 手势 | uiautomator2 支持 | 实测 |
|---|---|---|
| 点击 | `d.click(x,y)` / `d(text=..).click()` | ✅ |
| 长按 | `d.long_click(x,y,duration)` | ✅ 0.95s |
| 滑动 | `d.swipe(x1,y1,x2,y2,dur)` / `d.swipe_ext("up")` | ✅ 1.57s |
| 拖拽 | `d.drag(...)` | ✅ |
| 多点/捏合 | `gesture` / `pinch_in` **不存在** | ❌ 需自写 `d.shell("input ...")` 或用 minitouch |

**配方里怎么表达**（新增 step 类型）：
```yaml
steps:
  - do: tap        # 点击文本
    text: 签到
  - do: long_press # 长按
    text: 领奖
    duration: 1.0
  - do: swipe      # 滑动（支持语义方向）
    from: [0.5, 0.75]   # 归一化坐标，换分辨率也不失效
    to:   [0.5, 0.35]
    duration: 0.4
  - do: watch_video     # 看视频：等待 + 中途防熄屏
    max_sec: 30
    skip_after: 15      # 出现"跳过"就点
  - do: verify
    any: [已签到, 签到成功]
```

**关键设计**：坐标一律用**归一化比例**（0~1），不写死像素。换机型、换分辨率配方仍然有效。

「看视频」不是真的看，是**等待 + 轮询跳过按钮**：每 2 秒检查一次有没有「跳过/关闭」，出现就点，到 `max_sec` 强制退出。全程不需要 LLM。

### Q4 怎么省 token —— 这是整个方案的核心

实测数据（`probes/token_cost.json`，淘宝首页 385 节点）：

| 方式 | 数据量 | 相对成本 |
|---|---|---|
| 全量 `dump_hierarchy()` XML | **182,234 字符** | 基准（1×） |
| 只提取 text 列表 | **239 字符** | **0.13%**（省 760 倍） |
| 全屏 PNG 截图 | **1,908,788 字节** | 极高 |
| 压缩成 800px JPEG | **100,804 字节** | 约 1/19 |
| `exists` 布尔判定 | **5 字符** | 近乎 0 |
| UI 指纹（文本集合哈希） | **19 字符** | 近乎 0 |
| 两次 UI diff（只传变化） | **35 字符** | 近乎 0 |

**五条省钱规则，按顺序执行：**

**① 默认不看图，看文本。**
正常执行全程只用 `exists` 布尔 + 文本列表，**0 token**（本地 Python 判断，不进模型上下文）。

**② 失败才升级，且只给结构化摘要。**
配方某步找不到目标时，才把「当前界面文本列表（≤40 条）+ 可点节点（≤15 个，含文本和归一化坐标）」发给 LLM。这个包约 500~800 字符，而不是 182KB。

**③ 需要看图时，只给压缩后的截图。**
1.9MB PNG → 800px JPEG 是 100KB，而且**只截关键区域**（比如只截下半屏的任务区），比全屏再省一半以上。

**④ 用 UI diff 做变更检测，不重复传全量。**
实测两次 dump 的文本差异只有 35 字符（`{"add":["86.1 "],"del":["189 "]}`）。判断「点了有没有生效」只需要传这个 diff，不需要传两次全量。

**⑤ 设备端 watcher 处理常规弹窗，完全不经过 LLM。**
实测 `d.watcher` 可用（`has_watcher: true`）。把「跳过/关闭/以后再说/我知道了」这类固定弹窗注册进 watcher，**设备端每 2 秒自动检查并点击**，属于本地行为，0 token。

**token 预算估算**（8 个 App / 账号）：

| 场景 | 每次 LLM 调用 | 频率 |
|---|---|---|
| 一切正常 | **0** | 每天 |
| 单个活动改版 | 1 次，约 800 字符输入 + 200 输出 | 偶发（月均几次） |
| 需要看截图 | 1 次，100KB JPEG + 200 输出 | 罕见 |
| 掉登录 | **0**（只推送截图给你） | 偶发 |

**这就是为什么方案能长期跑下去：正常日子完全不花 token。**

## 2. 卡住时怎么处理 —— 四层降级

```
L0 登录体检（本地）
  ├─ 掉登录 / 被挤下线 → 停跑，推截图 + 一句话给你，0 token
  └─ 正常 → 进 L1

L1 配方回放（本地，0 token）
  ├─ 每步验证 → 全部通过 → 落账，结束
  └─ 某步失败 → 进 L2

L2 LLM 现场决策（1 次小请求）
  ├─ 输入：界面文本 + 可点节点（含归一化坐标），约 800 字符
  ├─ 输出：该点哪个（文本或坐标）+ 为什么
  ├─ 执行后验证成功 → 把新步骤写回配方 → 下次自动
  └─ 仍失败 → 进 L3

L3 人工兜底（0 token）
  └─ 推截图 + 卡在哪一步 + 建议动作给你
```

**L2 的关键是「写回配方」**。活动改版不是每次都找人改代码，而是：
`跑失败 → 我看一眼 → 写回 recipes/xxx.json → 下次 L1 直接过`。
**变化被吸收进配方，不变成你的维护负担。**

**防误报**（比失败更危险）：
- 每步点击后必须验证（界面指纹变化 或 验证词出现）
- 只有验证通过才记 `OK`
- 「点了但界面没变」→ 记为 `NO_EFFECT`，不计入成功
- 连续 3 天 `NO_EFFECT` → 自动停跑该活动，标记 `DEAD`，等你确认

## 3. 自动化测试工具要不要引入 —— 引入两个，不引入三个

调研结论（详见 `research/自动化工具选型.md`）：

| 工具 | 结论 | 理由 |
|---|---|---|
| **uiautomator2** | ✅ **主力** | 已在用。设备端 JSON-RPC、watcher 本地弹窗、xpath 服务端求值、手势齐全。唯一缺点是 selector 偶尔匹配不到（实测淘宝「红包签到」文本在 XML 里但 selector 查不到），需 fallback 到 XML 解析 |
| **Maestro** | ✅ **引入（配方格式参考）** | 声明式 YAML、`retry` 块、自动等待策略。**不换引擎**，但配方语法借鉴它，天然带容错 |
| **Airtest + Poco** | ⚠️ 备用 | 图像识别（找不到文本按钮时用），游戏/自绘 UI 场景强。体积大，按需装 |
| Appium | ❌ 不用 | 太重，为跨平台测试设计，签到场景杀鸡用牛刀 |
| AutoJs6 设备端 | ❌ 不用（本方案） | 手机端跑脚本确实省 Mac 依赖，但调试成本高、版本停更。留作二期可选 |

**引入 Maestro 的价值不在运行，而在配方语法**：它的 `tapOn` / `assertVisible` / `retry` / 自动等待，正好是我要的语义步骤结构。抄格式不抄引擎，省一堆设计。

## 4. 每日运行形态

```
定时触发（Hermes cron，或 Mac 上 launchd）
  │
  ├─ 读 accounts + activities，算出今天该跑哪些、各自时间窗
  │
  ├─ 串行队列（一台机同一时刻只能操作一个 App）
  │   ├─ 体检：开 App 判登录态
  │   ├─ 正常 → L1 配方回放
  │   ├─ 失败 → L2 现场决策 + 写回配方
  │   └─ 掉线 → 记 NEEDS_LOGIN，跳过
  │
  ├─ 汇总：成功 X / 失败 Y / 需登录 Z / 今日折合 ¥N
  └─ 推一条消息给你（附失败项截图）
```

**时间窗**：每个活动有自己的允许时段，实际执行在窗口内随机偏移 —— 既避开「所有 App 同一分钟集中点击」的风控特征，也避开签到入口的时段限制。

## 5. 现实约束（必须承认）

1. **一台机只能串行**。8 个 App × 约 90 秒 = 12 分钟。可以接受，但不可能「瞬时全部完成」。
2. **登录态是最大瓶颈**。实测 6 个 App 里 4 个掉线。方案里 L0 体检就是为此存在。
3. **收益远小于维护成本**。单账号每天几毛到几块，每个 App 一年改版数次。**建议控制在 5~8 个高价值、入口稳定的活动**，别把 50 个都接进来。
4. **多开受系统限制**。adb 不能切用户，只能靠系统应用双开。
5. **风险分层**（X 上 @TobyAtLarge 的判断，与实测一致）：小程序/品牌会员签到几乎无风险；需自动登录的中等；网赚 APP 带设备签名+强风控，金币类封号清零是常态。**建议只做前两类。**

## 6. 落地步骤

| 阶段 | 做什么 | 产出 |
|---|---|---|
| **P1** | 账号表 + 活动表 + 账本骨架；选 1 个已登录 App（淘宝或京东）跑通 L1 配方回放 | 1 个活动能每天自动签到并记账 |
| **P2** | L2 升级链路：故意改坏配方，验证「失败→LLM→写回→下次通过」 | 自愈能力可用 |
| **P3** | 扩展到 5~8 个活动；接 cron 定时；失败汇总推送 | 每日自动跑 |
| **P4**（可选） | 多开账号接入；Airtest 图像识别兜底；AutoJs6 设备端迁移 | 规模化 |
