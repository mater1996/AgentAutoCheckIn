# 系统观察记录实现

本实现属于《统一观察导航与执行整改方案》第一步中的 device 最小观察记录。只关联设备已有 foreground 读取与截图，不新增 ADB 命令，不把 Activity/task 当作业务页面身份或动作授权。

## 接口

`DeviceFrame.systemObservation` 为可选字段，兼容历史帧和既有离线构造帧：

```ts
{
  version: 'android-system-v1',
  before: {
    marker: 'topResumedActivity' | 'mResumedActivity' | null,
    activity: string | null,
    taskId: number | null,
    source: { path: string, sha256: string, startedAt: number, endedAt: number }
  },
  after: { /* 与 before 同形 */ }
}
```

类型在 `runner/staged/system-observation.ts` 导出：`SystemObservation`、`ForegroundObservationRecord`、`SystemObservationSource`。before 对应截图前成功的 foreground 命令，after 对应截图后的原有 foreground 命令。命令 JSON 路径为私有 evidenceDir 下的 `device-command-evidence/foreground-<uuid>.json`。SHA-256 对写入完成的完整 JSON UTF-8 字节计算，包含实际 command/stdout/stderr/status/起止时间等证据；不是 stdout 子串或历史 dump 文件的哈希。记录中的起止时间直接来自该命令证据。

原始 dump 只保存在私有命令证据中；帧上没有额外 URL、Intent、原始 stdout 或窗口字段。组件保留 dump 中的字面写法，不猜测 URL 或展开未知业务路由。

## 绑定与执行边界

`recordedCommand` 提前分配 UUID 路径，在原 finally 中完成证据写入，成功写入后才向可选观察回调传递 source。foreground 返回对象仍严格只有 package/userId，避免扩大原身份对象或帧顶层字段。capture 的观察回调单独构造 systemObservation，帧顶层仍由原身份返回值提供 package/userId。

正常 capture 的执行序列保持 `foreground → screencap → foreground → OCR`。两个 foreground 的 Activity/task 可以不同，只要原 package/user 检查通过；新增记录属于旁证。已存在的启动后一次 missing-marker 重读中，before 绑定真正成功的确认命令；失败的 missing 命令仍有独立原始证据，不成为 before 来源。

读取器优先使用 topResumedActivity；存在但畸形的 top marker 不借用 mResumedActivity。无 top 时才选 mResumedActivity；Activity 不一致为 null，task 不一致或缺失为 null。后台任务和 Intent 不参与当前状态推断。该读取器不授予任何执行权限，原 foreground 的 package/user 唯一性与合法性检查继续决定是否允许 capture/act。

截图后成功读取即保存两个来源到帧，包括随后因 package/user 变化而拒绝的失败帧；OCR 失败也保留关联。截图后 foreground 自身执行/解析/写证据失败时，没有成功 after，不构造完整 systemObservation；原始命令证据与已保存 PNG/失败帧沿用原处理。拒绝的 capture 不设置 currentFrame，保留原帧消费、时效、并发和执行前复核行为。

命令执行/解析失败与证据写入同时失败时，继续抛原始错误；原成功命令写证据失败则拒绝 capture。原 MissingForegroundMarkers.recorded 仍须实际保存成功，才可能获得已授权启动后的单次重读。
