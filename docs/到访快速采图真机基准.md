# 到访快速采图真机基准

只读采图测量，不领取、不进入任务、不调用模型API、不写运行收益账本。每轮withDeviceLock内prepare、原图captureBurst、后续deriveFrames、cleanup，最后Dozing且errors=[]。

第一轮证据 `evidence/raw-capture-benchmark-2026-11-01T11-06-50-016Z/benchmark.json`：8帧/250ms目标，总2000ms。实际2000.46ms超时，仅3帧完成持久化；立即derive报Raw capture busy，说明超时的外部调用仍在收尾。未将此称成功。本轮诊断脚本未显式跟踪外部调用drain，不能作为生产接入示范；生产main已有pending跟踪并在释放共享锁前drain。

第二轮证据 `evidence/raw-capture-benchmark2-2026-11-01T11-07-33-323Z/benchmark.json`：2帧/250ms目标，总1800ms，注入真实execFile并显式跟踪/drain外部调用。实际采图1280.07ms完成；一次真实本地Apple OCR解析615.45ms。两帧各63行，最终原始capture年龄1819ms、1149ms，均在5秒期限内。原id/path/capturedAt与source hash保留。没有toast事件，不能证明瞬时完成识别或领取可靠率。

结论：本机ADB前后foreground核验+PNG保存方案无法在2秒稳定采满8帧；两帧链路此次通过。

后续TDD实现显式`controllerCandidates[].capturePolicy={frames:2,intervalMs:250}`，从config经route传至controller；不配置保留旧8帧默认。frames必须1–8整数、interval0–250整数且计划跨度小于2000ms，错误配置在tap前拒绝，capturePolicy纳入route binding防中途改策略。相关controller/runtime/route/main22/22、staged类型通过；正常入口历史panel回放进一步断言原dispatcher实际收到frames2/interval250，8/8通过。没有启用真实到访live配置，仍缺真实短toast和正收益验收。

后续按实测配置再做下一次到访候选，不降低原toast组件识别、attempt/owner、5秒期限和正收益门禁。实际捕获短toast需下一次真实到访入口出现后验收，不能用静态列表截图代替。

最近任务收益确认仍为181/182各20；185列表观察2085，较2050多35未归因。本基准不改变收益归属或稳定审计。
