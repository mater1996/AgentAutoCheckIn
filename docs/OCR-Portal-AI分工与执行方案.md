# 签到系统：OCR、节点树、AI与动作工具分工方案

状态：方案待确认。只读了本地实测/现有代码并核查官方接口；未修改执行器、未操作手机、未调用业务模型、未启用调度。这里“Appium”指前文所说的arium，“Midscene”指midscne。

## 1. 推荐结论

保留现有TS业务计划、设备锁、SQLite账本。用本地OCR承担常见文本页面读取，必要时用AI理解图片或新流程；Portal/ADB承担统一动作，Appium保留为其他页面的结构化读取候选和诊断工具，不把已知旧树的淘宝任务列表交给它作为唯一依据。

不能简单排成“OCR不行→Portal→AI”的固定顺序：不同页面/字段选证据。淘宝滚动任务页已证实节点旧，继续读树增加成本但不能补齐；原生输入框可能反而适合节点。每个关键字段记录来源、截图、时间、可信性与是否允许动作。

Midscene不是独立于AI识图的第五种识别引擎：它负责把截图送给模型、解析结果、定位或组织动作。推荐复用现有Midscene只读静态截图适配器来补读，日常动作仍走单一调度器。

## 2. 工具分工和使用条件

| 工作 | 首选 | 什么时候升级/换工具 | 目前证据 |
| --- | --- | --- | --- |
| 任务标题、已做/总次数 | OCR，屏间重叠合并 | 漏行、重复冲突、裁剪、模糊或不明页面，补拍/裁剪一次，再AI补读 | 旧截图整表21/21匹配，仅一组样本 |
| 任务要求、奖励、按钮归属 | OCR文本+行几何候选，再校验 | 图标混入文字、奖励多档、多个相邻按钮、语义不明，用AI读同一截图 | OCR说明已出现错字；此部分未通过验收 |
| 任务页上下界和采集是否完整 | OCR边界文本+重叠连续性+回顶复核 | 新布局/找不到边界，AI判断；仍不明标不完整 | 本轮人工截图21项收全；自动OCR滚屏尚未实测 |
| 常见原生按钮/输入框 | 经当前画面核验新鲜的Portal或Appium节点；OCR定位也可 | 节点过时/缺失，退到OCR或AI定位 | 淘宝任务树跨屏冻结；不能用正常响应当新鲜证据 |
| 没文字的图标、图片卡片、复杂遮挡 | AI识图，经Midscene只读query/locate接口 | 解释不确定或目标不唯一时暂停；不能猜坐标 | 既有视觉路线成功过一轮，成本偏高 |
| 点击、滑动、返回 | 一个动作调度器，调用Portal或ADB | 确认无效果后才有限切换后端；异常未知时先读屏 | Portal导航曾成功；当前ADB修正尺寸后整表滚动成功 |
| 文本输入 | 已验证的输入通道；节点/图像确认焦点和结果 | 新输入页先学习与实测，不能假设中文可直接shell input text | 历史存在焦点/通道问题，不在本方案承诺已全部打通 |
| 选择做什么、顺序和停止条件 | 完整结构化清单+用户边界交给文字模型 | OCR证据不足或依赖图片语义时才加入对应截图 | 不按固定任务名称推断浏览/搜索/游戏等动作 |
| 新任务实际怎么完成 | AI结合真实落地页理解；首次监督验证 | 必须得到明确要求，越界/登录/验证就停 | 保存实际流程与成功条件，复用需核对适用上下文 |
| 完成与收益核验 | 同次任务回执+返回任务状态+正确资产页余额 | 读不清/数值冲突时AI补读；无证据记未知 | OCR读到“已完成”或余额增量单独都不足以证明该任务完成 |
| 记账、重试上限、去重、计划更新 | 本地TS/SQLite | 无需模型做算术或自行写收入 | 沿用现有账本与证据门禁 |

“本地OCR”仍是识别模型，只是不调用对话式视觉大模型；没有LLM API调用不代表没有计算或首次初始化成本。Apple Vision当前依赖这台Mac；未来移到Linux需重新选型和实测。

## 3. 一个具体任务怎么走

例子采用已见过的“你关注的商品都可抵(0/1)”与“浏览15秒”说明，但以下OCR接线与执行流程是拟议方案，不代表该任务已通过新路线跑通。此处不预设落地页一定只需等待15秒，最终以实际页面和监督学习为准。

### 第一步：先拿完整清单

ADB截图→OCR读本屏标题、次数、说明、奖励和按钮候选→统一调度器滚动→检查当前任务区域文字/位置确实变化→继续直到明确底部→返回顶部复核。按任务名、真实说明、次数总额及上下文去重；同名不同说明不强合并。

例如本轮参考截图有21项，验收时应将OCR输出与当次人工图审全表比较；21不是硬编码期望数，之后任务可能变化。只有明确顶部、相邻屏重叠连续、底部说明、回顶一致才允许标“收集完整”。画面没动不是到底，树没变也不是画面没动。

读取不到要求时保留unknown。可先标“标题清单完整、执行信息不完整”，只补读缺失字段；不得伪造0奖励或默认浏览时长去凑齐。影响任务选择的字段未知时不做确定性收益比较。

### 第二步：文字模型做一次业务计划

将整表原文、未知字段、允许动作、收益信息与已学流程给文字模型，输出每项做/跳过及依据、顺序、次数、停止条件。明确禁止购买/加购/支付/提现/会员/切账号/第三方登录授权；登录/验证码/人机验证就停止。

不写“任务名含浏览就等待”“任务名含小游戏就跳过”的程序分支。程序只校验计划结构、配额和允许动作范围；模型使用完整上下文和已验证经验判断。需要进一步了解的任务标待了解，不能编造做法。

### 第三步：找到当前任务对应按钮

回到目标当前所在屏，再截一帧OCR。只有任务身份/次数/说明匹配、标题与按钮在同一无遮挡行、候选唯一、坐标属于当前图时，调度器才点击一次。

若一屏有八个“去完成”，OCR只看到文字并不能保证知道哪个属于目标；须靠行容器/几何对应校验，多个候选或错位则AI结合当前整帧确认。第一次建立布局规则可让AI指导，但后续仍做当前框与遮挡验证，不能记住“第几个按钮”。滑动、弹窗、导航、键盘出现后所有旧坐标作废。

### 第四步：打开后理解真实要求，再执行

首次遇见的新落地页，通过Midscene只读aiQuery查看当前画面，解释实际要求、剩余时间、是否输入/搜索、完成证据是什么。业务计划接受这次新信息后才能派发有限动作；若与原计划冲突，停止该任务并更新计划。

已监督跑通的流程，可由本地程序按保存的实际要求执行点击/输入/有限等待，OCR读取倒计时和结束提示。页面、要求或关键条件不匹配时转回AI或停，不因名字没变就继续。新复杂流程确需Midscene aiAct时，作为单独“学习会话”独占动作权限，明确边界和请求/时间预算；结束或出错先读回现场再把权限交还本地执行器，不让两个控制器并行操作。

### 第五步：拿证据，再回列表核对并记账

先保存当次任务明确回执，再返回正确任务/资产页面，OCR读取对应次数与余额。如果反映“浏览15秒”但页面没有该任务的完成回执，仅等待够时长不报成功。

沿用已有成功门禁：当次回执、正确归属的任务状态、正确资产页实际变化相互一致；任务被替换需保留旧身份，不能把新任务0/1当作未完成再点一次。余额滚轮/动画或图标混淆时补一帧，仍不清再AI补读；不拿错误页面的数字入账。TS计算净变化，SQLite保存证据与结果，更新剩余任务计划。

## 4. 三个常见场景直观对照

**场景A：列表有标题、0/1和“去完成”。** OCR读清单；本地程序去重、核对次数并组织按钮候选；Portal/ADB滑动点击。只要字段与位置校验通过，本屏不需要视觉AI。文字模型在完整清单收齐后做业务计划。

**场景B：按钮只有一个图标，或打开新任务页不清楚要做什么。** AI读当前图、解释/定位；通过Midscene调用，动作由统一调度器执行。不是因为OCR报了高置信度就有任务语义。

**场景C：普通原生设置页/搜索输入框。** 经当前画面确认后，Portal/Appium可提供结构、输入框状态与坐标；适合无需每次大模型定位的确定操作。不能把该页面树好用推广成淘宝WebView滚动列表也可靠。

## 6. 怎么决定要不要调用视觉AI

只把OCR自报置信度当信号，不能单独决定“读对”。以下任何一条涉及执行或计划的关键字段时，先有限重读/扩大同帧裁剪，仍不明再AI补读：

- 当前页身份/遮挡不清、文字框裁切、次数格式不合法或两帧冲突。
- 多个候选按钮、行边界交错、目标在固定标题/键盘后面。
- 说明和金币图标混在一起、多个奖励数字含义不清、余额动画尚未稳定。
- 滚动后任务区域明显变了但记录没更新，或相邻页没有可确认的重叠。
- 新的任务落地页、图标语义、需要理解搜索/浏览/小游戏等实际交互。

截图文字只作为观测数据，不能成为授权扩大动作范围的指令。AI对看不清的字段允许返回未知；补读失败就标不完整/暂停，不能无限重试。启动预算先采取保守有界策略，具体调用次数和耗时根据首轮真机结果再定，不预先承诺“每轮零视觉”或精确节省比例。

## 7. 实施和验收顺序

1. **只读采集。** 接OCR到完整滚动采集，检查所有任务标题/次数/要求/奖励分别的漏项错项，逐屏存证据、确认头尾、回顶复核。先跑一次监督样本；通过后换时段/任务更新再重复，不用同图重复冒充长期稳定。
2. **只定位，不点击。** 对整表目标逐屏核对按钮归属、遮挡和位置，记录正确/错误/未知，再人工审计；未通过不执行。
3. **一个已授权普通任务闭环。** 收集→计划→执行→回执→余额→记账→更新剩余计划，说明哪些步骤零视觉、哪些为什么升级，实测总耗时/调用/token。整表正确不等于执行闭环通过。
4. **再扩到整批。** 未经用户确认跑通，不开无人值守定时任务。
