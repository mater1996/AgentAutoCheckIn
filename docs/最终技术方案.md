## 0. 目标（先定义清楚，再谈实现）

**核心：把各平台的签到任务统一打通，持续累积有长期价值的虚拟资产（积分/币），并把资产存量和增速可视化。**

| 优先级 | 目标 | 含义 |
|---|---|---|
| 1 | **不封号** | 不触发风控。封号收益归零，还会连累主账号 |
| 2 | **资产净增长** | 记的是「存量」和「增速」，不是单日流水 |
| 3 | **零日常人工** | 做不到就坚持不下去 |
| 4 | **平台可扩展** | 新增 App = 写一份配置，不改代码 |
| —— | 账面数字好看 | **不是目标**。账面 0.6 花不出去等于 0 |

**明确不做的**：短时红包（7~15 天过期、只能凑单用、面值小）。它是一次性优惠券，不是资产。

## 1. 技术选型

| 层 | 选型 | 为什么 |
|---|---|---|
| 执行引擎 | **Midscene.js `@midscene/android` 1.17.3** | 唯一靠「看截图」定位的路线。淘宝签到图标在无障碍树里没有节点，控件树方案碰不到 |
| 视觉模型 | **`codex/gpt-6.1-sol`**，走本机网关 `http://127.0.0.1:3425/v1` | 实测 4/4 定位准确；ChatGPT 订阅内不按 token 计费 |
| 设备控制 | **adb**（platform-tools 37.0.1） | Prep 归位、读数、缓存判断全部本地，0 模型调用 |
| 存储 | **SQLite（WAL）+ better-sqlite3 + Drizzle** | 查询是聚合型（存量/增速/过期），JSONL 不合适 |
| 面板服务 | **Node http + 原生 HTML + ECharts** | 零构建、单进程、1 秒启动。本地面板不需要 SSR 框架 |
| 配置 | **YAML**（accounts / assets / activities） | 人可读、可 git、加平台不改代码 |
| 调度 | launchd / Hermes cron | Mac 常开 |
| 通知 | 飞书 webhook | 已有连接 |

**为什么不用 Nuxt**：本地面板单用户、无 SEO、无路由需求。零构建的 Node + ECharts 少一层依赖和一次构建，出问题更好排查。若将来要远程多人访问，再套框架不迟。

**为什么不用 FastAPI**：Midscene 是 Node 包，执行器必须是 Node。统一 Node 避免维护两套运行时。

## 2. 系统架构

### 2.1 三进程模型

```
┌──────────────────────────────────────────────┐
│ 浏览器                                        │
│   面板：资产总览 / 存量曲线 / 活动状态 / 记录   │
└───────────────────┬──────────────────────────┘
                    │ HTTP :8787
┌───────────────────▼──────────────────────────┐
│ 进程 A：panel（只读）                          │
│   读 SQLite 出数据；绝不操作 adb                │
└───────────────────┬──────────────────────────┘
                    │ SQLite (WAL)
┌───────────────────▼──────────────────────────┐
│ 进程 B：runner（执行器）                       │
│   Prep → 解释 flow DSL → 读余额 → 记账         │
│   独占 adb，串行；崩溃不影响面板                │
└───────────────────┬──────────────────────────┘
                    │ adb
┌───────────────────▼──────────────────────────┐
│ 手机                                           │
└──────────────────────────────────────────────┘
```

**为什么必须拆**：一次签到 2~4 分钟，放 API 进程会卡死面板；adb 是独占资源；执行器崩了面板还要能看历史。

### 2.2 数据流

```
config/*.yaml ──sync──▶ SQLite（账户/资产/活动，只读镜像）
                            │
cron / 手动 ──▶ runner ──▶ run + asset_snapshot + cache_state
                            │
                        panel ──▶ 浏览器
```

YAML 是唯一真源；DB 是镜像。**不做双向编辑**，避免同步地狱。

## 3. 核心抽象：流程 DSL

**不同平台的签到大同小异，差异只在步骤序列。所以流程用 DSL 表达，执行器不认识"签到类型"。**

### 3.1 步骤类型

| `do` | 参数 | 用途 | 模型调用 |
|---|---|---|---|
| `ai` | `say`（自然语言）、`optional`、`wait` | 任何需要看图的动作 | 1 |
| `read` | `as: before\|after` | 读资产余额 | 1 |
| `dwell` | `seconds` | 停留（浏览类任务硬要求） | **0** |
| `back` / `swipe` | `wait` / `direction`、`times` | 导航 | **0** |
| `tap_text` | `text`、`optional` | 按无障碍文本点击 | **0** |
| `wait_for` | `text`、`timeout_ms` | 等文本出现 | 1 |
| `repeat` | `max`、`stop_when`、`each[]` | 批量任务，带停止条件 | 按内部步骤 |

### 3.2 三种形态，同一套引擎

```yaml
# ① 单点签到（京东形态）
flow:
  - do: ai
    say: 点击「签到」按钮
  - do: read
    as: after

# ② 档位奖励（淘金币形态）
flow:
  - do: ai
    say: 点击「立即领取」
    optional: true

# ③ 批量浏览任务（淘金币任务形态）
flow:
  - do: repeat
    max: 3
    stop_when: 任务列表里已经没有任何显示「去完成」的任务了
    each:
      - do: ai
        say: 在任务列表里找到第一个还显示「去完成」的任务，点击它
      - do: dwell
        seconds: 12
      - do: back
```

**没有任何 `if platform == 'taobao'` 这种分支。** 平台差异 100% 落在配置里。

### 3.3 余额差是唯一可信的收益来源

```
read before → 执行 → read after → delta = after - before
```

不用「应该得多少」（活动经常缩水发奖），不用「页面说成功了」（可能是残影）。

判定顺序：
1. `delta > 0` → `OK`
2. `delta = 0` 但验证词命中 → `ALREADY`（今天已领过）
3. 有步骤失败 → `ERROR`
4. 其他 → `NO_EFFECT`

**额外一条数据卫生规则**：若 `before > 0` 而 `after = 0`，判为**读取失败**而不是真的清零，不回写快照。跨页面读数（不同页面显示不同数字）产生的脏快照会被标 `INVALID_READ` 并删除——账本里宁可缺数据，也不要错数据。

## 4. Prep：起始状态契约

### 4.1 为什么必须有

Midscene 的缓存键是**指令文本**，**不包含起始页面**。起始页不对 → 计划失效 → 官方清空该 prompt 的缓存 → 下次重新规划。**起始状态不稳定 = 缓存永远命中不了。**

### 4.2 六阶段（全程 adb 本地判断，0 调用）

| 阶段 | 动作 |
|---|---|
| P0 设备健康 | 设备在线 / 亮屏 / `wm dismiss-keyguard` / 电量 > 15% |
| **P0.5 风控闸门（有作用域）** | **只在「目标 App 已在前台」时判定**：屏幕出现「验证后 / 滑块 / 人机验证 / 安全验证」→ 立即 `NEEDS_HUMAN`，不启动、不绕过。实测 2.4s 拦截 |
| P1 清干扰 | 收通知栏 + 按关键词点掉系统弹窗（≤4 轮） |
| P2 启动 App | 前台包名不对才 `am start`；冷启动才 `force-stop` |
| **P2.5 启动后闸门** | 目标 App 一起来就在验证页 → 同样 `NEEDS_HUMAN`（先判一次，别等它跑完才发现） |
| P3 等待就绪 | 轮询首页特征文本，400ms 间隔，每 5 轮清一次广告 |
| P4 归位 | `back` ≤3 次 → 仍不对则冷启动兜底 |
| P5 起始断言 | 特征文本未命中 → `NEEDS_HUMAN`，**不允许 Midscene 开跑** |

### 4.3 杀端还是归位

| 策略 | 结论 |
|---|---|
| 每次都冷启动 | ❌ 5~9s×活动数，且每次触发首屏广告，反而要更多清理 |
| 不干预直接跑 | ❌ 起始页不确定，缓存必然失效 |
| **back 归位，失败才冷启动** | ✅ 默认 |
| **每 App 每天首个活动冷启动** | ✅ 配合使用，拿干净起点 |

## 5. Midscene 缓存

### 5.1 两类缓存

| 缓存类型 | 缓存键 | 内容 | Web | Android |
|---|---|---|---|---|
| 任务指令缓存 | 规划 prompt | 执行计划（步骤序列） | ✅ | **✅ 生效** |
| 元素定位缓存 | 定位 prompt | 元素 XPath | ✅ | ❌ 仅 Web |

**Android 上缓存「先做什么」，不缓存「按钮在哪」。** 实测 56.2s → 32.6s（省 42%）。

### 5.2 缓存策略

| 策略 | 用于 |
|---|---|
| `read-only` + 成功才 `flushCache()` | **生产默认**：只在成功路径写，避免半截路径污染 |
| `write-only` | 重建缓存 |
| `read-write` | 开发调试 |

缓存文件：`midscene_run/cache/<cache_id>.cache.yaml`，一账号一份（`cache_id` 必须隔离，否则 A 的路径会套到 B 上）。

### 5.3 改版检测与自动重建

淘宝改版**不走应用商店**（首页模块、活动页、签到入口都是服务端下发），所以「关自动更新」无效。正确形态是：

| 环节 | 做法 |
|---|---|
| 检测 | 7 日滑动平均看 `cache_hit` 与 `exec_ms` 拐点 |
| 重建 | 清缓存，`write-only` 跑一次全量规划 |
| 验证 | 重建后立刻 `read-only` 再跑，验证通过才算成功 |
| 降级 | 重建 2 次仍失败 → 推送人工，停跑该活动 |
| 成本 | 走订阅通道边际成本 ¥0 → **重建不心疼** |

## 6. 数据模型

### 6.1 资产导向（不是流水账）

| 表 | 作用 |
|---|---|
| `asset` | 资产定义：平台、单位、汇率、有效期、兑换路径 |
| `asset_snapshot` | **每次读到的余额（主数据）** |
| `run` | 每次执行记录（辅助） |
| `account` / `activity` | 由 YAML 同步的镜像 |
| `cache_state` | 缓存健康 |
| `job` | 任务队列（面板只入队） |

### 6.2 核心 Schema

```sql
-- 资产
CREATE TABLE asset (
  id TEXT PRIMARY KEY, platform TEXT NOT NULL, name TEXT NOT NULL,
  unit TEXT NOT NULL,
  cny_per_unit REAL NOT NULL,      -- 唯一折算入口
  expiry_days INTEGER,             -- null = 长期
  redeem_path TEXT, note TEXT
);

-- 余额快照（主数据）
CREATE TABLE asset_snapshot (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts TEXT NOT NULL, day TEXT NOT NULL,     -- day 用本地时区，不能用 UTC
  asset_id TEXT NOT NULL, account_id TEXT NOT NULL,
  balance REAL NOT NULL, source TEXT DEFAULT 'read', run_id INTEGER
);
CREATE INDEX idx_snap_asset ON asset_snapshot(asset_id, day);

-- 执行记录
CREATE TABLE run (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts TEXT NOT NULL, day TEXT NOT NULL,
  account_id TEXT NOT NULL, activity_id TEXT NOT NULL,
  status TEXT NOT NULL,            -- OK|ALREADY|NO_EFFECT|ERROR|NEEDS_LOGIN|NEEDS_HUMAN|...
  cache_hit INTEGER, cold_start INTEGER DEFAULT 0,
  prep_ms INTEGER, exec_ms INTEGER,
  balance_before REAL, balance_after REAL,
  error TEXT, evidence_dir TEXT
);
```

### 6.3 关键指标

| 指标 | 口径 |
|---|---|
| 存量 | 最新快照的 balance |
| 今日净增 | 今日最后一条 − 前一日最后一条 |
| 7 日净增 | 今日 − 7 天前 |
| 折算价值 | 存量 × `cny_per_unit` |
| 过期风险 | `expiry_days` 与快照日期推算 |

## 7. 面板

`http://127.0.0.1:8787`，单进程，只读，30 秒自动刷新。默认监听 `0.0.0.0`，同局域网设备可访问（启动时会打印本机与局域网地址）。

| 区块 | 内容 |
|---|---|
| 成本条 | 今日/累计 tokens、调用次数、按参考价折算的 ¥、按意图（plan/locate/insight）的分布 |
| 收益 · 成本 · 净收益 | 四张卡：累计收益（账面）、累计成本（参考价）、累计净收益、统计天数 |
| 每日收益 vs 成本 | 组合图（收益柱 / 成本柱 / 净收益线 / tokens 虚线右轴）+ 明细表 |
| 账号 · App 细分 | 按 (账号, 活动) 聚合：累计收益（原始单位+折算）、成本、净、执行次数、成功/已签/异常、最近状态与日期 |
| 资产卡 | 每种资产：存量、折算、今日净增、7 日净增、读数次数、过期天数 |
| 资产存量曲线 | 30 天折线，按资产分系列 |
| 活动状态 | 时间窗、最近状态、耗时、最近错误 |
| 执行记录 | 每次 run：状态、余额变化、Prep/执行耗时、tokens、调用次数 |

**接口**：`/api/overview` · `/api/daily?days=30` · `/api/breakdown` · `/api/trend?days=30` · `/api/activities` · `/api/runs?limit=25`

### 7.1 成本观测

Midscene 已经按调用累计了 token，直接读 `agent.metrics`（`destroy()` 之前），落进 `run` 表：

| 字段 | 来源 |
|---|---|
| `prompt_tokens` / `completion_tokens` / `total_tokens` | `metrics.total*Tokens` |
| `cached_tokens` | `metrics.totalCachedInput` |
| `model_calls` | `metrics.calls` |
| `usage_json` | `metrics.byIntent` + `byModel`（可拆出 plan 与 locate 各花多少）|

收益与成本的换算：`成本¥ = tokens / 1e6 × COST_PER_MTOK`（默认 ¥2/百万，仅作参考价）。

**为什么仍要记一个参考价**：订阅通道当下边际成本是 ¥0，但一旦需要切到按量计费的备通道，这个数字立刻变成真金白银；面板上并排显示「收益 ¥ / 成本 ¥ / 净 ¥」，才能回答"这套自动化到底划不划算"。

### 8.1 屏幕常亮只在执行窗口内生效

`stay_on_while_plugged_in` 是位掩码：`1`=AC、`2`=USB、`4`=无线、`8`=底座，`15` = 全开。

不常亮时默认 1 分钟熄屏，Midscene 截到黑屏直接失败；但一直常亮耗电、有烧屏风险。所以执行器在 `runActivity` 入口保存原值 → 置 `15` → 无论成功、报错还是超时都在 `finally` 写回原值。

实测：基线 `0` → 运行中 `15` → 结束 `0`；异常路径基线 `3` → 抛错后仍 `3`。

注意这条设置**只在插电时有效**，跑任务必须保持充电。

## 9. 新增一个平台的方法

**四步，零代码改动：**

1. `config/assets.yaml` 加资产（汇率、有效期、兑换路径）
2. `config/accounts.yaml` 加账号（**必须先实测首页锚点文本**，写进 `prep.entry_text_any`）
3. `config/activities/<app>.yaml` 写 flow（步骤用第 3 节的 DSL）
4. 跑一次 `sync-e2e.ts <activity_id>` → **第一次必须人工看报告确认路径正确**，之后才能交给 cron

### 9.1 写配置的三条硬规则（都是踩坑换来的）

| 规则 | 为什么 |
|---|---|
| **`verify.any` 里绝不能放平台名**（如「京豆」「淘金币」） | 页面上到处都有这个词，`aiBoolean` 会恒为真 → 每天误判成 `ALREADY` |
| **每个 `read` 必须自带 `say`**，点名要读哪种资产 | 通用问句会读到页面上别的数字（实测京豆被读成 0） |
| **`ai` 步骤要短、边界清楚** | 「把能领的都领掉」这类复合指令会让模型漫游（实测 153s 跑进兑换页），单步只做一件事 |
| **`before` / `after` 两次 `read` 必须读同一个指标** | 不同页面/位置显示的是不同量纲（实测：京东「我的」页京豆总数 888，「京豆」页显示“今日获得 3”）。注意不是"同一页面"这么严格——淘金币任务页顶部也显示金币总额，两次都读「淘金币数量」就成立；关键是问句指向同一个数和同一种语义 |
| **平台改文案只改配置** | 京东这一期的签到入口叫「立即刮卡」不是「签到」——写成两条 optional 步骤，两个都试即可，不动代码 |

### 9.2 第一次跑一定要人看

新建的 flow 第一次执行时缓存是空的，AI 现场规划，路径可能不对。**必须人工看一遍 Midscene 报告**（`midscene_run/report/*.html`，每步都有截图和坐标），确认它点的是对的地方，再交给无人值守。

| 项目 | 结果 |
|---|---|
| 视觉定位精度 | 800px JPEG 下 4/4 命中，偏差 0.011~0.046（图标约 108px） |

### 踩过的坑（已修）

| 坑 | 真相 |
|---|---|
| 淘宝图标区定位 | 「领淘金币/红包签到/芭芭农场」在无障碍树里**既无 text 也无 content-desc**（Canvas 绘制），只能视觉定位 |
| 淘宝底部导航 | 以 `content-desc` 暴露：首页/视频/消息/购物车/我的淘宝 |
| 淘宝页面切换 | 所有页面共用一个 Activity（`welcome.Welcome`），**不能靠 Activity 名判断页面** |
| HyperOS 前台 Activity | 用 `topResumedActivity=`；`dumpsys window windows` 里没有 `mCurrentFocus`，要 `dumpsys window` |
| 设备端管道 | `adb shell "dumpsys \| grep"` 会断管丢输出 → 一律拉回本地解析 |
| 日期 | `toISOString()` 是 UTC，凌晨跑会记到前一天 → 用本地时区 |
| 单步 `aiTap` | 会偏约 100px（落在图标边缘外）；`ai()` 整段规划会自行重试 |
| 复合指令 | 「把能领的都领掉」会让模型漫游（实测 153s 跑进兑换页）→ 步骤必须短、边界清楚 |
| 缓存空文件 | `aiTap` 是定位动作，Android 不缓存 → 只有 `ai()` 才产生 plan 缓存 |
| **缓存失效的真实日志** | 实测捕获到 `cached aiAct plan failed, will replan and disable the stale cache` —— 官方描述的"失败即清空该 prompt 的 flow"确实发生，因此起始状态不稳的代价是**缓存被反复清空** |
| **京东的刮卡是任务门控的** | 页面提示「做任务解锁刮卡」时直接点刮卡必定失败；完整形态是「做任务 → 解锁刮卡 → 刮卡」。淘宝淘金币同理（「做任务解锁档位奖励」）。**两个平台的"签到"实质都是任务制** |
| **锚点太松会让 prep 假成功** | 京东原先用「搜索栏 / 推荐」判首页，但这两个词在京豆等二级页也有 → prep 误判归位，before 读数取到二级页的数字（实测 3 而非总额 1088）。**锚点必须选只在起始页稳定出现的元素**：优先底部导航的 `content-desc`（京东=首页/我的/购物车/消息/分类，淘宝=首页/视频/消息/购物车/我的淘宝） |

## 12. 风险与对策

| 风险 | 对策 |
|---|---|
| 起始状态不稳 → 缓存反复失效 | Prep 五阶段 + P5 起始断言；命中率告警 |
| 缓存被污染 | `read-only` + 成功才写 + 每日备份 |
| 平台改版 | 检测拐点 → 自动 `write-only` 重建（成本 ¥0） |
| 风控升级 | 时间窗随机化、每日一次、不硬过滑块、控制活动数 5~8 个 |
| 账号被封 | 优先小号；核心账号不多设备并发 |
| 手机长期插电 | 充电上限 80%、通风处 |
| 单模型通道 | 抽象 model 层，随时可切豆包/GLM |
| launchd 找不到 adb | plist 显式声明 `PATH=/opt/homebrew/bin:...` |
| 合规 | 仅自用；不对外提供服务 |
