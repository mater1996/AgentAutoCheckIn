# 任务标准流程 v1

目标：**任何签到/任务类活动，都用同一套流程表达。新增平台只写配置，执行器不改。**

现在的问题：`activity.steps_json` 把「目标、探测、任务选择、执行单元、终止条件」全压进一个数组，
所以 `max: 3` 是拍脑袋的，引擎不知道跨档值钱，也说不出"还剩几个任务"。

---

## 1. 七段标准流程

```
① PREP      归位到起始页        adb 本地，0 调用
② ENTRY     进入任务页          配置的步骤
③ PROBE     探测当前状态        1~2 次调用，返回结构化数字
④ PLAN      本地算该做多少      0 调用，纯计算
⑤ ACT       循环执行任务单元    每轮 1~2 次调用 + 0 调用的 dwell/back
⑥ COLLECT   领奖励             按需，1 次调用
⑦ SETTLE    读终态 + 判状态     1 次调用
⑧ BOOK      写快照 + 写 run     0 调用
```

**关键分界**：`PROBE` 返回**数字**，`PLAN` 在**本地**算，`ACT` 只执行。

模型只回答"现在是什么状态"，不回答"还要不要继续"——后者是算术。

---

## 2. 配置结构（一份活动 = 一个文件）

以淘金币为例，这是**可直接实现的目标形态**：

```yaml
id: tb_coin
name: 淘金币
account_id: tb_main
asset_id: taobao_coins
window: ["09:00", "21:00"]

# ── 目标：要什么，不要"做几次"
objective:
  strategy: all_tiers              # all_tiers | first_tier | fixed
  max_seconds: 900                 # 硬时间上限
  min_marginal_cny_per_hour: 20    # 低于这个边际价值就不做了

# ── 价值模型：把"值不值"变成数字
value:
  unit_reward: 30                  # 单任务预计金币
  unit_seconds: 35                 # 单任务预计耗时（ai点击20 + dwell12 + back2 + 余量）
  tiers:
    - { at: 3,  reward: 30 }
    - { at: 10, reward: 50 }
    - { at: 20, reward: 100 }

# ── ② ENTRY：怎么进任务页
entry:
  - do: ai
    say: 点击淘宝首页上方图标区的「领淘金币」，进入淘金币页面
  - do: read
    as: balance_before
    say: 页面上显示的「淘金币」数量是多少？只回复数字，不要单位和逗号
  - do: ai
    say: 点击页面下方的「赚更多金币」按钮，进入赚金币任务页

# ── ③ PROBE：探测，返回结构化数字
probes:
  - id: progress
    ask: 页面顶部的「完成进度」是多少？按 a/b 格式只回复数字，例如 3/20
    parse: fraction                 # → {done: 3, total: 20}
  - id: tasks_left
    ask: 任务列表里还有几个任务显示「去完成」？只回复数字
    parse: int

# ── ⑤ ACT：任务单元 —— "怎么做一个任务"
task:
  select: 任务列表里第一个还显示「去完成」的任务    # "做什么"
  steps:
    - do: ai
      say: 在任务列表里找到第一个还显示「去完成」的任务，点击它
    - do: dwell
      seconds: 12
    - do: back
      wait: 2

# ── ⑥ COLLECT：领奖励
collect:
  when: claimable                  # 探测到有可领档位时才领
  probe: 页面上是否有可点击的「立即领取」按钮
  steps:
    - do: ai
      say: 点击页面上方的「立即领取」按钮
      optional: true

# ── ⑦ SETTLE
settle:
  read: balance_after
  say: 页面上显示的「淘金币」数量是多少？只回复数字，不要单位和逗号
  verify_any: [已领取, 明天再来, 已领完, 今日累计奖励已领]
```

## 3. 终止条件（算出来的，不是写死的）

每轮 ACT 之后，引擎用最新 `probe` 结果算：

```ts
const state = { done, total, tasksLeft, elapsed, cnySoFar };

// 本地计算，0 模型调用
const nextCny   = valueOf(done + 1) - valueOf(done);
const perHour   = nextCny / unitSeconds * 3600;

const stop =
  state.done >= state.total              // 全做完
  || state.tasksLeft === 0               // 没任务了
  || state.elapsed > max_seconds         // 超时
  || perHour < min_marginal             // 不划算
  || objective.strategy === 'first_tier' && done >= tiers[0].at;
```

`valueOf(n)` = `n × unit_reward + Σ(tier.reward where n >= tier.at)`

**淘金币实算**（起始 3/20）：

| 进度 | valueOf | 边际 |
|---|---|---|
| 9/20 → 10/20 | 210 → 290 | **82.3 ¥/h** ← 跨档 |
| 19/20 → 20/20 | 560 → 690 | **133.7 ¥/h** ← 跨档 |
| 其他每步 | +30 金币 | 30.9 ¥/h |

阈值设 20 ¥/h，则**所有步都值得做**，会一路追到 20/20。
阈值设 35 ¥/h，则**只在跨档前做**，做完 10 档就停——但那不现实（差 1 个任务时不知道下一步跨不跨）。

结论：**用 `all_tiers` + 时间上限**，不用边际阈值筛选。边际阈值只用于"超目标后是否继续"。

## 4. 执行器伪代码（这是要写的东西）

```ts
async function runActivity(cfg) {
  const prep = await prep(cfg.prep);
  if (!prep.ok) return book(prep.status);

  await execSteps(cfg.entry);              // ② ENTRY
  let state = await probe(cfg.probes);      // ③ PROBE

  const t0 = Date.now();
  let plan = computePlan(state, cfg);       // ④ PLAN（本地）

  while (plan.shouldContinue) {             // ⑤ ACT
    if (Date.now() - t0 > cfg.objective.max_seconds * 1000) break;

    const before = state;
    await execUnit(cfg.task);               // 点一个任务 + dwell + back

    state = await probe(cfg.probes);        // 重新探测（1 次调用）
    if (state.tasksLeft === before.tasksLeft) break;  // 没进展，防止死循环

    if (crossedTier(before, state, cfg.value.tiers)) {
      await execSteps(cfg.collect.steps);   // ⑥ COLLECT
    }
    plan = computePlan(state, cfg);
  }

  await execSteps(cfg.collect.steps);       // 收尾再领一次
  const after = await readBalance(cfg.settle);   // ⑦ SETTLE
  return book(after, state);                // ⑧ BOOK
}
```

**三个防呆**：
- `tasksLeft` 没减少 → break（防重复点同一个任务）
- 总时长超限 → break（防跑飞）
- 步骤抛错 → 记 `ERROR`，但**已领到的收益仍然记账**（不能因为后段失败就丢掉前面的收益）

## 5. 扩展性：新增平台只写配置

| 平台/活动 | objective | probes | task.steps | collect |
|---|---|---|---|---|
| 淘金币 | all_tiers | progress(a/b) + tasks_left | 点任务→dwell→back | 立即领取 |
| 京东京豆 | first_tier | 是否已签到(boolean) | 点签到 | 无 |
| 芭芭农场 | fixed:N | 水滴数 | 点浇水 | 无 |
| 看视频签到 | fixed:N | 剩余视频数 | 播放→等跳过 | 无 |
| 长按领券 | all_tiers | 券数 | 长按→确认 | 无 |

**执行器代码完全不动。** 差异全在四个字段：`objective` / `probes` / `task` / `collect`。

## 6. 收益最大化怎么保证

四条：

1. **追档位不追次数**：`valueOf` 含档位奖励，跨档时边际 3~4 倍，自然会把任务做完
2. **不提前停**：`all_tiers` 策略下，只有"没任务了/超时/全做完"才停
3. **不白做**：`unit_reward` 与 `unit_seconds` 可随时改，改了立刻影响决策
4. **收益不丢**：后段失败也记账，已得的金币不会被回滚

## 7. 要新增的表（对应第 2 节配置）

| 表 | 字段 | 替代 |
|---|---|---|
| `objective` | `activity_id, strategy, max_seconds, min_marginal` | YAML 注释 |
| `value_model` | `activity_id, unit_reward, unit_seconds` | 无 |
| `tier` | `activity_id, at, reward` | 自然语言 |
| `probe` | `activity_id, probe_id, ask, parse` | flow 里的 read |
| `gain_event` | `run_id, source(task/tier/bonus), units` | 新增：记收益明细 |
| `cost_event` | `run_id, kind, tokens, ms` | run 里的扁平字段 |

`gain_event` 是补"收益构成"的关键：+120 能拆成 3×30 任务 + 30 档位。

## 8. 实施顺序（每步都能跑）

| 步 | 内容 | 验证方式 |
|---|---|---|
| 1 | 配置 schema 扩展（`objective/value/probes/task/collect`） | 配置能解析、旧配置兼容 |
| 2 | 引擎加 `probe` + `computePlan` + 新循环 | 干跑（不点屏幕）算出计划 |
| 3 | 接真实执行 | 跑一次淘金币，看是否追到 20/20 |
| 4 | `gain_event` 明细 + 面板展示 | +120 能拆成 90+30 |

**第 3 步就是你要的那次真实签到。**
