## 0. 一句话方案

**执行器先把手机「归位」到确定的起始状态 → 交给 Midscene 按多步指令签到（规划走缓存）→
结果与收益写入 SQLite → Nuxt 面板展示状态、收益、连续天数、漏签损失、缓存命中率。**

**为什么统一用 Node**

**为什么不用 Next.js**：Midscene 也能跑，但 Nitro 更轻，本地面板不需要 RSC / Edge。

## 2. 系统架构

### 2.1 进程模型（关键决策：执行器必须独立进程）

```
┌─────────────────────────────────────────────────────────────┐
│ 浏览器                                                       │
│   Nuxt 面板（今日 / 收益 / 连续 / 缓存健康 / 明细）             │
└───────────────────────┬─────────────────────────────────────┘
                        │ HTTP
┌───────────────────────▼─────────────────────────────────────┐
│ 进程 A：Nuxt（含 Nitro API）                                   │
│   职责：读 SQLite 出数据；写 = 只往 job 表插任务               │
│   绝不直接操作 adb、绝不跑 Midscene                             │
└───────────────────────┬─────────────────────────────────────┘
                        │ SQLite（WAL）
┌───────────────────────▼─────────────────────────────────────┐
│ 进程 B：执行器 runner                                         │
│   职责：轮询 job 表 → 前置准备 → Midscene 执行 → 记账          │
│   独占 adb；串行执行；崩溃不影响面板                            │
└───────────────────────┬─────────────────────────────────────┘
                        │ adb
┌───────────────────────▼─────────────────────────────────────┐
│ 手机（3d8a7934）                                              │
└─────────────────────────────────────────────────────────────┘
```

**为什么必须分进程**

| 理由 | 说明 |
|---|---|
| 长任务阻塞 | 一次签到 20~60 秒，放在 API 进程里会把面板卡死 |
| adb 独占 | 一台手机同一时刻只能被一个执行者操作，串行是硬约束 |
| 崩溃隔离 | 执行器被 App 异常拖死，面板照常能看历史 |
| 可观测 | 执行器日志与 Web 日志分离，排障清楚 |

### 2.2 数据流

```
config/accounts.yaml ─┐
config/activities.yaml ─┴→ 启动时 sync 进 SQLite（YAML 是唯一真源）
                                ↓
job 表 ←─ 面板「手动触发」/ cron 生成每日任务
   ↓
runner 取任务 → run 表（过程）→ reward 表（收益）→ cache_state（缓存健康）
   ↓
Nitro API 读表 → Nuxt 页面渲染
```

**YAML 与 DB 的分工**

| 内容 | 存哪 | 谁写 |
|---|---|---|
| 账号、活动定义（steps、汇率、时间窗） | `config/*.yaml` | 人改，git 管 |
| 执行记录、账本、缓存状态、任务队列 | SQLite | 机器写 |
| 截图、Midscene 报告 | `storage/` 文件 | 机器写 |

YAML 是真源，DB 里是镜像。**不做双向编辑**，避免同步地狱。面板不提供在线改配置。

## 3. 执行流程

### 3.1 每日调度

```
09:00  cron 触发
   ↓
生成 job：每个 enabled 活动一条，按 App 分组排序
   ↓  在时间窗内随机偏移（每活动 ±0~90 分钟）
runner 逐条消费
```

**按 App 分组**：同一 App 的多个活动连在一起跑，只启动一次 App，省冷启动。

### 3.2 前置准备（Prep）—— 这一层决定缓存能否命中

#### 为什么必须有这一层

Midscene 的缓存键是**指令文本（prompt）**，**不包含起始页面**。

`ai("从首页进入红包签到页面")` 的缓存计划，是在「当前处于首页」这个前提下录的。如果执行时手机停在别处（上一轮残留页面、弹窗、通知栏），计划会点错 → 失败 → 官方**清空该 prompt 的缓存 flow** → 下次又得重新规划。

**起始状态不稳定 = 缓存永远命中不了。** 这是整个方案的成败点。

#### 起始状态契约

每个活动声明前置条件：

```yaml
prep:
  package: com.taobao.taobao
  entry_text_any: [首页, 我的淘宝, 搜索]      # 判定「已在首页」的特征文本
  home_strategy: back_then_cold              # back 归位，失败才冷启动
  max_backs: 3
  cold_start_first_activity: true            # 每天该 App 第一个活动冷启动
  max_prep_sec: 45
  dismiss_keywords: [跳过, 关闭, 以后再说, 我知道了, 允许, 取消, 立即更新]
```

#### Prep 流水线（全部本地，0 模型调用）

| 阶段 | 动作 | 失败处理 |
|---|---|---|
| **P0 设备健康** | `adb devices` 有设备；`screenOn` 否则 `KEYCODE_WAKEUP`；`wm dismiss-keyguard` 解屏；电量 > 20% | 推送「设备离线/电量低」，标 `DEVICE_ERROR` |
| **P1 清干扰** | `cmd statusbar collapse` 收通知栏；检测系统弹窗（ANR、权限、更新）关键词 | 按 `dismiss_keywords` 点掉，≤5 轮 |
| **P2 启动 App** | 前台包名 == 目标？跳过。否则 `am start`，记 `cold_start` | 失败重试 2 次 → `LAUNCH_FAILED` |
| **P3 等待就绪** | 轮询 `entry_text_any` 命中，超时 20s | 超时进 P4 |
| **P4 归位** | 循环：清弹窗 → 检查 `entry_text` → 不行就 `back`（≤ `max_backs` 次） | 仍不行 → `am force-stop` + `am start` 冷启动 |
| **P5 起始断言** | `entry_text_any` 命中 → **ready**，交给 Midscene | 不命中 → `NEEDS_HUMAN` + 截图 |

**P3~P5 全部用 adb 读屏本地判断**（`uiautomator dump` 取文本），不消耗模型。

#### 「杀端还是归位」的结论

| 策略 | 冷启动耗时 | 副作用 | 结论 |
|---|---|---|---|
| 每次都 `force-stop` + 冷启动 | 5~9s × 活动数 | 每次触发首屏广告、更新弹窗、可能的登录校验，反而要更多清理 | ❌ |
| 直接跑，不干预 | 0 | 起始页不确定，缓存计划必然失效，反复清缓存 | ❌ |
| **back 归位，失败才冷启动** | 通常 1~2s | 起始页确定（首页），缓存可命中 | ✅ **默认** |
| **每 App 每天首个活动冷启动一次** | 每天 8 次 | 状态最干净；同 App 后续活动复用进程 | ✅ **配合使用** |

组合策略：**每天每个 App 第一次冷启动（拿干净起点），同 App 后续活动靠 back 归位复用进程。**

### 3.3 Midscene 执行

```ts
const agent = await agentFromAdbDevice(DEVICE_ID, {
  cache: { strategy: 'read-only', id: cacheId },
})

for (const step of activity.steps) {
  await agent.ai(step.ai)          // 规划走缓存，定位调模型
}
const verified = await agent.aiAssert(activity.verifyAny.join(' 或 '))  // 不缓存
const balance  = await agent.aiQuery(activity.balanceQuery)             // 不缓存
await agent.flushCache()                                                  // 成功后写回
```

### 3.4 验证与记账

```
验证：aiAssert 命中 verify_any → OK；不命中 → NO_EFFECT
读数：aiQuery 拿余额 → 与本次执行前记录比对，差值即实际收益
落账：run 表一条 + reward 表一条（三口径 + expires_at）
备份：成功后 cp cache/<id>.cache.yaml → .bak.yaml
```

**为什么用余额差而不是预期值**：活动经常「缩水」发奖，按 `expected_amount` 记账会虚高。余额差是唯一可信来源。读不到余额的活动才回退预期值，并在账本标 `amount_source: expected`。

### 3.5 收尾

```
back 到首页（不杀端，留给下一个活动）
记录 prep_ms / exec_ms / cold_start / cache_hit
随机 sleep 2~8s 再处理下一个
```

## 4. Midscene 缓存机制

### 4.1 两类缓存

| 缓存类型 | 缓存键 | 缓存内容 | Web | Android |
|---|---|---|---|---|
| **任务指令缓存** | 规划 prompt（`ai` / `aiAct`） | 执行计划（步骤序列） | ✅ | **✅ 生效** |
| **元素定位缓存** | 定位 prompt（`aiLocate` / `aiTap`） | 元素 XPath | ✅ | ❌ **仅 Web** |

结论：**Android 上缓存「先做什么」，不缓存「按钮在哪」。**
官方实测：同一任务 51 秒 → 28 秒（省 45%）。

### 4.2 我们怎么用它

| 手段 | 作用 |
|---|---|
| 指令拆成 3~5 步 | 每条独立缓存，定位次数 = 步骤数，可测 |
| 起始状态契约（3.2 节） | 保证缓存计划的前提成立，不被反复清空 |
| `read-only` + 成功才 `flushCache` | 失败路径不污染缓存 |
| 缓存文件备份 | 污染后可回滚 |
| `cache_id` 按账号隔离 | A 账号路径不会套到 B 账号 |

### 4.3 失效与回退

| 情况 | 官方行为 | 我们的对策 |
|---|---|---|
| 缓存规划运行时失败 | 本次回退 AI 重新规划，并**清空**该 prompt 的 flow | 计 `fails`；连 3 次重建 |
| 回退后规划成功 | **不回写**缓存 | 统一在验证通过后 `flushCache` |
| `aiAssert` / `aiQuery` / `aiBoolean` | **永不缓存** | 每活动各调 1 次，可接受 |

### 4.4 改版检测与自动重建（不靠"防改版"）

**淘宝的改版不走应用商店**：首页模块、活动页、签到入口都是服务端下发（mtop 动态配置 + 小程序化页面），热更新即可生效。所以「关闭自动更新」这类防御**无效**，不要写进方案。

正确的形态是：**不防变化，做「快检测 + 便宜重建」**。

| 环节 | 做法 |
|---|---|
| **检测** | 每次跑记录 `cache_hit` / `exec_ms` / `status`；用 7 日滑动平均看拐点。命中率跌破 60% 或耗时涨幅 > 50% → 判定改版 |
| **重建** | 清该活动缓存，以 `write-only` 策略跑一次全量规划 |
| **验证** | 重建后立刻 `read-only` 再跑一次，验证词命中才算成功 |
| **降级** | 重建 2 次仍失败 → 标 `NOT_FOUND`，推送人工，停跑该活动 |
| **成本** | 一次重建 ≈ 一次全量规划，走订阅通道边际成本 ¥0 → **重建不心疼，可以随时做** |

**这是方案能长期跑下去的关键**：不是假设活动不变，而是假设它每周都会变，并把「变了就自动重来」做成常态路径。

## 5. 数据存储（SQLite）

### 5.1 为什么从 JSONL 换成 SQLite

| 需求 | JSONL | SQLite |
|---|---|---|
| 按天/账号/活动聚合 | 全量扫描 + 内存聚合 | 索引，毫秒级 |
| 连续签到天数 | 读全部历史 | SQL 一次算 |
| 漏签检测（应有 vs 实有） | 生成日期序列求差 | SQL 一次算 |
| 一次执行写多条 | 可能半截写入 | 事务保证 |
| 趋势图（30/90 天） | 反复扫描 | 索引查询 |
| 备份 | cp 文件 | `VACUUM INTO` 单文件快照 |

一年约 3000 条 run、3000 条 reward，量不大，但**查询是聚合型**的，SQLite 更合适。

### 5.2 Schema

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;

-- 账号（由 accounts.yaml 同步）
CREATE TABLE account (
  id          TEXT PRIMARY KEY,
  app         TEXT NOT NULL,
  package     TEXT NOT NULL,
  user_id     INTEGER NOT NULL DEFAULT 0,
  cache_id    TEXT NOT NULL,
  enabled     INTEGER NOT NULL DEFAULT 1,
  note        TEXT,
  UNIQUE(package, user_id)          -- 双开靠 user_id 区分
);

-- 活动（由 activities.yaml 同步）
CREATE TABLE activity (
  id              TEXT PRIMARY KEY,
  account_id      TEXT NOT NULL REFERENCES account(id),
  name            TEXT NOT NULL,
  steps_json      TEXT NOT NULL,     -- ["打开淘宝 App","进入红包签到页面",...]
  task_fallback   TEXT,              -- 一句话指令，steps 全失败时降级
  verify_any      TEXT NOT NULL,     -- 逗号分隔
  balance_query   TEXT,
  entry_text_any  TEXT,              -- Prep 归位判据
  window_start    TEXT,              -- "09:00"
  window_end      TEXT,              -- "13:00"
  unit            TEXT,
  expected_amount REAL,
  cny_per_unit    REAL NOT NULL,
  expires_days    INTEGER,
  forbidden       TEXT,              -- 逗号分隔黑名单
  enabled         INTEGER DEFAULT 1,
  state           TEXT DEFAULT 'pending'   -- active | pending | dead
);

-- 每次执行
CREATE TABLE run (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  ts            TEXT NOT NULL,       -- ISO8601
  day           TEXT NOT NULL,       -- YYYY-MM-DD
  account_id    TEXT NOT NULL,
  activity_id   TEXT NOT NULL,
  status        TEXT NOT NULL,       -- OK|ALREADY|NO_EFFECT|NOT_FOUND|NEEDS_LOGIN
                                     -- |NEEDS_HUMAN|FORBIDDEN_HIT|LAUNCH_FAILED
                                     -- |DEVICE_ERROR|DEAD
  cache_hit     INTEGER,             -- 0/1
  cold_start    INTEGER DEFAULT 0,
  prep_ms       INTEGER,
  exec_ms       INTEGER,
  error         TEXT,
  evidence_dir  TEXT,
  prompt_ver    TEXT                 -- 指令版本，改指令时递增
);
CREATE INDEX idx_run_day  ON run(day);
CREATE INDEX idx_run_act  ON run(activity_id, day);
CREATE INDEX idx_run_stat ON run(status, day);

-- 收益（一次 run 可有多种币种）
CREATE TABLE reward (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  run_id         INTEGER REFERENCES run(id) ON DELETE CASCADE,
  day            TEXT NOT NULL,
  account_id     TEXT NOT NULL,
  activity_id    TEXT NOT NULL,
  unit           TEXT,
  amount         REAL,
  amount_source  TEXT,               -- balance_diff | expected | manual
  face_value_cny REAL,
  usable_cny     REAL,
  cash_cny       REAL,
  expires_at     TEXT,
  balance_before REAL,
  balance_after  REAL,
  created_at     TEXT
);
CREATE INDEX idx_reward_day ON reward(day);
CREATE INDEX idx_reward_act ON reward(activity_id, day);

-- 缓存健康
CREATE TABLE cache_state (
  account_id      TEXT NOT NULL,
  activity_id     TEXT NOT NULL,
  cache_file      TEXT,
  updated_at      TEXT,
  hits            INTEGER DEFAULT 0,
  fails           INTEGER DEFAULT 0,
  rebuild_count   INTEGER DEFAULT 0,
  last_rebuild_at TEXT,
  PRIMARY KEY (account_id, activity_id)
);

-- 任务队列（面板与 cron 只入队，runner 消费）
CREATE TABLE job (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  kind         TEXT NOT NULL,       -- daily|signin|cache_rebuild|probe
  account_id   TEXT,
  activity_id  TEXT,
  status       TEXT DEFAULT 'queued',  -- queued|running|done|failed|cancelled
  attempt      INTEGER DEFAULT 0,
  max_attempt  INTEGER DEFAULT 2,
  payload      TEXT,
  error        TEXT,
  created_at   TEXT,
  started_at   TEXT,
  finished_at  TEXT
);
CREATE INDEX idx_job_status ON job(status, id);
```

### 5.3 关键查询（面板直接用）

```sql
-- 今日概览
SELECT status, COUNT(*) n FROM run WHERE day = :today GROUP BY status;

-- 今日账面收益
SELECT SUM(face_value_cny) total FROM reward WHERE day = :today;

-- 连续签到天数（当前）
WITH ok_days AS (
  SELECT DISTINCT day FROM run
  WHERE activity_id = :aid AND status IN ('OK','ALREADY')
),
break_day AS (
  SELECT COALESCE(MAX(day),'1970-01-01') d FROM run
  WHERE activity_id = :aid AND status NOT IN ('OK','ALREADY','DEAD')
)
SELECT COUNT(*) FROM ok_days, break_day WHERE ok_days.day > break_day.d;

-- 缓存命中率（近 14 天）
SELECT day, ROUND(AVG(cache_hit),3) rate FROM run
WHERE day >= date('now','-14 day') AND status IN ('OK','ALREADY','NO_EFFECT')
GROUP BY day ORDER BY day;

-- 即将过期
SELECT * FROM reward
WHERE expires_at BETWEEN :today AND date(:today,'+30 day')
ORDER BY expires_at;
```

## 9. 成本

| 环节 | 单次调用 | 说明 |
|---|---|---|
| 规划（每步一条） | **0**（缓存命中） | 缓存失效时才调 |
| 元素定位（每步 1 次） | N | Android 不缓存定位 |
| `aiAssert` 验证 | 1 | 不缓存 |
| `aiQuery` 读余额 | 1 | 不缓存 |

按每活动 3 步：约 5 次调用。

**用实测值算**（每次定位输入约 4.6K tokens，见 1.1 节）：

| 项 | 计算 | tokens/年 |
|---|---|---|
| 8 活动 × 365 天 × 5 次 × 4.6K | 定位 + 验证 + 读数 | ≈ 67M |
| 首次建缓存（含规划） | 8 活动 | ≈ 2M |
| 改版重建（30 次/年） | — | ≈ 3M |
| **合计** | | **≈ 72M tokens / 年** |

**但实际是 ¥0** —— `codex/gpt-6.1-sol` 走 ChatGPT 订阅，配额内不按 token 计费。上面 72M 只是「如果换成按量计费 API 要花多少」的参考值（¥72 ~ ¥288/年），用于评估 fallback 方案的代价。

**这套方案的边际成本结构**

| 通道 | 边际成本 |
|---|---|
| codex（订阅） | **¥0**，只消耗配额 |
| 豆包 / GLM API（fallback） | ¥72 ~ ¥288 / 年 |

所以策略是：**日常走订阅，订阅配额告急时切 API**。



`prep` 全程 adb 本地判断，**不产生模型调用**，这是省下大部分成本的地方。

## 10. 失败处理矩阵

| 现象 | 检测层 | 处理 |
|---|---|---|
| 手机未连接 | P0 | `DEVICE_ERROR`，推送 |
| 屏幕黑着 | P0 | `KEYCODE_WAKEUP` |
| 通知栏遮挡 | P1 | `cmd statusbar collapse` |
| 系统弹窗（ANR/权限/更新） | P1/P4 | 按 `dismiss_keywords` 点掉，≤5 轮 |
| App 没起来 | P2 | 重试 2 次 → `LAUNCH_FAILED` |
| 起始页不对 | P4 | `back` ×3 → 冷启动 → 仍不对则 `NEEDS_HUMAN` |
| 掉登录 | P4 文本检测 | `NEEDS_LOGIN`，推送，不重试 |
| **被挤下线**（信息流在 + 下线通知框） | P4 模态框检测 | `NEEDS_LOGIN`；**必须先识别**，否则后续点击全落弹窗、误报成功 |
| 滑块验证码 | P4 | `NEEDS_HUMAN`，不硬过（硬过加重风控） |
| 命中「翻倍」黑名单 | 执行中 | `FORBIDDEN_HIT`，中断 |
| 执行完无变化 | 验证 | `NO_EFFECT`，重试 1 次；累计 3 次重建缓存 |
| 缓存 plan 失效 | Midscene 自动回退 | 记回退；本次不写缓存 |
| 活动结束 | 连续 3 天 `NOT_FOUND` | 标 `DEAD` 停跑 |

**误报比失败更危险** —— 失败会重试，误报没人管。

| 风险 | 影响 | 对策 |
|---|---|---|
| 起始状态不稳 | 缓存反复失效，退化成每次全量规划 | Prep 五阶段 + 起始断言；命中率告警 |

| 活动频繁改版 | 需重建缓存 | 命中率告警；重建是常态 |
| 手机长期插电 | 电池鼓包 | 充电上限 80%、通风处 |

| 合规 | 违反用户协议 | 仅自用；不对外提供服务 |

## 附：Midscene 缓存官方原文

> Midscene 支持缓存两类内容：AI 规划的步骤，以及匹配到的元素定位信息。前者可用于各类自动化任务，以减少 AI 模型调用次数并提升执行效率；后者中的 DOM 元素定位信息（XPath）在 Web 自动化任务中可显著减少重复定位开销，不过目前仅适用于 Web 场景。

> **任务指令缓存**：对于规划类操作（如 `ai`、`aiAct`），Midscene 会将 prompt 指令作为缓存键，存储 AI 返回的执行计划
> **元素定位缓存（仅 Web）**：对于定位类操作（如 `aiLocate`、`aiTap`），系统会将定位 prompt 作为缓存键，存储元素的 XPath 信息
> **失效机制**：当缓存失效时，系统会自动回退到 AI 模型重新分析
> **永不缓存查询结果**：查询类操作（如 `aiBoolean`、`aiQuery`、`aiAssert`）不会被缓存

> 当缓存命中时，脚本的执行时间会显著降低。例如在如下案例中，执行耗时从 51 秒降低到了 28 秒。
