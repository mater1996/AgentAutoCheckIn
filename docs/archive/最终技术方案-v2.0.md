## 0. 一句话方案

**用 Midscene 以自然语言操作手机完成签到；开启官方缓存，让「路径」从第二次起直接复用。
收益按「积分 → 人民币」逐笔记账，Web 面板看状态、收益、连续天数、漏签损失。**

## 1. 为什么是 Midscene

### 1.1 决策依据

| 维度 | 说明 |
|---|---|
| **路径可复用** | 官方内置缓存：`prompt → 执行计划`，第二次起不再重新规划 |
| **抗改版** | 靠看截图定位，按钮挪位置 / 改样式 / 换图片都能点 |
| **输出结构化** | 执行报告含每步动作、坐标、截图、耗时；`aiQuery` 能直接读出界面数值 |
| **接得上记账** | 报告 + `aiQuery` 输出即账本数据源 |
| 可维护 | MIT，15.4k★，2026-10 仍在更新 |

### 1.2 为什么不选其他

| 候选 | 放弃原因 |
|---|---|
| 肉包 Roubao（2.4k★）/ ApkClaw（800★）/ Andclaw（514★） | 手机 App 形态，面向人对话，拿不到结构化中间数据，接不上记账 |
| Open-AutoGLM（26.5k★）/ AutoGLM-GUI | 依赖「限时免费」模型，不可持续 |

| 纯 uiautomator2 脚本 | 淘宝自绘界面 selector 匹配不到，改版即失效 |

## 2. Midscene 缓存机制（方案的核心）

这一节是整个方案能长期跑下去的基础，先说透。

### 2.1 官方支持两类缓存，效果不同

| 缓存类型 | 缓存键 | 缓存内容 | Web | Android |
|---|---|---|---|---|
| **任务指令缓存** | 规划类 prompt（`ai` / `aiAct`） | AI 返回的执行计划（步骤序列） | ✅ | **✅ 生效** |
| **元素定位缓存** | 定位类 prompt（`aiLocate` / `aiTap`） | 元素 XPath | ✅ | ❌ **不生效（仅 Web）** |

**结论：Android 上能缓存「先做什么」，不能缓存「按钮在哪」。**

官方实测效果：同一任务执行耗时 **51 秒 → 28 秒**（省 45%）。省掉的正是规划调用，定位调用仍在。

### 2.2 这对我们意味着什么

用 `ai("打开淘宝完成红包签到")` 这种一句话指令，第二次起：
- ✅ 不再调用模型「思考下一步做什么」
- ✅ 直接按缓存计划执行
- ⚠️ 但每个要点的元素，仍要模型定位一次

**所以流程要拆成多步指令**：每条指令独立命中自己的规划缓存，定位次数 = 步骤数，可测、可优化。

### 2.3 缓存策略与文件

| 策略 | 配置 | 适用 |
|---|---|---|
| 禁用 | `cache: false`（默认） | 调试 |
| 读写 | `cache: { id: "taobao" }` | 开发期 |
| **只读 + 手动写** | `cache: { strategy: "read-only", id: "taobao" }` + `agent.flushCache()` | **生产环境（我们采用）** |
| 只写 | `cache: { strategy: "write-only", id: "taobao" }` | 首次建缓存 / 重建 |

- 缓存文件：`./midscene_run/cache/<id>.cache.yaml`
- 清理：`agent.flushCache({ cleanUnused: true })`

**选 `read-only` 的理由**：只在任务成功时写缓存。`read-write` 会把中途失败的状态也写进去，容易把半截路径当成完整路径存下来。

### 2.4 失效与回退（必须知道的坑）

| 情况 | 官方行为 | 我们的对策 |
|---|---|---|
| 缓存规划运行时失败（比如本次没弹窗） | 本次回退到 AI 重新规划，并**清空**该 prompt 的缓存 flow | 失败计 `fails`；连续 3 次重建缓存 |
| 回退后规划成功 | **不回写**缓存（页面状态已变，flow 不可复用） | 任务结束统一 `flushCache` 前先过验证词 |
| 查询类操作 | **永不缓存**（`aiAssert` / `aiQuery` / `aiBoolean`） | 用于验证签到、读余额，必然调模型，一次即够 |

### 2.5 我们的缓存分层

```
第一层：Midscene 规划缓存（官方）
  prompt → 执行计划，跨天复用，省掉规划调用
        ↓ 定位仍在调模型
第二层：指令拆分
  长流程拆成 3~5 条短指令，各命中独立缓存，定位次数可控可测
        ↓ 若定位开销仍不可接受（P2 可选优化）
第三层：坐标导出
  解析执行报告里的 Locate center，生成预置坐标脚本
  注意：识图来源仍是 Midscene，只是把结果落成坐标
```

P0 只做第一 + 第二层。第三层等实测数据说话。

## 4. 数据模型

### 4.1 `accounts/accounts.yaml`

```yaml
accounts:
  - id: tb_main
    app: taobao
    package: com.taobao.taobao
    user_id: 0            # 0=主空间 / 999=应用双开
    cache_id: tb_main     # Midscene 缓存标识，一账号一缓存
    enabled: true

  - id: tb_dual
    app: taobao
    package: com.taobao.taobao
    user_id: 999
    cache_id: tb_dual
    enabled: false
```

| 字段 | 说明 |
|---|---|
| `id` | 全局唯一，账本主键 |
| `package` | Android 包名（主空间与双开**相同**） |
| `user_id` | **双开实例的唯一区分依据**：0 主空间 / 999 双开 |
| `cache_id` | **必须按账号隔离**。两个账号共用缓存会把 A 的路径套到 B 上 |

**双开启动**（已实测）：`adb shell am start --user 999 -n <pkg>/<Activity>`
启动后前台为 `u999`，`am get-current-user` 仍为 0，仍可正常读屏和点击。

### 4.2 `activities/<app>.yaml`

```yaml
app: taobao
account: tb_main
activities:
  - id: tb_redpacket
    name: 红包签到
    task: 打开淘宝，进入红包签到页面并完成签到      # 一句话指令（降级用）
    steps:                                  # 多步指令，各命中独立缓存
      - ai: 打开淘宝 App
      - ai: 从首页进入「红包签到」页面
      - ai: 点击领取今天签到奖励
    verify_any: [已签到, 签到成功, 明日再来]
    balance_query: 当前红包余额是多少元      # aiQuery，不缓存
    window: "09:00-13:00"
    reward:
      unit: 红包
      amount: 0.5
      cny_per_unit: 1.0
    forbidden: [翻倍, 立即翻倍]
    enabled: true
    state: pending            # active | pending | dead

  - id: tb_coin
    name: 淘金币签到
    task: 打开淘宝，进入领淘金币页面领取今天的淘金币
    steps:
      - ai: 打开淘宝 App
      - ai: 进入「领淘金币」页面
      - ai: 领取每日淘金币
    verify_any: [已签到, 领取成功]
    balance_query: 当前有多少淘金币
    window: "09:00-21:00"
    reward:
      unit: 淘金币
      amount: 50
      cny_per_unit: 0.01      # 100 淘金币 = ¥1
    enabled: true
    state: pending
```

| 字段 | 作用 |
|---|---|
| `task` | 一句话指令，`steps` 全失败时降级使用 |
| `steps` | 多步指令，**每条独立命中缓存** |
| `verify_any` | 成功判定词 |
| `balance_query` | 读余额的自然语言问句（`aiQuery`） |
| `window` | 允许执行时段，实际在窗口内随机偏移 |
| `cny_per_unit` | **积分→人民币唯一折算入口** |
| `forbidden` | 黑名单，出现即中断（淘宝「翻倍」后红包限指定专区，实际价值缩水） |
| `state` | `active` 正常 / `pending` 待验证 / `dead` 活动结束 |

### 4.3 缓存文件 `cache/<cache_id>.cache.yaml`

由 Midscene 生成，不手改，但要纳管：

```
cache/tb_main.cache.yaml        ← Midscene 输出，git 跟踪
cache/tb_main.cache.bak.yaml    ← 每次成功签到后备份
```

**为什么要备份**：缓存被失败路径污染后（官方会清空该 prompt 的 flow），能从上次好的状态恢复，不必从零重学。

### 4.4 账本 `ledger/YYYY-MM-DD.jsonl`

```json
{"ts":"2026-10-30T09:12:03","account":"tb_main","activity":"tb_redpacket",
 "status":"OK","cache_hit":true,"ms":28400,
 "reward":{"unit":"红包","amount":0.5},
 "face_value_cny":0.5,"usable_cny":0.5,"cash_cny":0.0,
 "expires_at":"2026-11-14",
 "balance_before":12.3,"balance_after":12.8,
 "evidence":"evidence/2026-10-30-tb_main-tb_redpacket/"}
```

`cache_hit` 必须记 —— 它是判断缓存是否真生效的唯一依据。**面板要看这个趋势**：命中率掉了说明路径在漂移。

**三个金额分开**

| 字段 | 含义 | 说明 |
|---|---|---|
| `face_value_cny` | 账面价值 | 按官方汇率折算 |
| `usable_cny` | 可用价值 | 受抵扣上限约束（京豆单笔最高抵 50%） |
| `cash_cny` | 真现金 | 签到基本为 0 |

签到收益几乎全是账面价值、不可提现。混成一个数会自欺。

### 4.5 状态机

| status | 含义 | 计收益 | 后续 |
|---|---|---|---|
| `OK` | 成功 + 验证通过 | ✅ | 备份缓存 |
| `ALREADY` | 今日已签 | ❌ | 结束 |
| `NO_EFFECT` | 执行完但界面无变化 | ❌ | 累计 3 次 → 重建缓存 |
| `NOT_FOUND` | 找不到入口 | ❌ | 重建缓存 |
| `NEEDS_LOGIN` | 掉登录 / 被挤下线 | ❌ | 推送，不重试 |
| `NEEDS_HUMAN` | 滑块/验证码 | ❌ | 推送截图 |
| `FORBIDDEN_HIT` | 命中黑名单 | ❌ | 中断报错 |
| `DEAD` | 活动结束 | ❌ | 自动停跑 |

## 5. 每日运行流程

```
cron 触发（Hermes cron 或 launchd）
│
├─ 0. 环境自检：adb 连接 / 唤醒 / 免锁屏 / 电量
│     失败 → 推送「设备离线」
│
├─ 1. 登录体检（本地，0 调用）
│     Activity 名含 Login → NEEDS_LOGIN
│     出现「账号下线通知」→ NEEDS_LOGIN
│     → 汇总一次推送
│
├─ 2. 串行执行每个活动（一台机同时只能操作一个 App）
│     ├─ 建 Agent：cache = { strategy: 'read-only', id: cache_id }
│     ├─ 按 steps 逐步执行
│     ├─ verify：aiAssert 验证词（不缓存，必调一次）
│     ├─ read：aiQuery 读余额（不缓存，必调一次）
│     ├─ 成功 → flushCache() 写回 + 备份缓存文件
│     └─ 失败 → 记状态，不写缓存（避免污染）
│
├─ 3. 汇总：成功 X / 已签 Y / 失败 Z / 需登录 W / 今日账面 ¥N / 缓存命中率
│     → 飞书一条消息
│
└─ 4. 落盘：ledger + evidence（Midscene 报告 + 截图）
```

**时间窗随机化**：避开签到入口的时段限制；避免「所有 App 同一分钟集中点击」的机器特征。

## 6. 成本模型

### 6.1 单次执行（缓存命中后）

| 环节 | 模型调用 |
|---|---|
| 规划（每步一条指令） | **0（缓存命中）** |
| 元素定位（每步 1 次） | N 次 |
| 验证 `aiAssert` | 1 次（不缓存） |
| 读余额 `aiQuery` | 1 次（不缓存） |

按每活动 3 步计算：约 5 次调用 / 活动。

### 6.2 年度成本

| 项 | 计算 | 年成本 |
|---|---|---|
| 8 活动 × 365 天 × 5 次调用 × 约 1.3K tokens | ≈ 19M tokens | **¥19 ~ ¥76** |
| 首次建缓存（8 活动，含规划） | ≈ 1M tokens | ¥1 ~ ¥4 |
| 改版重建（假设 30 次/年） | ≈ 3M tokens | ¥3 ~ ¥12 |
| **合计** | | **≈ ¥23 ~ ¥92 / 年** |

按 ¥1~4/百万 tokens 估算（DeepSeek / 豆包 / GLM 区间）。**每月几块钱**，可以接受。

不需要本地模型，也不需要自建脚本引擎。

### 6.3 想再降成本的路（可选，P2）

| 手段 | 效果 | 代价 |
|---|---|---|
| 减少 steps 数 | 线性降定位次数 | 单步做的事变多，失败影响面变大 |
| 报告坐标导出成预置脚本 | 定位降到 0 | 要维护导出逻辑；路径漂移需重建 |
| `screenshotShrinkFactor` 调小 | 每张图 token 变少 | 太小会定位不准 |

先用 P0 实测数据说话，再决定动不动。

## 7. 失败处理矩阵

| 现象 | 检测 | 处理 |
|---|---|---|
| 屏幕黑着 | `screenOn == False` | `KEYCODE_WAKEUP` + `svc power stayon true` |
| App 没起来 | 连续两次前台包名 ≠ 目标 | 重启 App，最多 3 次 |
| 掉登录 | Activity 含 `Login` / 「验证码登录」 | `NEEDS_LOGIN`，推送，不重试 |
| **被挤下线** | 信息流在 + 「账号下线通知」模态框 | `NEEDS_LOGIN`；**必须先识别**，否则后续点击全落弹窗、会误报成功 |
| 滑块验证码 | 「请拖动滑块」 | `NEEDS_HUMAN`，不硬过（硬过加重风控） |
| 命中「翻倍」 | 黑名单词出现 | `FORBIDDEN_HIT`，中断 |
| 点了没反应 | 前后界面无变化 | `NO_EFFECT`，重试 1 次；累计 3 次重建缓存 |
| 缓存 plan 失效 | Midscene 自动回退重新规划 | 记回退次数；本次不写缓存 |
| 活动结束 | 连续 3 天 `NOT_FOUND` | 标 `DEAD` 停跑 |

**误报比失败更危险** —— 失败会重试，误报没人管。所以每步必须验证。

## 8. Web 面板

Mac 本地，读 `ledger/` `accounts/` `activities/` `cache/`，不写业务数据。
单进程（FastAPI 或 Node）+ 静态前端，`localhost:8080`，局域网可访问。

### ① 今日

| 区块 | 内容 |
|---|---|
| 概览卡 | 成功 / 已签 / 失败 / 需处理 / 今日账面 ¥ / **缓存命中率** |
| 活动列表 | 账号 · 活动 · 状态 · 耗时 · 账面价值 · 截图缩略图 |
| 待处理 | `NEEDS_LOGIN` / `NEEDS_HUMAN`，点开看全屏截图 |

### ② 收益

| 区块 | 内容 |
|---|---|
| 累计 | 账面 / 可用 / 现金（三个分开，标注「账面不可提现」） |
| 趋势 | 日 / 周 / 月折线 |
| 分账号 | 各账号贡献占比 |
| 分币种 | 淘金币 / 京豆 / 红包，数量 + 折算 |

### ③ 连续与漏签

| 区块 | 内容 |
|---|---|
| 连续天数 | 每活动当前连续 / 历史最长 |
| 漏签 | 最近 30 天漏签日期 |
| **漏签损失** | `amount × cny_per_unit` 估算「少赚多少」 |
| **即将过期** | 按 `expires_at` 排序，30 天内到期 |

淘金币宝箱有容量上限（满了不累积）、京豆 2026 新规有效期最长 180 天（过期作废）——这两项让「漏签损失」「即将过期」成为必需指标，不是可选项。

### ④ 缓存健康度

| 功能 | 说明 |
|---|---|
| 缓存命中率趋势 | 掉下来说明路径在漂移 |
| 每活动缓存更新时间 | 上次重建时间 |
| 手动重建缓存 | 清缓存后以 `write-only` 跑一次 |
| 手动触发 | 单活动立即跑一次（调试用） |
| 手动补录 | 输入今日实际收益（有些 App 读不到余额） |

| 阶段 | 交付 | 验收标准 |
|---|---|---|
| **P0 打通** | 装 Midscene + 跑通淘宝红包签到 + 开缓存 + 记账 + 面板显示 | **连跑两次**：第二次明显更快、报告里规划调用消失；连续 3 天自动签到成功 |
| **P1 稳健** | 失败矩阵 + 缓存备份/重建 + 飞书推送 | 清空缓存后能自动重建；掉登录 / 滑块 / 黑名单都正确报状态 |
| **P2 扩展** | 淘金币 + 京东 + 美团；多账号双开 | 5~8 活动稳跑一周，误报率 0 |
| **P3 面板** | 收益趋势、连续天数、漏签损失、缓存命中率 | 数据与 `ledger/` 对得上 |

**P0 的验收重点是「连跑两次」** —— 它是验证「路径缓存真生效」的唯一硬证据。
如果第二次没变快，说明缓存在 Android 上没按预期工作，要立刻调整（改多步指令 / 换模型 / 上坐标导出），而不是继续往上堆功能。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 缓存被污染 | 路径错乱，越跑越差 | `read-only` + 成功后 `flushCache` + 每次备份 |
| 定位开销高于预期 | 成本上升 | 减少 steps；或上坐标导出 |
| 平台风控升级 | 点击无效 / 奖励缩水 | 时间窗随机化、每日一次、不硬过滑块、控制活动数 5~8 个 |
| 账号被封 | 收益归零 | 优先小号 / 双开号 |
| 活动频繁改版 | 需重建缓存 | 命中率告警；重建是常态，接受它 |
| 手机长期插电 | 电池鼓包 | 充电上限 80%、通风处 |
| 手机离线 | 当日全失败 | 环境自检 + 离线告警 |
| 合规 | 违反用户协议 | 仅自用；不对外提供服务 |

## 附：Midscene 官方原文摘录（缓存）

> Midscene 支持缓存两类内容：AI 规划的步骤，以及匹配到的元素定位信息。前者可用于各类自动化任务，以减少 AI 模型调用次数并提升执行效率；后者中的 DOM 元素定位信息（XPath）在 Web 自动化任务中可显著减少重复定位开销，不过目前仅适用于 Web 场景。

> **任务指令缓存**：对于规划类操作（如 `ai`、`aiAct`），Midscene 会将 prompt 指令作为缓存键，存储 AI 返回的执行计划
> **元素定位缓存（仅 Web）**：对于定位类操作（如 `aiLocate`、`aiTap`），系统会将定位 prompt 作为缓存键，存储元素的 XPath 信息
> **失效机制**：当缓存失效时，系统会自动回退到 AI 模型重新分析
> **永不缓存查询结果**：查询类操作（如 `aiBoolean`、`aiQuery`、`aiAssert`）不会被缓存

> 当缓存命中时，脚本的执行时间会显著降低。例如在如下案例中，执行耗时从 51 秒降低到了 28 秒。
