# 任务标准流程 v2（收集 → 决策 → 执行）

替代 v1 的「八段单循环」。核心变化：**把"做多少、做什么"从执行过程里拿出来，变成先产出、可审阅的计划。**

---

## 1. 事实基线（2026-10-30 实测）

### 1.1 淘金币任务页的真实结构

**8 个任务，配额合计 20 次。20 是档位门槛，不是任务数量。**

| # | 任务名 | 配额 | 类型 | 固化可行性 |
|---|---|---|---|---|
| 1 | 看看你关注店铺的优惠 | 0/1 | 浏览店铺 | ✅ 点开 → 停 12s → 返回 |
| 2 | 你关注的商品都可抵 | 0/1 | 浏览商品 | ✅ 同上 |
| 3 | 看看#夜胶原 | 0/5 | 浏览话题 | ✅ 同上，重复 5 次 |
| 4 | 拍立淘逛感兴趣的宝贝 | 0/5 | 拍照搜图 | ⚠️ 需相机权限 |
| 5 | 去蚂蚁庄园逛逛哟 | 0/1 | 跳小程序 | ✅ 点开 → 停 15s → 返回 |
| 6 | 去蚂蚁森林收能量 | 0/1 | 跳小程序 | ✅ 同上 |
| 7 | 去支付宝农场逛逛哟 | 0/1 | 跨 App（支付宝） | ⚠️ 会离开淘宝 |
| 8 | 搜一搜你心仪的宝贝 | 0/5 | 搜索 | ✅ 点搜索框 → 输入 → 点搜索 → 返回 |

### 1.2 档位

| 进度门槛 | 奖励 | 说明 |
|---|---|---|
| 3 | 30 金币 | 通常已完成 |
| 10 | 50 金币 | 需完成 10 次 |
| 20 | 100 金币 | 需完成 20 次（全部配额） |

### 1.3 可行性算账

```
总配额 20
− 拍立淘 5（需相机）
− 支付宝农场 1（跨 App）
= 可达 14/20
```

**14 < 20 → 100 金币档拿不到，损失 ¥1.00。**

这是"哪些该做"必须前置计算的原因：少做 6 次不只是少 6 次任务钱，而是**丢掉整档奖励**。

### 1.4 页面特性

- 淘金币相关页面**全部 Canvas 渲染**，无障碍树 0 节点 → 本地文本点击/断言不可用
- 入口路径：首页「领淘金币」→ 可能进双11游戏页 → 右侧「日常版」→ 橙色「赚更多金币」→ 任务页
- 每日签到是**独立入口**（「今天可领 50 金币」），不在任务列表里

## 2. 三阶段架构

```
① 收集 Inventory   1 次 aiQuery，全量拿清单与档位 → 存 JSON
        ↓
② 决策 Plan        0 调用，本地算可行性/优先级/跳过 → 产出可审阅计划
        ↓
③ 执行 Execute     按计划跑；能 adb 就 adb，不行才 aiTap；坐标学一次后固化
```

**关键原则：计划是产物，不是过程。** 可以在执行前审阅、修改、只跑一部分、中断续跑。

## 4. 阶段②：决策（0 调用）

### 4.1 输入

- inventory.json
- 任务类型规则（`config/tasks/<platform>.yaml`）
- 风险策略（哪些类型默认跳过）

### 4.2 算法

```
1. 算每个任务的剩余次数 = quota_total − quota_done
2. 按类型标注执行方式与单位成本
3. 排除 risk = skip 的任务
4. 累加可达进度 → 判断能否跨档
5. 若跳过某任务导致掉档，把"掉档损失"显式列出来
6. 按 (单位收益 / 单位成本) 排序，产出执行序列
```

### 4.3 产出（可审阅）

```json
{
  "target": 20,
  "feasible": 14,
  "reachable_tier": 10,
  "unreachable_tier": 20,
  "loss_if_skip": 1.00,
  "plan": [
    {"seq":1, "task":"看看你关注店铺的优惠", "times":1, "how":"adb",       "est_cny":0},
    {"seq":2, "task":"你关注的商品都可抵",   "times":1, "how":"adb",       "est_cny":0},
    {"seq":3, "task":"看看#夜胶原",         "times":5, "how":"adb",       "est_cny":0},
    {"seq":4, "task":"去蚂蚁庄园逛逛哟",     "times":1, "how":"adb",       "est_cny":0},
    {"seq":5, "task":"去蚂蚁森林收能量",     "times":1, "how":"adb",       "est_cny":0},
    {"seq":6, "task":"搜一搜你心仪的宝贝",   "times":5, "how":"adb+input", "est_cny":0.10},
    {"seq":7, "task":"拍立淘逛感兴趣的宝贝", "times":5, "how":"aiTap",     "est_cny":0.10, "risk":"需相机"},
    {"seq":8, "task":"去支付宝农场逛逛哟",   "times":1, "how":"aiTap",     "est_cny":0.03, "risk":"跨App"}
```

**这一步不花一分钱，但产出了可以给人看的计划。**

### 4.4 可配置的策略

```yaml
# config/tasks/taobao.yaml
platform: taobao

# 任务类型：决定"这类任务怎么算完成"
kinds:
  browse:   { dwell: 12, swipe: 1 }
  miniapp:  { dwell: 15 }
  search:   { dwell: 8, input: "女装" }
  camera:   { dwell: 10, risk: high }

# 名称 → 类型（只做分类，不决定执行细节）
match:
  - { pattern: "搜一搜|搜索", kind: search }
  - { pattern: "蚂蚁庄园|蚂蚁森林|农场", kind: miniapp }
  - { pattern: "拍立淘", kind: camera, skip: true }
  - { pattern: "支付宝", skip: true }
  - { pattern: ".*", kind: browse }

# 掉档策略：宁可做高风险任务也不掉档？
tier_policy: prefer_tier   # prefer_tier | prefer_safe
```

`tier_policy: prefer_tier` 时，若跳过导致掉档，计划里会把被跳过的任务重新加回并标注风险。

## 5. 阶段③：执行

### 5.1 分流

| 类型 | 执行方式 | 每轮成本 |
|---|---|---|
| 浏览类 | 点任务 → 停 12s → 返回（全 adb） | ¥0 |
| 小程序类 | 点任务 → 停 15s → 返回（全 adb） | ¥0 |
| 搜索类 | 点搜索框 → 输入 → 点搜索 → 返回 | 2~3 次 aiTap ≈ ¥0.02 |
| 拍立淘 | 需相机，aiTap 兜底 | ¥0.02~0.05 |

### 5.2 学习与固化

**首次执行**：坐标未知 → `aiTap` 定位一次 → 记录归一化坐标
**后续执行**：直接用记录的坐标 `input tap`，0 调用

```json
// data/playbook/tb_main_tb_coin.json
{
  "version": 1,
  "learned_at": "2026-10-30",
  "elements": {
    "entry_icon":   [0.50, 0.238],
    "daily_tab":    [0.972, 0.219],
    "earn_more":    [0.50, 0.260],
    "task_row_1":   [0.85, 0.42],
    "claim_button": [0.36, 0.29]
  }
}
```

**失效处理**：每 3 轮探测一次进度；连续 2 次无增长 → 判定坐标失效 → 清除该元素 → 下次走 `aiTap` 重学。

### 5.3 续跑

计划里每条带 `done: true/false`。中断后重新读 inventory，对照计划跳过已完成项。

## 7. 为什么废弃 v1 的单循环

| | v1 单循环 | v2 三阶段 |
|---|---|---|
| 开始前知道总数吗 | ❌ 边做边探 | ✅ 一次拿全 |
| 能提前算可行性吗 | ❌ | ✅ 14/20，够不到 100 档 |
| 能人工干预吗 | ❌ 跑到一半没法停 | ✅ 计划可审、可改 |
| 中断能续跑吗 | ❌ 不知道做到哪 | ✅ 计划即进度 |
| 能跳过高风险任务吗 | ❌ 碰到才发现 | ✅ 计划阶段就排除 |
| 能按类型批量执行吗 | ❌ 混在一起 | ✅ 同类连续跑 |
| 每个任务让模型规划几次 | 8.6 次（实测） | 0 次 |

v1 的 `task.steps` 是一条复合 `ai()` 指令，含 4 个分支，模型每次都要重新拆解 → planning 占 83% 的 tokens。v2 把"怎么做"移到计划阶段（本地计算），执行阶段只做单动作。

## 9. 实施顺序

| 步 | 内容 | 验证 | 成本 |
|---|---|---|---|
| 1 | 收集阶段：inventory + JSON 落盘 | 跑一次，确认 8 任务/20 配额/档位全拿到 | ¥0.02 |
| 2 | 决策阶段：本地算法 + 计划落盘 | 干跑，确认可行性与掉档提示正确 | ¥0 |

| 4 | 坐标固化 + 失效重学 | 连跑 3 天，看命中率与成本 | — |
