## 3. 最小候选识别：窄版本，完整页面与唯一控件

建议合同族为通用 `entry-recovery`，首个版本仅认识本次双11广告，不宣称支持所有启动广告或所有 popup。观察输出单独为 `known-launch-ad`；实际授权仍由 runtime 所有。探针版本 `run210-specific-ad-proposal-v1` 的门槛如下：

1. 1080×2400 PNG，owner 精确为当前包/user，非空 frame id、合法原始 OCR bounds、无 observationError。真实运行还须有同一捕获的前后 owner 证据与下述 freshness。
2. 顶部系统状态区 `[0,0,1080,100]` 不作为广告身份；其余 `[0,100,1080,2400]` 完整覆盖页面像素，包含推广主体、跳过、底部品牌、系统导航。沿用 `componentMatches` 原阈值：16px tile，任一通道差 >24 的像素占比不得 >0.035，阈值未放宽。
3. 完整内容区 OCR 与真实参考逐项配对，文字和数量一致、bounds 差 ≤5px，保留原始误识别（例如“直降再叠劵”），不把纠正后的文字写回历史。全屏拒绝登录/验证/授权/允许/付款/支付/同意/确认等上下文。
4. 全页任何含规范化“跳过”的 OCR 必须唯一，并且原文精确为“跳过”；文字 bounds 必须位于固定 ROI `[850,110,1000,205]`。伪“跳过广告”、额外“跳 过”、偏移控件都拒绝。
5. 唯一 action 只由当前 OCR 中心生成。原帧 1 给出 `tap(920,157)`，原帧 2 给出 `tap(921,157)`。这是离线 proposal，不是已发出的动作，也未证实点击一定退出广告。不得点中央图、推广搜索、商品或依靠任意 back/launch 恢复。

实测两帧 PNG 并不相同：2592000 像素中 1431 个像素变化，全部限制在 `[884,138,986,174]`，即跳过文字局部；最大通道差 198。单参考按原严格阈值不能跨帧匹配，反向也不行；`[0,205,1080,2400]` 广告主体则匹配。因此探针使用两个真实参考做 OR，保留原阈值。无法凭这两帧推断变化是倒计时、字体动画还是其他原因。

这是有维护成本的窄方案：广告文案/素材变化会停止并要求新真实来源；甚至同一素材的跳过渲染变化也可能需要额外参考。不能承诺“只加一次参考以后每天可用”。若只保留顶部、底部稳定结构以规避素材维护，中央遮挡消融已经证明不安全；若要与素材无关，必须另行证明客户端控件语义与全屏遮挡检测，现有证据不足。

## 4. 有界恢复合同草案（尚未实现）

挂在 `enter_activity` 普通导航前的独立 prelude，保持 `open_app` 的前台 checkpoint 原语义。每个 session/attempt 仅一个 entry-recovery 状态；不要让 enter_activity/open_list 重入或新建 runtime 重置额度。普通任务导航授权覆盖退出已识别广告的意图，消费、登录和授权流程不在此合同范围内。

建议预算为可审阅初值，并非广告时长测量：总恢复 deadline 固定为首次进入 prelude 时间 +3000ms，且不得超出 stage/session deadline；新鲜帧检查至发送前 ≤1500ms；最多 1 次 skip tap；最多 2 次只读再观察，单次等待 500ms、累计等待 ≤1000ms。观察/OCR/归档也计入 deadline，不因新帧、重入或异常刷新。

状态至少记录 `contractVersion + sourceManifestDigest + sessionId + taskAttemptId + package + userId + recoveryId + phase + startedAt + deadline + sourceFrameId + capturedAt + pngSha256 + rawOcrSha + action + consumed + observationCount + waitMs + dispatchedAt + outcome + unknown`。

| 状态/输入 | 唯一允许行为/后继 |
|---|---|
| 初始已是 home/landing/panel | 用原合同真实确认；没有广告动作。按落点继续原入口路由。 |
| ready + 真实已识别广告 + 预算足够 | 为当前 frame/PNG/OCR/sourceVersion 绑定一次 skip proposal。 |
| 发送前 | 再验原始 PNG/OCR/source SHA、owner、唯一几何、原 action/当前 frame 身份、freshness、deadline；将 consume/attempt/source/action 持久化并 fsync 成功后才可能调用 device.act。持久化失败直接停止。 |
| tap 返回成功 | 仅说明派发返回；进入 awaitArrival，仍无首页/活动成功结论。记录派发起止/结果。 |
| tap 异常/超时、发送后崩溃、durable consumed 无明确结果 | unknown，停止；禁止自动重发，禁止重新 launch/back，禁止改用模型。 |
| 新帧且真实 home | 必须 frame id 不同、capturedAt 晚于派发完成、同 owner、未过原 deadline；记录 recovery confirmed，回到普通 enter_activity 的首页合同，重新捕获后使用其原来的一次首页 tap。恢复本身不能标 enter_activity 完成。 |
| 新帧且真实 landing | 记录恢复落点；enter_activity 可按原 landing arrival 语义完成；open_list 再用自身 landing→panel 合同。 |
| 新帧且真实 panel | 仅证明导航落点 panel；后续任务清单/余额仍走各自原门槛，不能冒充任务回执或收益。 |
| 仍为同款已识别广告 | 只读观察，最多上述 2 次/1000ms；不再次点。到限仍挡住就 needsLearning/stopped。 |
| 未识别页面、登录/授权/付款、owner 错误、坏 OCR、超时 | 立即停止；不把“跳过后应该首页”作为证据。 |

可选更保守模式：从 ready 直接进入只读等待，至多 2×500ms，再见真实 home/landing/panel 才继续；预算用尽停止，不切换到 tap 模式，不另开一轮预算。本轮 1006ms 两帧未自然退出，不能据此承诺只读等待有效；它是减少一次瞬态误停的有限尝试。两个模式应由配置明确二选一，不串联成隐形重试。

进程恢复：最小版本对 resume 一律 fail closed，除非未来能从 durable 同一 recoveryId/attempt/deadline 还原完整权威；缺失原记录不能重建 ready。原导航 `navigationStates` 当前为内存状态且 resume 拒绝，这个限制应保留。任何广告 consume 不得借新帧或阶段重建额度。
