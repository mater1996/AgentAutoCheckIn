## 最小修复候选及离线验证

候选只改变菜单缺字的职责：当原 OCR 不含 `•••` 时，不强制这个图标必须成为文字锚点；同一张参考的完整 menu ROI 和其余六区像素必须照常通过。若原 OCR 有 `•••`，仍要求精确唯一和原有 ≤5 px 边界；menu ROI 内额外未知文字仍按原规则拒绝。其他身份与入口精确文字、bounds、全局 blocker、text ROI、参考 SHA、原图校验、总预算和 runtime freshness 不变。不添加 `...`、`…` 等别名、substring、不新增原参考、不改原 frame、不拼参考、不裁 ROI、不增重试。

该候选只有 scratch checker 改动（不是生产实现）；新增 probe 记录了实际匹配 witness：原拒绝帧返回 landing、建议 `(115,998)`，耗时 47.864 ms，实际单一参考为 run201 `2ef5882b-2795-4d31-8d52-2fb3bf75c1f1`，七区全 true。原精确菜单 OCR 存在的诊断正例也通过。

共 17 个负例全部 null：七个完整 ROI 分别遮挡但保留原 OCR；另有 wrong owner、重复入口、缺入口、错 identity、入口 bounds 超 5、权限 blocker、menu ROI 未知字、重复菜单字、已有菜单 bounds 超 5、外来 panel marker 十例。修改 PNG 的负例均为 scratch 合成样例，不冒充独立真实截图。

建议下一步只实施这条窄的版本化图标策略，并让独立审计使用同版本与同原证据重新判定；实现前后需要正常 engine/runtime/audit 边界与过期帧/事件覆盖，再进行已授权范围内正常入口验收。本诊断未执行上述后续步骤。这里的通过只说明 landing 识别及候选动作可生成，不说明列表已打开、任务被选中、奖励被验证或收益已入账。
