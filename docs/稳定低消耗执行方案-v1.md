状态：历史设计版本，正式执行层尚未实现或真机验收。日期：2026-10-31。

后续设计见[Portal与Midscene组合执行方案 v2](Portal与Midscene组合执行方案-v2.md)。Portal安装、入口手势与首屏层级读取已完成少量实测，详见v2证据；下文“尚未安装”描述属于该版本撰写时点。

执行顺序补充：先验证Mobilerun Portal的完整层级、焦点状态和无障碍手势通道，再决定OCR补充范围；投屏比较要区分scrcpy SDK注入与UHID/AOA硬件鼠标。详见[Portal层级与Mac投屏比较](../research/Portal层级与Mac投屏比较-2026-10-31.md)。这是方案调整，尚未安装或真机对照。

本轮只写方案与调研、核对既有记录。没有改业务代码、操作手机、创建任务或启用调度。旧“等刷新取得v2第二次成功”不作为本轮执行目标，后续应按本方案决策重新排期，不删除历史证据。

## 1. 推荐决策

**保留账号、活动、资产、账本和面板；日常执行改为“本地观察＋有状态检查的流程”，模型用于理解新流程及少量异常。**

之前：几乎每个读数、定位、等待、步骤决策都走Midscene视觉模型；复用的多是指令，失败后再全量重扫与评估。

建议：一份新观察供各模块共用，优先用当前页面的可靠控件树或OCR；按已经验证过的页面前提和流程执行。只有实际页面无法被现有流程解释时才向模型提交完整上下文。普通失败先局部复核，不重复全量扫描，也不换任务凑成功。

Midscene仍可用，但不再是日常执行的强依赖。它可提供学习期视觉定位、有限探索和报告，亦可被直接视觉调用或其他Agent替换。官方文档明确：定位缓存是Web-only，查询结果不缓存，因此Android规划缓存不等于免模型执行。[1]

OCR值得采用为候选读屏器，不能先承诺它能解决所有问题。它读取“写了什么、在哪里”；任务含义和完成条件仍须从实际上下文学习，点击、焦点和奖励触发须另行验证。

## 3. 进程与职责

```text
面板/API进程 → 已有SQLite队列 → 单一设备worker（独占设备锁）
                                     │
              ┌──────────────────────┼──────────────────────┐
              ↓                      ↓                      ↓
        观察与本地解析           业务计划与流程执行        验证、成本与账本
        截图/控件树                 当前清单              状态证据、余额差
        OCR/局部图像                预算与配额            结束或更新剩余计划
              │                      │
              └──歧义/未知→受限学习适配器（可用Midscene或直接视觉）
```

- 面板只读状态、显示计划和入队，避免长手机操作阻塞HTTP。
- worker是唯一手机拥有者，控制动作、时间预算、取消、证据和入账。OCR不能操作设备。
- 本地OCR按需启动一个子进程、模型加载一次，JSONL/stdin-out或本地IPC返回结果；批次内复用，批次后可退出。是否保活由实测冷启动成本决定，不先建新常驻服务。
- 流程和规划均在worker内，不另建多Agent管理层。模型只是按需的外部调用；超时/调用配额必须在适配器边界生效，不能只在调用完成后检查总预算。
- 同一截图绑定frame_id、时间、宽高、前台、滚动状态；控件树另有时间戳，页面已改变时不得混作同一状态。OCR结果只属于该frame；滚动、跳转、键盘和弹窗变化后重取，不能持久缓存旧按钮坐标。

### 一次观察，多处使用

任务面板同一新鲜截图同时产出页面身份、遮挡、余额、档位、任务行、说明、次数、奖励和按钮框。本地模块共用这些事实，不分别向模型问多个问题。视觉兜底也合并成一次结构化读取。无关区域动画不能触发全屏重识别；改变检测只决定“需要重读”，不能证明任务完成。

任务行必须关联自己的说明、配额和按钮；出现多个“去完成”而无法绑定到所选任务时不点击。OCR位置只是当前目标定位，不能成为按名称猜业务做法的依据。

页面读取方法按已测覆盖选择，不每一步机械地先慢dump、再OCR、再模型全部跑一遍。当前页面树已知不可读时可直接OCR；改版或版本变化再采样覆盖。

## 4. 两种运行方式

### 学习新流程

1. 获取完整当前任务、实际说明和页面上下文；先确定能否在现有边界内做。
2. 模型判断已学流程是否真的适用；要求不足就打开入口只读实际落地页，不从标题猜浏览/搜索/游戏。
3. 父执行器监督实际动作，记录每次前提、动态目标、输入焦点、页面结果和完整完成提示。
4. 验证任务状态和同口径资产变化，保存候选流程。保存的是“怎样找到和判断”，不是最终屏幕坐标。
5. 另一次真实适用场景验证后才进入日常执行；说明或页面不匹配就暂停该流程，历史成功不覆盖当前差异。

学习有独立预算，不能每天自动无限重学；大改版需要人工审阅。两个成功是早期复用门槛，不等于长期可靠。

### 每日执行

1. 准备设备、确认账号实例和活动页面；登录/验证码/验证挑战停止。
2. 完整收集一次实时清单，合并重叠页，保留底部证据；读不全时不把清单当完整。优先本地解析，有歧义才合并视觉兜底。
3. 产出明确业务计划：做/跳过、原因、顺序、各几次、最大时长、模型额度和停止条件。成熟流程按历史实测成本排序；未知项不伪造成本。档位按当前实际规则计入计划，不把已达门槛当已领奖。
4. 执行前重新定位当前目标并核对要求和配额。若标题/说明/奖励改变且无法确立身份，局部重新理解，不凭相似名称硬合并。
5. 每个状态执行小动作后检查预期变化；按真实要求进行停留或滚动。静态“浏览10秒可领”不是倒计时已启动；时间到了不自动当完成。
6. 返回后只更新该任务相关状态、余额/档位与剩余计划。同页其他行明显变化、身份冲突、列表版本漂移才使相关计划失效；无必要不整表重扫。批次末做一次完整核对；异常状态无法安全恢复时写“状态待刷新”而非强制重扫。
7. 收尾核对真实资产余额，保存可证实净增，未归因部分保留未归因；初始/执行后计划有版本，不覆盖历史。

普通失败后停该批次的依赖动作，保存上下文供下一次计划跳过/复验。不一边状态不明一边执行下一任务；可读且无副作用的局部核对不需要重建整轮。

### 以“浏览15秒”为例

```text
当前面板与目标行确认 → 当前按钮定位 → 点击
→ 确认实际目的页/要求 → 按页面要求停留或滚动
→ 在关键时点本地读取计时/完成状态
→ 保存完整完成提示 → 有界返回 → 核对该任务与余额 → 更新计划
```

日常流程的步骤、等待和分支由配置执行。模型不需要每隔一秒看截图，也不需要对每次back规划。等待上限到达而没有完成证据则失败；一次有条件重试只针对已证实无副作用的未生效动作。

## 5. 稳定性不是多套几次重试

| 已暴露问题 | 新方案必须做的检查 |
| --- | --- |
| 点击exit0但没变化 | 已确认目标、页面稳定、一次点击、观察目标状态；明确仍原页且无副作用才重新定位一次。第二次无效停止。分别记录定位与输入效果，不能先怪模型或ADB |
| 中文注入成功但输入框空 | 确认真实焦点/键盘→输入普通词→读回输入框→提交→确认同词结果。旧yadb已在焦点明确时成功，不先换输入库 |
| 余额误读成商品奖励/预览 | 确认所属页面与余额区域、标签和截图；奖励数字与余额分字段。关键读数不确定就未知；同OCR重复两次不算独立验证 |
| 最后一次任务行消失 | 保存本attempt目标页完成证据，再结合余额/进度等；单凭消失不算成功；可见计数矛盾不得覆盖 |
| 固定模板失效 | 前提不匹配即停用，不用旧坐标继续点击；失败证据进入离线维护队列 |
| 模型502或卡住 | 成熟本地流程能在无模型时运行；歧义环节停止。模型设请求超时与总调用上限，预算外不自动换模型重试 |
| 失败后昂贵重扫 | 局部核对一次；未知不能恢复时收尾为待刷新。只有全局失效或批次末才重新完整收集 |

收益账与任务状态分开：任务有完成证据但余额未读到，可以报告任务证据成立、到账未确认；资产净增存在但流程报错，保留PARTIAL和净增，不自动扩大到多任务完成。没有可靠余额就不记估算收益。

普通浏览授权边界保持：不购买、加购、支付、提现、开会员、切账号、第三方授权；不输入凭据；出现登录或人机验证停止。邀请发送、组件添加、游戏及跨应用流程尚未验通，需各自明确范围，不按浏览类自动扩权。

## 6. 数据契约（拟议，未建表）

保留现有 `account`、`activity`、`asset`、`run`、`gain_event`；复用现有证据文件与快照能力。先新增结构化记录，确认查询需要后迁表，不为方案先造大库。

| 拟议记录 | 关键字段与约束 |
| --- | --- |
| observation | id/run_id/frame_id/captured_at/page_key/source/fields_json/confidence_json/screenshot_path/tree_path；关键字段保留原文、框、来源及未知理由 |
| task_instance | id/scan_id/account_id/activity_id/observed_name/instruction/quota_before/reward_display/observed_row_ref；名称和位置均不是跨天稳定主键 |
| workflow_version | id/version/hash/preconditions/actions_json/success_contract/source_attempt_ids/status；候选、有效、失配分开，适用条件必须可检验 |
| execution_plan | id/run_id/revision/inventory_ref/ordered_items_json/skip_reasons/budgets_json/execution_allowed；每项有次数、流程版本、停止条件 |
| task_attempt | id/run_id/task_instance_id/plan_id/workflow_hash/before_obs/after_obs/receipt_obs/status/error/started_at/ended_at/model_calls；attempt绑定当前一次，不跨任务复用回执 |
| reader_measurement | observation_id/engine/model_version/cold_or_warm/latency_ms/critical_field_results；用于OCR选型与漂移检测 |

看板口径：

- 日资产净增：既有 `gain_event` 按对应 `run.day/account_id/activity_id` 汇总；只记真实结算来源，禁止同时记余额净增和其拆项造成重复。
- 模型调用/tokens：既有 `run.model_calls/total_tokens`，缺测留空；付费金额按真实输入、缓存输入、输出计量与实际价目计算。
- 正常入口完成率：完整闭环成功的正常run / 有真实机会的正常run；人为指定任务、补点和诊断另列。
- 任务执行可靠性：成功且无人工补救attempt / 适用且有配额attempt，同时公布覆盖了多少流程、多少未知/跳过。
- 人工负担：人工恢复次数和分钟；不能只看tokens下降却每天需要人修。
- 积分名义人民币值与实际抵扣分列，不能用显示奖励或固定换算假装现金收益。

## 7. 范围与业务计划示例

基于今天盘点，第一阶段仅拟纳入：**直接领取、已验证的普通浏览、累计档位领取**。回首页入口回访可作为下一种独立流程；仍需真实验证。搜索保留“交互可达但奖励未触发”，不因换OCR就宣布支持。答题需语义判断且有后续未知；联动、邀请、组件和游戏不纳入第一批。

实际计划必须来自当日页面，不能把今天20条照搬到明天。下面只是计划形状，不是已授权执行清单：

- 做：已验证且当前要求匹配的直接领取一次；普通浏览按实际剩余额度和本轮预算分配；达到真实档位且按钮可领时单独领取。
- 顺序：先确定可领取项，再按实测成功率、耗时与可用价值选择浏览，必要时穿插档位领取；未知估值不伪造收益最优。
- 跳过：条件未验证、需要其他人/消费/新权限、当天匹配的真实失败、预算不足项；理由逐项保存。
- 停止：任务/页面身份不明、二次点击无效、计时无进展超时、配额矛盾、登录/验证、模型/时间预算耗尽。

先保证少量可用能力，不追求20条全做。新增平台先写页面与流程配置；若确有新原语，再扩通用能力，避免在执行器里写淘宝特判。

## 8. 成本预算与可证伪验收

以下均为**建议门槛/目标，不是实测成绩**，可随第一轮数据调校。调用限制为强约束，性能数字为验收目标。

| 项 | 初始建议 |
| --- | --- |
| 已验证单任务日常模型调用 | 目标0；允许最多1次合并视觉确认；仍歧义就停，不连续重规划 |
| 成熟活动每批次模型调用 | 上限3次，含入口/清单歧义/收尾；超出转诊断，不静默扩大额度 |
| 新流程学习 | 单任务最多8次模型请求、最多5分钟；先到即停。请求自身设超时；不自动启用每日重学 |
| 本地读取 | OCR模型常驻后的单截图p95目标≤2秒；记录冷启动、截图传输、树提取和OCR各段；达不到先换读屏方案再扩平台 |
| 普通浏览流程额外开销 | 在页面真实要求的停留时间之外，p95目标≤20秒；入口/首次完整收集单列，不能偷偷排除后声称整轮快 |
| 失败恢复 | 无副作用的同状态点击最多重定位一次；普通任务不整段重放 |
| 小样本验收 | 3种代表流程（直接领取、浏览、档位）各至少2个独立有效机会，完整正常入口至少一轮；不足配额就标未验，不硬凑 |
| 短期可靠性观察 | 人工监督跨至少3天累计20个有效机会，≥19次无人工补救，误记收益0；分别公布各类型与跳过。通过只证明初步可用，不证明长期稳定 |
| 调度 | 上述通过后由用户确认才恢复；调度验收不能替代业务验收 |

人民币预算不能先造数：目前已核对的是调用量与tokens，不是实际API账单。订阅内可能不逐次收费，仍有配额、延迟和人工成本；按量备用按供应商实际输入/缓存/输出价格分别计费，当前价格和用户订阅边际支出未核实。新路线本地OCR无需逐次云OCR付款，但有主机运行和维护成本，不能称系统零成本。

必须记录完整运行总时长、截图/树/OCR/模型/动作/业务等待耗时、调用与tokens、到账、人工干预和未覆盖项。只要新路线依旧经常依赖模型定位、或点击本身持续无效，就应停止扩展；先解决对应的读屏/驱动缺陷，必要时只保留一键签到等更简单活动。

## 9. 开发与验证顺序

1. **离线读屏对照**：用既有真实截图覆盖面板上下部、任务页、完成提示、键盘、错页数字、组件预览与遮挡。人工标注关键字段和目标按钮；同图比较RapidOCR与Apple Vision。记录关键字段精确匹配、误接受、目标框是否落入真实按钮、冷/暖延迟与内存。已有截图缺状态就明确缺口，不制造样本。
2. **真机执行原语**：不做全量任务，先确认定位正确后的点击效果、页面变化、返回，以及焦点→输入→读回。定位正确而动作无效就调查输入/渲染前提，不再加模型规划。
3. **最小主线**：从正常入口自行收集、给出具体计划、选择当前适用普通任务、执行、核验、结算、更新剩余计划。无需指定taskName或人工补点；失败也必须有可信状态。这个阶段是主要交付，不能用离线测试和指定任务回放代替。
4. **减少调用与复用**：在同一主线测本地流程，验证失配时能停、未知能保留、模型断线不会误执行/误入账。逐项比较旧run的实际成本，不能通过把清单和收尾移出计量范围做低数字。
5. **监督观察后再讨论调度**：按上面的窗口和机会数验收；用户确认后恢复已有调度，不新增并行调度器。

方案确认后只先实施前两阶段及最小主线所需变更；保留旧入口作对照，成功后再收敛入口。先备份，因为当前项目无Git。调研、方案与实测记录分别保留。

## 10. 当前确认与未确认

- 已确认：旧路线有成功与真实收益，但正常入口未完整通过，调用量偏高；局部打开返回不等于主线通过。任务清单动态，不能按固定名称和位置执行。
- 已确认：OCR与控件树可以作为本地观察候选；Midscene缓存范围有明确限制，不能据缓存承诺Android零调用。[1][2][7]
- 未确认：两种本地OCR在本机、本截图、动态图和关键数字上的准确率、速度、内存，以及真正降低了多少调用。
- 未确认：间歇点击无效根因、搜索任务触发前提；本方案没有以技术选型掩盖这两个实际问题。
- 本轮交付：本设计、配套技术选型、官方页面原文、数据库指标摘录；没有交付一个已实现的OCR执行器。
