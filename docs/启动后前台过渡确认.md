# 启动后前台过渡确认

此改动只处理本设备实例已成功执行并保存 `launch-start` 后，紧接着的首次 `capture()` 读不到严格前台标记的情况。`act(launch)` 仍只执行一次 resolve 和一次 start，不在其中截图，也不等待第二次 launch。

严格解析规则保持原样：优先读取 `topResumedActivity=`；没有该标记才读取 `mResumedActivity:` / `mResumedActivity=`。候选必须唯一、格式有效，且启动确认必须同时匹配原始启动的 package 和 Android user。`Resumed:`、`ResumedActivity:`、`mFocusedApp` 及任意 ActivityRecord 都不能作为别名或补足身份。

## 一次只读确认

- start 返回且检查成功时建立一个固定的单调时钟截止时间：完成后 1500ms。start 命令证据写入成功后才授予本次确认资格，写证据耗时也占用预算。
- 首次 capture 开始便消费资格。其第一条 foreground 命令的 timeout 为该截止时间的剩余整毫秒。
- 只有严格解析得到 missing，即两种候选标记都不存在，且该命令原始证据已成功保存，才可等待 250ms 并重读一次。等待前剩余预算必须大于 250ms；等待后重新核算剩余预算。
- 最多两条启动前台读取（原读取加一次重读），共享同一个 1500ms 截止时间。不存在重置预算、第三条读取或重发 start 的分支。正常截图后的 foreground 检查属于原 capture 流程，仍然执行。
- 歧义、格式错误、无效身份、不同 package/user、exec 失败、迟到结果和预算耗尽直接失败。即使迟到输出恰好匹配 owner，也不能接受。
- 启动确认失败后，本设备实例后续 capture 返回原失败，不再执行 foreground，防止 runtime 的通用只读观察重试绕过这次确认的边界。后续新 session 使用新的设备实例。其他动作会撤销尚未消费的启动确认资格。

生产命令继续使用 `execFile` 的 timeout；本确认向命令显式传入剩余预算。调用链等待真实 exec promise 完成以及命令证据写入，期间保持设备 exclusive，不用 `Promise.race` 提前释放设备。注入的 `DeviceExec` 必须履行 timeout 并在底层进程结束后才 settle；超过截止时间的已完成输出仍会被拒绝。进程终止后的 drain 和证据写入可能晚于接受结果的截止时间，但不能因此接受迟到结果或提前让下一条设备操作进入。

## 证据与成功含义

每次 foreground 都继续在 `device-command-evidence/foreground-<uuid>.json` 保存完整 stdout/stderr、时间、timeout、退出结果、严格候选与分类。新增 `launch-transition-<uuid>.json` 保存原 owner、start 完成时间、单调截止时间、1500ms 预算、重读上限、实际等待及原因 `post_launch_foreground_markers_missing`、最终状态与耗时。没有发生等待时 `waits` 为空。

`foreground_confirmed` 仅说明本次严格 foreground 在期限内匹配 owner；`completionInferred` 固定为 false。之后仍执行新的 screencap、PNG 校验、截图后 owner 校验、OCR 和 runtime 的登录/验证风险检查。不会刷新旧 frame 的 id、capturedAt 或动作权限。耗尽或失败维持 unknown；真实 runtime 回归测试证明观察重试和 stage 重入均不会执行第二次 launch。
