# run204 页面转场诊断

结论：run204 在两个无业务动作的观测之间，从 `2155` 任务面板变为完整绘制的赛车 landing；导航按现有合同正确拒绝。对 run200 的首个失败是身份 OCR 原文不同；对 run201 两张来源，身份文字与 bounds 全部通过，但新增的音效 OCR「4）」和 Android 导航 OCR「三」先触发 ROI 重叠文字拒绝，随后仍有真实音效像素 gate 失败。不能只删除 OCR 阻塞就宣称恢复。此帧应归为**已绘制、稳定性及数据就绪状态未知的 landing**；证据不足以认定新稳定变体，也不足以认定明确加载占位。没有后续帧，不能推定等待会恢复，`0000` 不是可接受的资产余额。

本次只写本文、[离线 probe](probes/run204-transition-probe.ts)及[完整输出](probes/run204-transition.output.json)，未修改生产代码、来源清单、原始证据、数据库、ledger 或调度，未调用设备、实时 OCR 或模型 API。probe 内 validator 只在 TMPDIR 创建并删除回放沙盒，通过保存的 OCR 重放校验；没有打开数据库。未重跑全量测试。

## 原因判定与有界只读恢复所需证据

已经证明的直接原因是**保存帧不满足来源合同**。应用为何自己从panel切到landing仍未知。三个可区分的假设及未来证据：

1. 已绘制的新页面状态/音效状态组合：若后续多帧持续维持无斜杠音效、稳定身份和按钮且数据正常，可支持稳定候选；当前只有一张末帧，不足以新增稳定来源。
2. 数据初始化/刷新中间态：若受控的后续只读序列在无业务动作下从0000到完整真实数据并通过原gate，可支持短暂过渡；当前没有后续帧，不能断言“再等就好”。
3. 页面实例重建、应用内部重置或网络异常：需要原始生命周期/页面实例或网络完成/失败证据并与时间对齐。当前foreground、状态栏瞬时速率、两个截图均不能区分这些原因。

若后续另行授权恢复研究，最低证据应是一个**预先限定次数和总耗时的纯观测实验**：例如最多2次补帧、每次间隔≤5秒、累计等待≤10秒且受原stage deadline更严限制；这只是建议的实验上界，不是现有生产策略或已授权实施。每帧保存全图PNG、原始OCR、hash、capture前后foreground、采集与处理时间、同一session/owner/attempt、原始gate逐项结果以及累计观测次数。应用唤醒是额外环境变化，必须记录，不能混称全程无状态改变。帧过期须重采，旧帧不能重新取得点击权限。

恢复标准必须区分“允许继续观察”和“允许继续导航”：确认已知owner、无登录验证/遮挡、没有已发出结果未知的动作，才能讨论只读补帧；发现新的界面、错误owner、观测错误或预算耗尽立即停止。只读观察不能触发tap/back/launch/游戏/能量/任务/领币/ledger。若后续重新得到当前**原合同完整通过**的panel或landing，仍需在正式动作前使用当时新鲜帧，并确认动作本身已有单独授权；原run204 stopped不改写。

若末帧组合长期稳定但始终不通过，必须先人工审核真实来源、建立正负例，再另案调整来源合同；不能以“等待多次”替代gate。若只想允许未知landing短暂再观察，应先建立离线回归，覆盖从未知恢复、永久未知、错误owner、验证/遮挡、超预算、已有dispatch-unknown禁止重放等情况。对资产恢复，至少需要回到拥有标记panel并取得可独立audit的余额证据；两次独立新鲜采样才可讨论稳定读数，不能拿当前0000或首帧2155补填后续。
