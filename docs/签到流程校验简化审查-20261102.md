# 签到流程校验简化审查（2026-11-02）

## 结论与审查边界

普通页面识别、浏览要求和完成回执可以优先使用当前画面的关键词；不能再让无关商品文字、动态店名/会员等级、旧截图位置或旧促销后缀成为整步失败条件。关键词用于回答这一阶段的业务问题：当前是什么页、真正要求做什么、这次是否完成。关键词本身不能证明余额属于哪个资产，也不能证明一个动作未派发，因此账户归属、本次 attempt 关联、未知输入不重发、正确余额字段仍须保留。

本次仅阅读源码、配置、已保存证据和 SQLite（`mode=ro`），并用 Python 等价表达式复核两个选择条件。没有运行生产入口、测试套件、OCR、模型、网络或手机命令，没有写配置、计划、账本或历史证据。唯一交付文件为本文。代码检查和安卓自动化技能仅用于只读审查。仓库无 Git，祖先目录未发现适用的 AGENTS.md。另一个工作流正在修改 device/runtime；本文描述的是阅读时的实现，行号供定位，不代表已合并其后续修复。

实际入口为 `runner/staged/main.ts:26` → `runActivitySession` → runtime 各阶段 → store。当前批次配置为 `data/evidence/plans/tasks-once-20261102/config.json`：`navigationPolicy=current-text-v1`、`panelReadPolicy=focused-v1`、`taskObservationPolicy=current-components-v1`、`aiTaskRecovery=true`、`balanceComponent=false`、`scriptValidationMode=false`、`selectionAllowNew=false`，单 session 一项。不能用旧像素分支的限制概括当前所有分支，也不能把“current-components”理解成所有历史依赖都已移除。

## 两个已复核的具体误拒

### 1. 发现精选好物：1/3 被当日按名屏蔽

`main.ts:55` 将当天 `completed/supervised_success + gainCoins>0` 的执行映射成 `name[]`，丢掉 task instance、要求、完成轮数、所属批次和尝试情况。`runtime.ts:918` 又用 `!(opts.completed ?? []).includes(d.name)` 否决当前候选。这不是 `done >= total`，而是“当天一轮成功即整名禁做”。`engine.ts:237` 另有按 count/quota 的纯选择函数，但当前 choose 没有调用它，不能据它宣称正常入口已按次数处理。

实际只读证据：

- 账号 bundle 的 run218 当日成功记录为“发现精选好物 / 浏览”，原快照 `0/3`，本次收益 50；SQLite 只读查得 run.day=`2026-11-02`。
- 批次初始完整清单 `evidence/staged-2026-11-02T11-25-34-259Z/inventory.json` 中它仍是 `1/3`；run225 再次完整清单中也为 `1/3`。
- 当前 plan 明确该任务 `decision=do, initialExecutions=1, observedDone=1, observedTotal=3`，没有本批已尝试记录。
- Python 等价条件复核：旧按名条件 eligible=false；“当前未满额 + do + 本批 attempts < 1”条件 eligible=true。这是规则复核，未运行生产选择器或手机。

最小建议：选择输入保留具体任务身份/轮次与本批尝试数，不再把成功历史压扁成名称禁表；本批以当前 do 和本批一次上限判断。账号当天历史继续保存，run218 仍占据当天已完成一轮，不能改为未完成。若产品另设“每名每日只做一轮”，应明列策略；不能由去重实现暗中替代本批已批准计划。本审查不修改该策略或继续执行。

同时，`loadPlanDecisions` 保存了 times，choose 并未消费它；本批失败已通过 plan 改为 pending 排除，而不是选择器自身保证 attempts。这不要求新建大队列：在现有 plan/已保存执行输入的选择条件消费本批尝试上限即可。run224、run225 都已消耗本批一次，即使无收益、修复后本来可识别完成，也不能再选。

### 2. 浏览15秒得：文案尾字导致不能复用，还存在动态身份障碍

plan 当前原文为“你关注的商品都可抵 / 浏览15秒得”，记录 `0/1`、浏览奖励 30；dwell 合同是同名 `/浏览15秒`。两份最近完整清单均读到“浏览15秒得”，所以不是孤立的手写差异。plan 的 pending 原因直接写了“不精确匹配”。

最小建议是保留原文，派生用于行为匹配的“普通浏览、15秒”语义；仅去掉不改变要求的“得”等奖励连接词。不要直接改 plan 文案、模糊匹配所有包含“浏览”的任务、或丢掉“下单/输入/连续滑动”等实质条件。

仅修尾字还不够：该合同浏览身份包含 `^←我的足迹币1440$`、`^浏览过$`、`^加购过$`。历史余额 1440 不是页面身份，币数改变会继续拒。其他合同还有 `^君乐宝百汇专卖店$`、`^青铜会员$`、`^肥料0$`。应把这些动态内容降为历史学习记录，以当前目的页上下文和明确独立浏览要求决定能否复用等待动作。它目前为 pending，技术匹配修复不自动将其改为 do；先在既有普通浏览授权内核实当前完整要求并刷新决策，不能把待核能力说成已执行。
