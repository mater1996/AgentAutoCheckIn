## 具体行为

以真实农场来源 160 为例：当前页面只要来源合同真实、package/user 正确，页面身份文字各唯一，当前 `浏览5秒` 与 `得奖励` 为同一相邻组件，即返回 browsing/5000；完整且唯一的 `任务已完成` 与 `继续逛逛吧` 组件和合同要求的奖励金额才返回 completed。实际等待、刷新、尝试绑定、超时、返回和结算由调用方负责；等待时间经过不能证明完成。

1. 验证合同内容哈希、来源结果/session 原始哈希、正收益和任务映射；历史合同通过既有冻结 provenance 验证。读取并验证 browsing/receipt 的 PNG/OCR 原始哈希，保留 requirementEvidence 和独立 IP 学习来源真实性。
2. 验证当前 owner、尺寸、框合法性和阻断文字。当前 PNG 必须可解码；当前 raw OCR 的 `pages[0].file`/尺寸绑定 PNG，saved frame 的 id/path/capturedAt/owner 绑定传入帧；身份、要求、完成、金额与风险字段的文字和框必须在 raw/saved/传入帧中一致。无关商品文字和已有无关标题精修不会阻断 IP 页。早期 raw-pages 历史帧仅可通过原始哈希与 summary 派生的精确 frame 回放。
3. 页面身份使用合同已有的完整文字正则，当前每个身份必须唯一；保留来源可证的相对上下关系。识别相邻组件依赖当前两行的重叠、先后与行高比例，不绑定历史位置或 ±6px，不比较商品、装饰或组件历史像素。source 160 browsing 与 receipt 的页面身份不同，分别使用实际来源的身份。
4. 浏览必须有真实 browsing 来源中的完整秒数与 `得奖励`；秒数与合同严格相等，当前文字唯一且相邻，无冲突要求/完成。来源只有完成证据或缺少完整要求时不能凭当前任务名、列表指令或历史像素造等待来源。IP 通过既有 `buildTextDwellContract` 绑定独立保存的真实 5 秒来源；旧 receiptOnly 本身仍不授权等待。
5. 完成必须有完整 `任务已完成` 及 `继续逛逛吧`，且唯一、相邻、位于当前主身份之后。仅容许来源 134 中包围完整短语的引号，不补字、不容错替换。若原合同包含 `+金额`，须唯一、严格相等并与完成组件有当前几何关系；引文来自当前文字。缺完整完成文字的历史帧保持 unknown。

## 边界与待整合

- 新函数是观察器；runtime 策略开关、调度等待、独立 audit 同步与实现归档由父任务负责。本子任务未改动这些文件，不能宣称新策略的正常入口已验收。
- 固定继承 1080×2400 与淘宝 owner 范围；不推断任务名，不支持新的秒数/新页面/新奖励流程。
- 没有模糊匹配或运行时 OCR。来源要求缺字、当前文字合并/缺字、唯一身份缺失时返回 unknown；未添加来源中没有的别名。
- PNG 解码及 raw/saved 路径绑定不等于独立验证文字确实存在于像素。当前可信捕获链若同时产生了错误 OCR，或出现无可读文字遮罩，本策略不保证发现；同路径 PNG 被换成同尺寸合法图片也无法从不带当前 PNG 哈希的 DeviceFrame 单独判断。取消历史像素门槛后保留这一明确限制，不以历史装饰比较弥补。
- 合同仍使用旧版本标识，运行与审计归档必须额外记录策略 `current-components-v1`，避免把新判断解释为旧像素策略的结果。
