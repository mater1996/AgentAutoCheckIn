## 最小修复建议（未落生产）

建议保持固定 ROI、现有 `lo > 180`、严格逐像素双向相等、唯一数字标签、完整 coin/arrow/title、全不透明 PNG、同帧严格4位整数 OCR、frame/hash 绑定和预算检查，向原图 glyph 来源增加一个经过视觉检查、hash 固定的新形状样本：

```ts
{
  path: 'evidence/staged-2026-11-01T14-28-53-024Z/fe1dce16-9782-4b0e-a70f-87b0c82b8f09.png',
  sha256: 'bb13541fde0147fb944bf1614dc128af50bc9463465cbb7d58c6d98f61758dcd',
  value: 2155,
}
```

这里 `2155` 仅为此原图四个 glyph 的人工标注，运行时仍逐位组合；绝不能加入整个金额白名单、复制历史结果或直接接受 OCR 前缀。最小实现可扩充 `EXTRA_SOURCES` 并更新组件版本。若后续多个灰度变体持续出现，应另立任务设计稳定的前景分割及负例验证，本诊断不主张“一像素容差”、最近邻接受或阈值整体调整。

可复现 probe 在 scratch 生成生产模块副本，只调整资产根、sharp 导入路径和上述来源条目；原 `runner/staged/balance-component.ts` 未被写入，副本不会参与实际运行。该副本得到：

- 9/9新帧 accepted=2155，均经过真实本地整数 OCR；其中8帧不是新增来源帧，但它们的二值形状相同，因此属于同一形状的重复验证，并非8种新泛化样式。
- 5个合成图像负例（数字核心、coin、arrow、title遮挡及额外长度区域）全部在 OCR 前拒绝。
- 7个明确合成的 OCR 负例 `2135`、`155`、`2155 50`、`2155.50`、`¥2155`、`2155無`、`-2155` 全部因严格整数或 glyph/OCR 不一致而拒绝。这些是假输出的拒绝探针，不是伪造正例 OCR。
- 单独修改相邻人民币区域 `(240,285,60,22)`，真实本地 OCR 后仍 accepted=2155，说明不需要把相邻金额绑定成余额。

负例边界的最小要求：保留现有34项组件测试；新样本的核心缺笔、币/箭头/标题遮挡必须拒绝；完整不同金额应由其真实 glyph 识别且与OCR一致，错误OCR不得借新样本获准；金额含人民币符号、小数、多组数字不得通过。局部遮挡恰好让形状等于另一个真实数字、或仅改变阈值外像素，单靠二值图无法普遍区分，本次有限负例不证明任意遮挡都可检出。
