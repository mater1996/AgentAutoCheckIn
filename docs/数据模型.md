# 数据模型 v1.0

对应实际代码（SQLite + Drizzle）。**这份文档描述现状 + 缺口，不是愿望清单。**

> v0（配方 + JSONL 账本）已归档到 `archive/数据模型-v0-配方版.md`，与当前实现不符，不再维护。

---

## 0. 一句话结构

```
一个账号 → 多个活动 → 每个活动有 目标 / 探测 / 任务单元 / 档位
                        ↓ 每次执行
                    run（执行记录，含成本）
                        ↓ 读余额
                asset_snapshot（资产快照，主数据）
```

**核心原则**：快照是真相，run 是过程。收益 = 快照差值，不靠平台自报。

---

## 1. 五个阶段

每次执行都走这五段，每段产出不同数据：

| 阶段 | 干什么 | 产出 | 成本 |
|---|---|---|---|
| **① 准备 Prep** | 设备健康 → 风控闸门 → 清弹窗 → 启动 → 归位 → 起始断言 | `run.prep_ms` + 失败状态 | 0 调用 |
| **② 探测 Probe** | 读当前状态：余额、进度、剩余任务、档位 | `snapshot` / `run.balance_before` | 1 次/项 |
| **③ 执行 Act** | 按任务单元反复操作，直到终止条件成立 | 中间快照（可选） | 1~2 次/单元 |
| **④ 结算 Settle** | 读终态 → 算差值 → 判状态 | `run.balance_after` + `run.status` | 1 次/项 |
| **⑤ 记账 Book** | 写快照、写 run、更新缓存健康 | `asset_snapshot` + `run` | 0 |

**现状问题**：阶段②③④在代码里是一条直线（`flow` 数组），没有独立边界。探测和结算只是 flow 里的两个 `read` 步骤，无法表达"先探测再决定做几个"。

## 2. 实体清单（现状）

### 2.1 `account` — 账号

```sql
id, app, package, user_id, cache_id, enabled, note
```

| 字段 | 含义 | 备注 |
|---|---|---|
| `id` | 全局唯一（`tb_main`） | 账本主键 |
| `package` | Android 包名 | 双开同包名 |
| `user_id` | `0` 主空间 / `999` 双开 | 唯一区分依据 |
| `cache_id` | Midscene 缓存标识 | **必须一账号一份** |

**缺口**：无 `platform` 字段。现在隐含只有 android，接 iOS/Web 时要加。

### 2.2 `activity` — 活动

```sql
id, account_id, name, steps_json, verify_any, balance_query,
entry_text_any, asset_id, window_start, window_end, enabled, state
```

`steps_json` 就是整条 flow 的序列化。**这是当前模型的根问题**：目标、探测、任务选择、执行单元、终止条件全压在这一个 JSON 字符串里。

### 2.3 `asset` — 资产

```sql
id, platform, name, unit, cny_per_unit, expiry_days, redeem_path, note
```

`cny_per_unit` 是**唯一折算入口**。历史快照不重算，只影响新记录。

### 2.4 `asset_snapshot` — 资产快照（主数据）

```sql
id, ts, day, asset_id, account_id, balance, source, run_id, note
```

每读一次余额写一条。`source`: `read`（模型读）/ `manual`（人工补录）。

### 2.5 `run` — 执行记录（含成本）

```sql
id, ts, day, account_id, activity_id, status,
cache_hit, cold_start, prep_ms, exec_ms,
balance_before, balance_after, error, evidence_dir,
prompt_tokens, completion_tokens, total_tokens, cached_tokens,
model_calls, model_name, usage_json
```

### 2.6 `cache_state` / `job` — 辅助

`cache_state` 记缓存命中/失败/重建次数；`job` 是任务队列（**当前未启用**，调度走 cron）。

## 3. 收益模型

### 3.1 三口径

| 口径 | 字段 | 含义 |
|---|---|---|
| **账面** | `balance × cny_per_unit` | 名义值 |
| **可用** | 扣除过期/门槛 | 真能花掉的 |
| **现金** | 提现/抵扣已发生 | 实际到账 |

现状只实现了**账面**。`expiry_days` 存了但面板没有"即将过期"预警。

### 3.2 收益来源只有一种

```sql
delta = run.balance_after - run.balance_before
```

**优点**：可信，不受平台缩水发奖影响。
**缺口**：**不知道这 120 金币从哪来**——是任务给的 90 + 档位 30，还是别的？没有任何明细。

实测那次 `80 → 200 = +120`，按任务数推断是 3 任务 × 30 + 档位 30，但**这是倒推，不是记录**。

### 3.3 档位价值（已算，未入模型）

| 进度 | 档位奖励 | 跨档边际 |
|---|---|---|
| 3/20 | +30 | — |
| 10/20 | +50 | 82.3 ¥/h |
| 20/20 | +100 | 133.7 ¥/h |

**这组数字现在只活在文档里，代码不认识 `tiers` 这个概念。** 所以 `max: 3` 是拍脑袋写的，不是算出来的。

## 4. 成本模型

### 4.1 两类成本

| 类型 | 记录位置 | 现状 |
|---|---|---|
| **模型 token** | `run.prompt_tokens` 等 7 个字段 | ⚠️ 字段已建，**库里 0 条有值** |
| **时间** | `run.prep_ms` / `run.exec_ms` | ✅ 有真实数据 |
| **人工介入** | — | ❌ 无记录（`NEEDS_HUMAN` 只记状态，不记补跑耗时） |

**token 字段是空的**：`SELECT COUNT(*) FROM run WHERE total_tokens IS NOT NULL` → **0**。代码里 `agent.metrics` 读取逻辑已写（`signin.ts:352`），但历史 7 条 run 都发生在加这个功能之前。

单点实测能拿到数（探针 `model_default_check.ts` 跑 2 次调用得 14,216 tokens），但**还没在完整流程里落过库**。这是缺口，不是已完成项。

### 4.2 成本折算

面板按 `COST_PER_MTOK`（默认 ¥2/百万）折算。走订阅时边际成本 ¥0，但仍记参考价。

### 4.3 单次实测（terra 通道）

| 调用类型 | tokens/次 | 说明 |
|---|---|---|
| `locate` | ~4,500 | 定位，Android 不缓存 |
| `insight` | ~7,100 | 读数/判断，带整屏上下文 |

**缺口**：`run.usage_json` 存了按 intent 的分布，但面板没展示 plan/locate/insight 拆分。

## 5. 状态机（代码实际产出 7 种）

代码里真正会写入的 status 值：

| 状态 | 来源 | 含义 | 计入收益 |
|---|---|---|---|
| `OK` | signin | 余额增长（`grew`） | ✅ |
| `ALREADY` | signin | 验证词命中但余额没涨 | ❌ |
| `NO_EFFECT` | signin | 跑了但余额无变化、也无验证词 | ❌ |
| `ERROR` | signin | 步骤抛错 **或** 读数校验不通过 | ❌ |
| `NEEDS_HUMAN` | prep | 风控页 / 起始断言不过 | ❌ |
| `DEVICE_ERROR` | prep | 设备离线/低电 | ❌ |
| `LAUNCH_FAILED` | prep | App 起不来 | ❌ |

### 关于 `INVALID_READ`（重要）

数据库里有 4 条 `INVALID_READ`，但**代码里不存在这个状态字面量**，`db/schema.ts` 也没定义枚举——这 4 条是当时手工 `UPDATE` 打标记的。

**真实行为**：读数校验不通过时，`failed.push(...)` 然后走到 `status = 'ERROR'`。所以"读数不可信"和"步骤抛错"**在库里分不开**，只能靠 `error` 文本里有没有"读数不可信"来辨。

这是缺口：应当有独立状态（如 `BAD_READ`），否则面板统计 `bad` 时会把"读错了"和"跑挂了"混为一谈。

### 状态判定顺序（代码原文）

```ts
if (grew) status = 'OK';
else if (verified) status = 'ALREADY';
else if (failed.length) status = 'ERROR';
else status = 'NO_EFFECT';
```

**注意**：`grew` 优先于 `verified`。余额涨了就算成功，哪怕没看到验证词。

## 6. 缺口汇总

| # | 缺口 | 影响 | 优先级 |
|---|---|---|---|
| 1 | **无 `objective` 表** | 目标写在 YAML 注释里，查不到 | P0 |
| 2 | **无 `tier` 表** | 引擎不认识档位，`max` 只能拍脑袋 | P0 |
| 3 | **无 `probe` 定义** | 探测是 flow 里的临时步骤，不是可复用状态源 | P0 |
| 4 | **无 `task` 表** | 任务选择靠自然语言，无法统计"做了哪些任务" | P1 |
| 5 | **无收益明细** | 只有总额差值，不知构成（+120 拆不出 90+30） | P1 |
| 6 | **无过期预警** | `expiry_days` 存了没用 | P1 |
| 7 | **无 `platform` 字段** | 隐含只有 Android | P2 |
| 8 | **无人工成本记录** | `NEEDS_HUMAN` 的实际代价未知 | P2 |
| 9 | **读数失败无独立状态** | 与 `ERROR` 混淆，面板 `bad` 统计不准 | P1 |
| 10 | **token 未落库** | 代码已写但 0 条数据，成本口径无法验证 | P0 |

## 7. 目标模型（待建，需确认）

这是缺口 1~4 的解法，**尚未实现，等你确认后写入代码**。

```yaml
objective:
  metric: taobao_coins          # 追哪个资产
  strategy: maximize_value      # 追价值，不追次数
  constraints:
    max_seconds: 900
    risk_level: low

probes:                          # 探测：返回结构化数字，不是是非
  - id: progress
    ask: 页面顶部「完成进度」显示的数字是多少？按 a/b 格式回复
    parse: fraction              # → {done, total}
  - id: tasks_left
    ask: 任务列表里还有几个显示「去完成」？只回复数字
    parse: int

tiers:                           # 档位：把"值不值"变成数据
  - { at: 3,  reward: 30 }
  - { at: 10, reward: 50 }
  - { at: 20, reward: 100 }

unit:                            # 任务单元：怎么做
  - do: ai
    say: 在任务列表里找到第一个还显示「去完成」的任务，点击它
  - do: dwell
    seconds: 12
  - do: back

terminate_when:                  # 终止条件：本地计算，0 调用
  any:
    - progress.done >= progress.total
    - tasks_left == 0
    - elapsed > max_seconds
    - marginal_cny_per_hour < 25
```

**关键**：终止条件由引擎算，不由模型答。模型只负责探测出数字。
