# 审计：正常主线复用与结算归档

本轮范围：只读源码、当前联合配置/计划、最新正式 run218–223 的已有 JSON、v2 索引所指 bundle、stage 索引及只读 SQLite。正式 run 最大编号读回为 **223**。只新增本报告；没有修改实现、配置、计划、原证据或账本，没有连接设备、调用模型、运行任务或启用调度。目录没有 Git 元数据，不能据此核对提交历史。以下行号以本轮读取的现有文件为准，项目根为 `/Users/mater/Project/checkin-platform`。

## 结论

**反复卡检查的原因不等于“16 类都没学过”。历史首学已经提供可复用来源；正常入口现在是多种候选执行合同和页面检查串联起来的一次单任务会话，缺少统一的次数/进度消费、完整规划归档、AI 辅助稳定证据汇总与发布接线。** 当前联合配置也只覆盖 12 个精确任务身份，其中 11 do、1 pending，并非 16 类全部进入正常路线。

真正的结算归档已经工作过：run218 正常入口取得同 attempt 回执，余额 2265→2315，两张结算新帧同为 2315，SQLite 有 +50 gain_event，v2 执行归档完整。DB 的 DIAGNOSTIC、result 的 diagnostic_only、候选脚本状态，说明尚未宣称可独立稳定复跑，**不表示没有到账或没有记账**。同样，首学成功只证明来源与那次执行，不能自动证明当前合同完整、入口接通或满足两次独立正常成功。

当前先要讨论的是公共路线：哪些页面用文字/相对布局、何时交 AI、如何消费真实额度和稳定验收次数。继续对每个新正常页面补一组历史像素、再让用户逐任务监督，会重复暴露同一类接线问题。本文仅提出路线与验收条件，不实现新 planner，也不改变既有策略。

## 2. 次数、状态、计划推进没有统一

### 2.1 名字级当天屏蔽与真实额度冲突

`main.ts:43–48` 从 v2 成功执行中查 DB 的当日记录，生成 completed **任务名数组**；`runtime.ts:790` 在 scriptValidationMode=false 时，只要名字在数组里就排除。它不按 exact task+instruction、合同版本、已成功次数或稳定验收次数判断。当前联合配置为 false，因此 run218 后“发现精选好物”会被当天整体屏蔽，即使后来列表显示 1/3。

本轮按现有 bundle 与 DB 相同条件离线核对：2026-11-02 当天进入此屏蔽数组的是 run218“发现精选好物／浏览”，+50。run220 已保存完整列表中该项仍为 1/3。这个缺陷会阻挡同日第二独立成功，但不能倒推它是 run220 停止的原因：run220 用的是 **仅 IP 的缺陷复验配置**，IP 未见，选不到目标符合其窄范围。

`config.ts:84–86` 把 initialExecutions 转成 times；当前 plan 的 12 项 initialExecutions 均为 1。但正常 choose 不读取 times，也不消费 maxAttempts。`engine.ts:217–228` 另有按 taskDefinitionId 或精确 name+instruction、maxAttempts 和完成 count 选择的纯函数 `selectCurrentTask`；本轮检索仅发现其定义和测试，runtime 没调用。不能用该函数的测试通过来证明正常路线已按次数规划。

因此需要明确区分：页面额度、计划允许执行次数、已派发 attempt、确认成功次数、同执行过程的稳定验收次数。缺席/日限不等于执行失败；已派发结果未知也不能当作可重新执行的空位。

### 2.2 采集结果与账户规划脱节

`store.ts:197–207` 只在已经选到任务时，生成该任务的一张 snapshot、一条 `complete:false` inventory、一项 do 的 plan，并写 `paused_after_staged_task`、`requiresInventoryRefresh:true`、nextTask 默认 null。它明确标注“不是完整 inventory plan”。并不消费 `collect_list` 保存的完整名单，也不回写原 plan 的 do/skip/pending、次数与下一步。

实际读回：run218、219 的 v2 execution 均存在，progress 均暂停且 nextTask=null；run220–223 因 task=null 不产生相应任务 execution/progress，session-state 的 v2Archived=false、partial=false。这里 false 不表示文件归档失败，而是无选中任务时跳过任务图谱。但这会让“已经完整盘点却未选到目标”和“尚未到列表即失败”都停留在 session 证据层，主线进度无法从同一结构说明下一步。

run220 inventory 去重 20 个 exact name+instruction；按**当前联合 plan**离线交集有 4 项仍有额度：拍立淘 0/5、精选 1/3、话费 0/1、金币加抵 0/1。这只是已有名单与当前计划的离线比较，不代表现在 live 页面仍有这些任务。当天名字屏蔽还会排除其中精选，其余是否可执行仍需新鲜页面与目的页合同核实。

## 4. AI 面板接入与公共检查的边界

当前配置 `aiPanelReader=true`、`aiTaskRecovery=false`、`localActivityNavigation=true`。这表示 AI 读取面板/余额；任务内仍优先并要求本地合同；首页/活动页仍走本地导航。已存在的 AI 任务恢复模块需要显式开启，且按 `docs/AI任务判断接线.md:19` 本来也不扩大 home/landing 导航。

- `runtime.ts:31–39`：AI 认出面板可直接满足面板身份；若 AI 返回 isPanel=false，继续调用旧本地 navigation inspector。AI 面板不是首页入口定位器。
- `runtime.ts:455、518、681–688`：本地导航阶段 Agent 预算为 0，unknown/obscured 直接 needsLearning，禁止 fallback。run223 正是这一公共入口先拒绝，尚未接触任何任务合同。
- `runtime.ts:698–722`：已派发任务先查本地落地/回执；未匹配且未开 aiTaskRecovery 时硬停。run219 的错误来自这里，不是“AI 已看过所有未知落地页并决定不可做”。
- `observations.ts:45–48`：AI sidecar 校验失败被折叠为 isPanel=false、blocked=true；`runtime.ts:776` 再汇报 Inventory page identity failed。run221 多出的 rewardOffers.Max 字段属于 schema 问题，被外层混报成页面身份失败。当前 reader 的 `ai-panel-reader.ts:13–16` 已只剥离 quote 附加字段，其余结构仍严格；旧 run221 保持 stopped。run222/223 没有走到新列表分支，不能算此修改已 live 验通。

run223 原始 result/stages 证明 open_app completed、enter_activity stopped、动作数组为空；像素细因采用已有只读诊断 `docs/run223首页导航停止.md:5–9`：文字/布局可见正常，chrome 的两条窄区域不匹配。当前源码 `activity-navigation.ts:184–203` 确实把这些区域纳入整组像素匹配，全部组通过才返回 home。**即使把所有任务合同补齐，公共首页先拒绝仍会使它们一个也跑不到。** 本轮没有重放图像 checker或改变门槛；“正常首页误拒”的图像判断来自该已有诊断。

## 5. 结算与归档：已经有能力，仍需补全审计边界

### 5.1 现有真实链条

`runtime.ts:804–816` 要求已选任务、原 baseline、回执；learned/controller 路径核对同 attempt；返回所属面板最多取 4 次观察，用 `observations.ts:76–81` 检查最后两次余额一致、正增量，以及可见同任务计数不矛盾。列表任务行允许不出现；名称变化不会被直接当成另一任务的计数完成。

`store.ts:80–93` 还检查 receipt attempt、任务原额度、返回/结算阶段 completed 和实际正增量。`:113–115` 防止同 attempt 再次入账；`:120–147` 把已接受正收益写为 DB DIAGNOSTIC，同时写 asset_snapshot 和 gain_event，再输出 status=completed、learningValidation=diagnostic_only。`:193–215` 写 v2；`:219–228` 先不可变文件、后 bundle、最后 manifest，报告 partial/issues。不是仅写一段“看起来成功”的日志。

### 5.2 还需要补齐的归档与验收

1. **实际计划没有源码级封存。** `main.ts:24` 读取 plan，但 `:27–28` 的 scriptFiles/sourceSnapshot 包含配置、未包含 cfg.planFile；config.json 只保存路径。对 run218–223 的 stage source candidates 和 source-snapshot.json 程序核对，六次均没有 plan.json 归档。27/29 份源码/配置归档哈希全部匹配，只能证明这些文件的来源完整，不能证明未归档的完整 do/skip/pending 输入从未改变。建议未来封存计划字节与 hash，并绑定所用 inventory、合同选择、次数决策。
2. **成功不等于自动提炼经验。** run218/219 的 usedExperienceVersionId=null、derivedExperienceVersionIds=[]。共享知识当前有5个 experienceVersions，均 supervised_only。`store.ts:164–189` 写 candidate，`:206` 保持 automaticRunnerAcceptance=false；`source-archive.ts:20–33` 会剔除携带 runtime frame/action 的操作步骤，避免把账户证据直接变成跨账户脚本。此隔离是正确边界，不应删掉校验来制造“复用已发布”。需另有结构化可复用过程与验证证据连接。
3. **清理验证晚于入账。** `session.ts:29–34` 先 save 再 cleanup；cleanup 若失败，最终状态会转 unknown，但先前入库/结果不会自动变更。当前六次 cleanup 都 errors=[]、Dozing，因此没有在这些记录中发生此冲突；后续稳定判定仍须读取 final、session-state 和 cleanup，不能只认 DB/result completed。
4. **运行内两次余额一致与独立两新帧审计有层次。** `stableSettlement` 本身没有 frameId 参数；正常 runtime 每次调用 observe 得到新 capture，run218 两个不同 ID 已核实。store 依赖阶段结果，不独立重放两帧原图。稳定验收必须继续核实原图、owner、时间、新帧ID及回执归属，不能只信 samples 的数字。
5. **文件与 DB 不是同一事务。** store 的 DB transaction 完成后才逐项写文件；失败会令 session unknown。已有不可变冲突与重试修复机制，但稳定判定需要求 archived.v2Archived=true、partial=false、issues=[]，核对 bundle/result/final 一致，不能只看到 gain_event 就认全部归档完成。

## 6. 稳定证据、registry 与“自动 promotion”并未接成一路

`recipes.ts:2–9` 只加载 registry.json 中 state=validated、steps hash 一致、至少两次独立 completed 验证且 evidenceFile 存在的 stage recipe；当前默认 `data/stage-records/recipes` 目录不存在，联合配置也未指定替代 recipeRoot。正常主线实际运行的是显式配置候选，不能说正在消费已验证 registry。loader 本身只检查验证记录与文件存在，不独立回放内容；发布者仍须为 evidence 真实性负责。

`script-validation.ts:743–781` 是只读稳定审计，按同 fingerprint 的独立 session 计数并返回 candidate/stable 报告；没有写 registry 或将 v2 execution 变成 automaticRunnerAcceptance=true。`:445` 明确 diagnostic_only 只是 informational；真正旧门槛在 `:453–471`，仍要求 whole-session zero-model。`:690–738` 还比较当前实现与封存源码。因而 run218 的 AI 成功不能通过这个旧标准，且当前实现后续已改动；**不应直接删除旧限制，把原零模型报告刷成稳定。**

已批准的新口径见 `docs/AI辅助稳定脚本推进方案.md:3–7`：允许脚本内 AI、同适用过程两次独立正常入口、真实回执、两新帧正收益、源码/配置、预算和清理、无聊天手工坐标/修账。现有覆盖清单是新口径的人工可审证据快照；本轮在 main/runtime/store/registry 路径未见调用该新口径的自动证据汇总和发布步骤。

因此需要分开记：单次已确认收益、已学候选可执行、AI辅助独立成功次数、旧零模型审计状态、共享/跨账户验证。两次独立成功应以 session+attempt 去重，并绑定影响执行过程的版本；恢复同一 attempt 不增加次数。源码来源归档通过不替代稳定验证。按已有 AI 辅助清单与最新六次结果，仍只有精选一次新正常成功，没有任何一类新增第二次独立成功。

## 8. 建议的统一正常路线与验收条件

应先让用户确认公共页面判断策略和连续执行范围，再围绕已有 staged 主线接通这些环节。无需让16类重新人工首学，也不宜立即另造 planner 或直接复活旧 YAML 循环。

1. **先解决公共页面的判断契约。** 首页/活动落地页采用当前可见文字、相对布局、唯一入口和所属前台证明，歧义时有界 AI；正常列表使用当前新鲜面板证据。是否替换首页旧像素门槛属于策略调整，应先抛出确认。验收需覆盖run223已有拒绝帧和真实遮挡/歧义负例，并检查实际 dispatcher 与归档策略版本一致，不以离线 checker 通过宣称真机完成。
2. **复用已学过程，明确能力映射。** 当前 exact task+instruction 对应合同、入口、等待/连续滑动、回执、返回和结算；补的是未接配置或缺失步骤。把当前未覆盖4类、闪购多条件pending、日限和缺席显式列出，不自动用别名/同类标题扩展执行权限。新策略确认前，保留 aiTaskRecovery=false 这个当前配置事实，不能因模块存在便自行开启。
3. **将完整盘点与次数决策绑定。** 全名单生成 do/skip/pending 和理由、当前额度、计划次数、已消费 attempt、独立成功次数、下次条件；替换名字级当天屏蔽。选择来自该计划，但每次派发前仍用新帧重绑唯一按钮。验收包括“精选1/3且已有1次成功仍可安排第2独立session”、同名不同要求不能继承、unknown attempt不重发、日限跨日等待。
4. **保留一次任务的结算原子边界，再讨论连续 session。** 每项仍是新 attempt、真实回执、所属资产页两新帧稳定正增量、幂等入账和完整归档；返回后刷新实际名单。若用户确认连续执行，外层可受总次数/时长/模型预算约束串行调用，遇新问题停止报告。当前“每session一项并息屏、不启调度”的授权与实现不能靠改 maxTasks 偷换为长批次。
5. **归档计划与推进结论。** 保存实际计划字节/hash、完整 inventory 的来源、新鲜度、选用合同版本、次数账、停止原因和下一条件；没有选中任务也记录盘点/规划状态。保留账户事实与共享候选隔离，不把 frame/action 操作日志直接发布成跨账户 recipe。
6. **另建明确版本的 AI 辅助证据判定接线。** 复用现有 source/receipt/settlement/cleanup 核验，按新口径累计同适用过程两次独立正常成功、记录失败及AI成本。旧whole-session-zero-model继续作为历史标准。稳定报告通过后是否发布registry应是显式、可复核的后续步骤，不能把store固定的diagnostic标签当作没有收益，也不能把某字段改成stable来代替证据。
7. **降低每轮公共观察成本。** 以已有usage建立基线，减少首页非面板完整任务识别、盘点后重复找目标、余额结算再次解析整表等支出；按阶段限定观察目标与结果schema。验收同时检查失效/遮挡/错owner/超龄/未知派发，不跨新帧沿用旧点击授权，不在连续滑动段塞入慢AI观察。

优先级是：先确认公共首页/未知页策略与执行范围；随后接通次数/规划归档和证据汇总；再针对未覆盖配置补已有合同入口。每步用已有离线证据核对，再在获准的正常入口累计真实结果。新问题先报告用户、确认后改；本报告不构成实现或真机执行授权。

## 本轮核验方法与限制

采用 systematic-debugging 的证据链方法做静态追踪，没有运行 reproducer、测试、ADB或模型；只读审计范围优先于技能中的重现/修改流程。命令输出来自真实文件解析、只读SQLite查询、源码检索和SHA256重算。总数、计划交集、usage、归档哈希和最新run均由Python核对。模型附加字段的既有RED/GREEN、run223像素细因和16类历史首学按其已有文档记录引用，未冒充本轮重新执行。配置只读取任务/限制/开关及来源字段，未读取账号凭据文件或输出模型密钥。
