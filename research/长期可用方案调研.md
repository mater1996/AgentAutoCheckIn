# 长期可用方案调研（第二版）

调研时间：2026-10-29
背景：上一版推荐 AutoGLM，但它的模型「限时免费」不可持续，9B 模型每步都推理也贵。
本版目标：**找到能长期跑下去的方向**，核心是「AI 自动化 + 签到」但成本可控。

---

## 结论：正确的答案是「本地小模型 + 缓存」，不是「云端大模型」

关键洞察：**AI 手机自动化不是必须用大模型，也不是必须用云端。**

| 思路 | 成本 | 长期可持续 |
|---|---|---|
| 云端大模型（AutoGLM-Phone） | 限时免费 → 之后按 token 计费 | ❌ 不可控 |
| **本地小模型（UI-TARS-7B 量化）** | **电费，0 元** | ✅ |
| **AI + 缓存（Midscene）** | **首次调用后命中缓存，0 调用** | ✅ |

**你这台 Mac 是 Apple M6 / 24GB 统一内存 —— 这个配置正好能本地跑 7B 视觉模型。**

实测数据（社区基准，M4 16GB 4bit）：
- UI-TARS-1.5-7B 4bit：**文件 4.9 GB**
- 生成速度：23.1 tok/s，首字延迟 3.9 秒
- 你的 M6 / 24GB 比这个基准更强，可跑 6bit 甚至 8bit

## 一、四个候选框架（都能长期用）

### ⭐ 1. Midscene.js —— 15,431 stars，2026-10-29 推送

- 仓库：https://github.com/web-infra-dev/midscene
- 许可：MIT
- **有 Android SDK**：`@midscene/android`，通过 adb 控制设备
- **有 YAML 脚本**：声明式自动化流程
- **有 MCP server**：可接入 Claude Desktop / Cursor
- **支持任意 OpenAI 兼容接口** → 可接本地 Ollama

**这是本版最推荐的框架**，理由有三：

**① 内置 AI 缓存（决定性优势）**
官方文档 `midscenejs.com/caching` 明确说明支持缓存两类数据：
- AI Planning 步骤（跨流程复用）
- 元素定位信息（matched element localization）

> Midscene supports caching two kinds of data: AI Planning steps and matched element localization information. The former can be used across automation workflows to reduce AI model calls and improve execution.

**这意味着**：第一次跑签到用 AI 找到「红包签到」按钮，之后每天直接命中缓存，**0 次模型调用**。只有界面改版时才重新调 AI。

这正好解决「长期跑成本高」的核心问题 —— 它天然实现了「AI 学习一次，之后纯脚本回放」的机制，比我原方案自己写的「配方写回」更成熟。

**② 可接本地模型**
社区已验证：`ollama` + `qwen3-vl:8b` 可用（有踩坑文档）。也支持 UI-TARS。

**③ 有 Android 完整链路**
- 环境配置文档齐全（`midscenejs.com/zh/platforms/android`）
- 支持原生应用、混合应用、系统界面
- YAML 脚本：`midscenejs.com/automate-with-scripts-in-yaml`

### 2. Mobilerun / Droidrun —— 9,867 stars，2026-10-28 推送

- 仓库：https://github.com/droidrun/mobilerun（原 droidrun）
- 许可：MIT
- Benchmark：**91.4%**（AndroidWorld 类基准领先）
- 支持 **Ollama 本地模型**（官方文档有专章）
- CLI + Python API + Docker
- 支持 Android 真机 / 模拟器 / iOS

**特点**：把「无障碍树 + 截图」结合，比纯视觉省 token。可配 `qwen2.5vl`、`gemma3`、`deepseek` 等本地模型。

**缺点**：是框架不是平台，没有 Web 面板和定时调度，要自己包。

### 3. Mobile-Agent（阿里通义）—— 9,340 stars，2026-10-28 推送

- 仓库：https://github.com/X-PLUG/MobileAgent
- 许可：MIT
- 模型：GUI-Owl（基于 Qwen2.5-VL）
- 有 ModelScope 和百炼在线 Demo

**缺点**：偏研究，工程化程度不如前两个。模型体积大（GUI-Owl 系列）。

### 4. UI-TARS-desktop（字节）—— 39,433 stars，2026-10-09

- 仓库：https://github.com/bytedance/UI-TARS-desktop
- 许可：Apache-2.0
- 模型 UI-TARS-1.5-7B 开源，有 MLX 量化版（Apple Silicon 可用）
- **0.5s 单步响应**（官方宣称）

**缺点**：主要面向桌面，Android 支持不如前三个。

## 二、本地模型可行性（关键）

你这台机器：**Apple M6 / 24GB 统一内存 / 12 核（2 超级核 + 4 性能核 + 6 能效核）/ Metal 4**

| 模型 | 量化 | 体积 | 24GB 能否跑 |
|---|---|---|---|
| **UI-TARS-1.5-7B** | MLX 4bit | **4.9 GB** | ✅ 轻松 |
| UI-TARS-1.5-7B | MLX 6bit | ~7 GB | ✅ |
| UI-TARS-1.5-7B | MLX 8bit | ~9 GB | ✅ |
| **Qwen3-VL-8B** | Q4 | ~6 GB | ✅ 推荐 |
| Qwen2.5-VL-7B | Q4 | ~6 GB | ✅ |
| GUI-Owl（Mobile-Agent） | — | 较大 | ⚠️ 需实测 |

**参考性能**（M4 16GB / 4bit，比你机器弱）：
- UI-TARS-1.5-7B：PP 260 tok/s，TG 23.1 tok/s，TTFT 3.9s

**判断**：本地跑 7~8B 视觉模型完全可行。签到是短任务（5~20 步），每步 3~5 秒推理，一个签到 30~60 秒，可接受。

**关键**：配上 Midscene 的缓存后，**日常运行根本不需要推理**。

## 四、最终方案

### 主方案：Midscene.js + 本地 Qwen3-VL + 缓存

```
框架：Midscene.js（Android SDK + YAML 脚本）
模型：本地 Ollama 跑 Qwen3-VL-8B（或 UI-TARS-1.5-7B）
      ↓ 首次识别界面元素
缓存：Midscene 内置缓存（AI Planning + 元素定位）
      ↓ 之后每天
日常：命中缓存，0 次模型调用，纯本地执行
调度：Mac cron（Mac 常开）
记账：自己写（仍是空白，见下）
面板：自己写
```

**为什么这个能长期跑**：

| 阶段 | 模型调用 | 成本 |
|---|---|---|
| 第一次跑某活动 | 3~8 次推理 | 本地，0 元 |
| 之后每天跑 | **0 次**（命中缓存） | 0 元 |
| 活动改版 | 缓存失效 → 重新推理 1~3 次 | 0 元 |
| 模型升级 | 换 Ollama 模型，不改代码 | 0 元 |

**成本结构从「按 token 付费」变成「一次性电费」。** 这是能长期跑的关键。

### 备选方案：Mobilerun + 本地 Ollama

如果 Midscene 的 Android 支持不够好，换 Mobilerun。它 benchmark 更强（91.4%），但没缓存机制，每次都要推理（本地模型所以还是 0 元，只是慢）。

### 兜底方案：自建 uiautomator2

已实测跑通的那套（`runner/checkin.py`）。用于：
- 界面完全固定、无需 AI 的简单签到
- 需要精确验证（余额变化）的场景

### 不建议：云端 AutoGLM / 云手机平台

- AutoGLM-Phone 限时免费，之后价格未知
- 云手机 $1.4~30/月，自用单账号没必要

## 五、还差什么（必须自己写）

调研确认，以下仍是空白，没有任何现成项目：

**1. 收益记账（积分 → 人民币）**
所有框架只记「任务成功/失败 + 对话 + 录像」，**没有一个做收益折算和汇总**。

**2. 签到模型（账号/活动/状态/连续天数）**
你要求的「设计全面」，需要：
- 账号表（含 user_id 支持双开）
- 活动表（含汇率、时间窗、验证规则）
- 账本（含账面/可用/现金三种口径、有效期）
- 连续签到天数 / 漏签损失（淘金币宝箱容量上限，漏一天真损失）

**3. 面板**
Midscene / Mobilerun 都没有 Web 面板（AutoGLM-GUI 有，但那个方案不可持续）。

## 六、修正后的完整架构

```
┌─ 执行层 ─────────────────────────────────────┐
│ Midscene.js (Android SDK)                    │
│   ├─ 首次：AI 定位元素（本地 Qwen3-VL）       │
│   ├─ 缓存：Midscene 内置（AI Planning + 定位）│
│   └─ 日常：命中缓存，纯 adb 执行，0 推理       │
├─ 调度层 ─────────────────────────────────────┤
│ Mac cron（按活动时间窗随机偏移）              │
├─ 数据层（自己写）─────────────────────────────┤
│ accounts.yaml  账号（含 user_id 双开）        │
│ activities.yaml 活动（汇率/时间窗/验证）      │
│ ledger/*.jsonl  账本（三口径 + 有效期）       │
├─ 记账层（自己写）─────────────────────────────┤
│ 每天签到后读 App 余额 → 算收益 → 落账         │
├─ 面板层（自己写）─────────────────────────────┤
│ 今日状态 / 收益 / 连续天数 / 失败项截图       │
└──────────────────────────────────────────────┘
```

## 七、下一步建议

**先做一个小验证，30 分钟内能出结果：**

1. 装 Ollama，拉 `qwen3-vl:8b`（约 6GB 下载）
2. 装 Midscene（`npm i @midscene/android` 或 YAML CLI）
3. 用 Midscene 对淘宝跑一次「找到红包签到按钮并点击」
4. 再跑第二次，观察是否命中缓存（日志会显示）

**如果第二次 0 模型调用 → 方案成立，可以放心长期跑。**

这一步不需要你注册任何账号、不需要 API Key、不花钱。
