# 自动化工具选型调研

调研时间：2026-10-29
目的：签到自动化要不要引入现成的 UI 测试工具？引入哪些？

---

## 一、候选清单

| 工具 | 类型 | Stars / 热度 | 语言 | 维护状态 |
|---|---|---|---|---|
| **uiautomator2** (`openatx/uiautomator2`) | Android UI 驱动 | 主流 | Python | ✅ 3.7.1 @ 2026-10-23 |
| **Maestro** (`mobile-dev-inc/Maestro`) | 声明式 YAML 测试 | 高 | YAML + Kotlin | ✅ 活跃 |
| **Airtest + Poco**（网易） | 图像识别 + UI | 高 | Python | ✅ 活跃 |
| **Appium** | 跨平台 UI 测试 | 最高 | 多语言 | ✅ 活跃但重 |
| **AutoJs6** | 设备端 JS 脚本 | 6.5k | JS | ⚠️ 更新变慢（6.7.0 @ 2026-03） |
| **Hamibot** | 设备端 + 云端 | 3.1k | JS | ✅ 商业运营 |

## 二、逐个判断

### uiautomator2 —— ✅ 主力，已选定

**原理**：设备上跑 atx-agent + uiautomator server（HTTP/JSON-RPC），Python 侧发请求。
不是 Appium 那套 WebDriver，轻得多。

**实测确认可用**（`probes/`）：
- `dump_hierarchy` 0.91s 拿 385 节点
- `exists` 布尔判定 0.14s
- `xpath` 服务端求值 0.54s 拿 31 个可点节点
- `watcher` 设备端弹窗监控可用
- `long_click` / `swipe` / `drag` / `swipe_ext` 全部可用
- `gesture` / `pinch_in` / `pinch_out` **不存在**（需 shell `input` 或 minitouch）

**已知坑（实测踩到）**：
1. **selector 偶尔匹配不到** —— 淘宝首页的「红包签到」在 XML 里存在，但 `d(text="红包签到").exists` 返回 false。需 fallback 到直接解析 XML + 按 bounds 中心点击。
2. **熄屏时 `dump_hierarchy` 返回空树** —— 只有 systemui 骨架 20 节点。必须先确认 `screenOn`。
3. **`app_current()` 会返回残留任务的 Activity** —— 前台是淘宝却报美团的 `YodaRouterTransparentActivity`。要读 `dumpsys window mCurrentFocus` 并校验包名。
4. **透明 Activity 导致包名瞬时抖动** —— 需连续两次采样一致才判定稳定。

**结论**：作为主力引擎，但必须自己包一层健壮性（上述四个坑都在 `runner/checkin.py` 里处理了）。

### Maestro —— ✅ 引入（只抄格式，不换引擎）

**价值**：
- 声明式 YAML：`tapOn` / `assertVisible` / `inputText`
- 内置 `retry` 块（失败重试，可配次数）
- **自动等待策略**：替代固定 `sleep()`，按应用行为自适应等待 —— 这是最值得抄的设计
- `runFlow` 支持子流程复用

**为什么不直接用**：
- 它是测试框架，不是自动化执行器。要跑在 CI 里、面向「验证」而非「完成业务动作」
- 没有「设备端 watcher 自动处理弹窗」这类长期运行所需能力
- 加一层就多一层依赖和调试成本

**结论**：**配方 YAML 的语法照它设计**（`tapOn`/`assertVisible`/`retry`/自动等待），引擎自己实现。省一堆设计工作，零运行依赖。

参考：https://docs.maestro.dev/reference/commands-available/retry

### Airtest + Poco —— ⚠️ 备用，按需装

**价值**：**图像识别**。当签到按钮是图片、Canvas 绘制、或者没有 text/desc 属性时，uiautomator2 的 selector 完全失效，这时只能靠模板匹配或 OCR。

- Airtest：基于 OpenCV 的图像匹配，`touch(Template("btn.png"))`
- Poco：Unity/游戏引擎的 UI 树（签到用不上）

**成本**：体积大（含 OpenCV + 模型），启动慢。

**结论**：**先不装**。等真的遇到「找不到任何文本属性」的签到按钮再引入。触发条件明确：L2 连续两次都找不到可点节点。

**替代方案**：真需要 OCR 时，用 PaddleOCR 单独调用（更轻），或设备端 AutoJs6 内置 OCR。

### Appium —— ❌ 不用

为跨平台测试设计，WebDriver 协议，会话管理重。签到场景杀鸡用牛刀。
启动一个 session 就要几秒，8 个 App 串行会拖到不可接受。

### AutoJs6（设备端）—— ❌ 一期不用，二期可选

**优势**：脚本跑在手机上，Mac 不用开机；无障碍服务点击不受 MIUI USB 安全设置限制。
**劣势**：调试靠手机屏幕、无断点、版本更新变慢（6.7.0 @ 2026-03，社区反馈 activity 放缓）。

**结论**：一期用 Mac + adb（调试快、我能直接改）。等配方稳定了，可以把高频的几条迁到 AutoJs6 做无人值守（Mac 关机也能跑）。

### Hamibot —— ❌ 不用

商业服务，按量收费（设备 ¥1/次、定时任务 ¥0.6/次）。脚本市场「签到」分类只有 1 个脚本，生态很薄。
唯一价值是 REST API 能远程触发，但我们自己就有 adb。

---

## 三、最终选型

```
引擎：uiautomator2（自建健壮性包装）
配方语法：借 Maestro 的声明式风格（tapOn/assertVisible/retry/自动等待）
图像兜底：Airtest（按需，暂不装）
不用：Appium（太重）、Hamibot（收费且生态薄）
二期可选：AutoJs6（迁到设备端做无人值守）
```

## 四、健壮性包装清单（uiautomator2 必须自己补的）

| 坑 | 处理 |
|---|---|
| selector 匹配不到但 XML 里有 | fallback：解析 XML 拿 bounds → 算中心 → `d.click(x,y)` |
| 熄屏时 dump 空树 | 每次 dump 前检查 `screenOn`，否则先 `KEYCODE_WAKEUP` |
| `app_current()` 返回残留 Activity | 读 `dumpsys window mCurrentFocus` + 校验包名前缀 |
| 透明 Activity 包名抖动 | 连续两次采样一致才判定 |
| 别的 App 模态框挡住启动 | `app_stop` 后重试启动，最多 3 次 |
| 固定弹窗挡路 | 设备端 `watcher` 注册（0 token） |
| 点击后无变化 | UI diff 判定 `NO_EFFECT`，不计成功 |
