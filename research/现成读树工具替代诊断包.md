# 现成工具替代Portal定制诊断：能力核查

结论：先搁置定制诊断APK安装，优先使用Appium UiAutomator2的现成清无障碍缓存与页面树能力做一次对照。本轮只核查公开文档/源码，没有安装、启动或操作手机。当前master能力不等于本机已安装版本；实际选定版本须在测试前确认。

| 现成路径 | 已核实能力 | 关键限制 | 建议 |
| --- | --- | --- | --- |
| Appium + UiAutomator2 | 文档明确有mobile: resetAccessibilityCache；Source handler读XML前调用reset；显式forceClear跳过“无事件则延迟清理”的优化。[1][2][3] | 清的是自身UiAutomation读取连接的缓存，不是远程清Portal连接。仍依赖应用暴露的Accessibility节点。要运行现成Android测试server，不能说无需手机辅助组件；本机淘宝效果未测 | 首选，直接匹配本轮所需能力 |
| Maestro | viewHierarchy前refreshAccessibilityCache，内部waitForIdle(500)与uiAutomation.serviceInfo=null。[4] | 同样依赖Android无障碍；未证明优于Appium，安装/启动仪器连接会改变基线 | 第二个对照，不与Appium同时跑 |
| openatx uiautomator2 | 检索官方仓库已有dump_hierarchy、active root、深度参数；本轮对应完整README未成功保存 | 不把dump_hierarchy当作已确认的显式强制清缓存API；历史普通dump结果不足以替代本次新鲜度对照 | 如本机已具备可先做低成本读树，强刷新能力需继续核对实际版本 |
| Chrome DevTools / WebView DOM | Chrome官方说明可检查已启用调试的WebView。[5] | 要目标应用启用WebView debugging；不能把手机USB调试等同WebView调试。尚未检查淘宝是否暴露接口 | 先只读查调试socket，存在才考虑DOM路径 |
| 本地OCR / 现有视觉补读 | 项目视觉组合run124曾采集20条；OCR未本机对照 | 视觉有推理消耗，OCR还需行分组/配额绑定/完整性核对 | 树方案对照仍不行时的备选；不把换包装当省模型 |

推荐保留现有TS/SQLite业务框架，替换/比较观察层即可；不因选择Appium就重写任务计划、收益核验与账本。Appium/Maestro客户端本地操作不要求用云端测试服务，商业设备云不是本次必要条件；本次不做无关SaaS采购或完整平台重选。

最便宜的下一实验（未执行）：
1. 确认本机工具/实际版本；只读检查是否有可用WebView调试入口。
2. 没有DOM入口则使用现成Appium UiAutomator2 server，配置保留应用数据并禁止自动启动/强停/权限自动授予；建立新连接后先确认淘宝仍在当前任务页。不要使用clearApp/pm clear/reset app替代resetAccessibilityCache。
3. 调用明确的resetAccessibilityCache后获取页面XML，和当前截图对照任务名、配额与位置。静止对照完成即报告暂停；下一次用户继续才做单次滚动对照。
4. 读到当前列表证明可替代观察层；仍旧/缺失说明换工具未绕过页面提供层问题，不反复安装框架。安装或启用仪器连接可能改变其他无障碍状态，保存设置并在退出核验恢复。

为什么原路线偏重：之前调查集中在Portal公开API，确认它没开放clearCache后，过早推进了定制服务；未先确认Appium已提供同类现成功能。定制包适合细分Portal自身连接/事件问题，但业务目标只是可靠读取列表时，应先以现成工具验证是否足够。已生成的APK保留，不必因投入过就继续安装。

证据目录research/evidence/现成读树工具核查，含已保存Appium README、Source.java、AXWindowHelpers.java、Maestro service源码。Chrome条件来自本轮官方页面检索正文，未取得完整HTML存档；该条来源强度明确区分。外部源码取master，未声称固定release具备所有最新参数。

## 实测后的判断与备选路径

Appium静止读取3次与截图相符，单次滚动后3次reset读取仍返回旧首屏，详见docs/Appium单次滚动读取实测.md。两个工具均旧，说明问题不能仅用Portal序列化缓存解释；不等于已证明是系统缓存，也不等于已排除Android缓存。

措辞修正：reset请求成功返回只证明接口调用完成。已保存Appium上游AXWindowHelpers实现中，clearAccessibilityCache捕获异常后只写日志，接口返回不是每个节点强制重取的证明。[2]该源码来自master，具体已装server10.7.6内部行为还需版本源码/运行日志复核，不能把master分支细节冒充已装版本实测。

仍有低成本现成配置未验证：本机已装driver8.7.3 README明确列出enableMultiWindows和enableTopmostWindowFromActivePackage，两者默认false；可以用一次所有窗口/最上层窗口对照排除当前选中旧窗口的可能。[1]这是待验假设，当前没有证据表明目标任务面板一定属于另一个Android窗口。

其余路径：
- 业务绕行优先离线OCR对照：利用已存滚动前后真实截图，比较文字、配额、行/按钮绑定和坐标，不需要唤醒手机。可评估Apple Vision或PaddleOCR；尚未实测，不能保证中文/小字准确率。需要少量行组织与核验代码，不是切换配置即可完成任务系统。
- 现有Midscene视觉采集曾成功一轮，保留作按需补读；每屏固定调用的成本问题仍未解决。
- 真正DOM路径须目标淘宝活动页开放调试；此前只识别到小米浏览器socket，当时淘宝主进程未运行，因此未排除活动页运行后有可用入口，不能宣称淘宝永远不可调试。[5]
- 若目标为确诊，可用另一台设备/ROM的同类页面做对照；不同账号、版本与任务会影响比较。重启/重连只能测恢复，不能单独定位病因。暂不建议继续轮换相同无障碍后端工具或清淘宝应用数据。

本轮仅离线资料核对，未唤醒或操作手机。建议顺序：最多一次窗口配置对照；若仍旧，转向保存截图的OCR验证，避免长期卡在根因研究。
