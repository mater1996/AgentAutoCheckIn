# 签到平台方案评估与现成方案对比

日期：2026-10-30。结论：**目标与资产平台方向正确，现有技术栈可以继续；执行层需要从“按预设步骤尝试”收敛到“确认页面后执行、验证结果后复用”。暂不建议推倒重写，也不建议继续靠坐标和等待时长逐项打补丁。**

本轮读取了当前源码、配置、数据库和运行日志，做了离线语法检查与未知状态误判复现；网上候选只做官方资料和源码核查，**均未安装或真机测试**。推荐是待验证的工程判断，不是稳定性排名。详见[本地检查记录](evidence/方案评估-2026-10-30/本地检查记录.md)。

完整改进设计、进程模型、数据契约和阶段验收见[签到平台改进建议 v1](../docs/签到平台改进建议-v1.md)。本轮未修改业务代码、未操作手机、未启用调度。

## 1. 哪些方向是对的

| 已有方向 | 我的判断 | 应保留的理由 |
|---|---|---|
| 围绕长期积分资产而非短时红包 | 对 | 与用户实际目标一致；能区分积累和一次性消费优惠 |
| account / activity / asset / snapshot | 对 | 账号、任务和资产各自独立，后续加平台才不必重建账本 |
| 配置化表达平台差异 | 对 | 一个执行器承载多平台比平台特判易维护；但配置须包含真实流程与验证契约，不能只改名字 |
| 收集→本地决策→执行 | 对 | 先了解配额、奖励和档位，再决定做什么，便于审阅、续跑与预算 |
| Node + SQLite + 简单面板 | 合适 | 单机、单手机、单用户没有必须换数据库或前端框架的证据 |
| 视觉理解＋本地确定动作 | 合适 | 控件树可读时利用它；页面不可读或歧义时用视觉。不可读应按当前页面实测，不能一次采样推断整个App |
| 缓存和执行经验复用 | 值得保留 | 减少重复规划有价值，但缓存不能代替页面与到账验证 |

Midscene 官方明确：Android 可复用任务规划；定位 XPath 缓存只适用于 Web；aiQuery/aiBoolean/aiAssert 等读数和断言不缓存。因此“Android 缓存以后完全不调用模型”和“缓存能保证长期稳定”都不成立。[21]

## 2. 真正需要改的地方：之前是什么／建议改成什么

| 之前/当前实现 | 建议改成 | 为什么 |
|---|---|---|
| 读数失败后留下0/0或-1，进入“无剩余任务”判断 | 把有效观测、没有任务、暂时未知分开；未知时暂停依赖它的动作 | 不知道当前状态，不能等价成做完 |
| 每轮完整重放入口，ensurePanel直接true | 每段有可验证前提；先确认当前位置，局部恢复失败才重走入口 | 多执行命令不能证明页面正确；每轮冷启动还浪费时间 |
| 用任务名正则判断browse/search/camera，再套模板 | 给模型完整页面和任务上下文，真实执行并验证后存配方 | 名字是显示信息，不能证明执行要求；现有拍立淘/搜索分类已经来回推翻 |
| 按同名YAML、历史清单和历史位置复用 | 配方保存前后条件与来源；当前清单带会话/页面/时间证据，重新绑定实时目标 | 同一天列表也会变；归一化坐标只解决尺寸，不解决布局漂移 |
| 只要余额增加就OK | 收益事实、流程完成度、观测质量分别记录 | 做成一部分与全部成功应该在面板上可区分 |
| 用轮次×估计奖励拆任务收益，达档就算档位收益 | 总变化保留为事实；分项必须有领取/到账证据，否则未归因 | 执行次数不等于完成次数，已达档不等于本轮新领取 |
| HTTP接口返回后，在panel进程执行手机逻辑 | panel入队、独立worker消费；所有入口共用设备锁 | 异步Promise不代表独立进程，多个入口可能争用一部手机 |
| 一边维护自定义flow，一边维护Midscene Test和重复engine | 保留一套活动调度和一套任务执行语义，逐步统一 | 重复入口、节点和参数契约更容易漏接；当前tapRow生成/注册/schema已不一致 |
| 订阅内“不逐token收费”被写成系统零成本 | 现金支出、token参考成本、执行耗时、人工维护分开 | 成本瓶颈可能是每天修脚本，不是模型单价 |

以上来自本地静态核查与已有运行记录；并非本轮新真机根因验证。尤其最新tapRow合同不一致是当前源码问题，不能倒推它就是run #31当时的根因。

**不建议把“入口必须0调用”作为硬目标。**偶尔一次受限视觉确认可能比二十秒重放入口、然后在错误页面反复探测更省事。先比“每次有效完成总耗时、总调用、人工修正次数”，再优化token。

Maestro 官方建议在条件出现时用带轮询的断言，处理动画稳定与点击无变化；retry文档也提醒不要用整段重试掩盖不稳定。这些机制比单纯增大sleep更值得借鉴，当前栈也能实现。[33][34]

## 3. 网上的方案：跨层比较

下表比较“能替代哪一层”，不把支持列表或演示当成已跑通。开源许可不等于所有模型权重或第三方服务也免费。

| 候选/层次 | 已证实的能力 | 与本项目的匹配和缺口 | 硬件/长期成本 | 判断 |
|---|---|---|---|---|
| **现有 Midscene / 开源执行框架** | 规划缓存、视觉操作、结构化报告；Test支持自定义业务节点。[21][37][38] | 已在当前项目接通；需要补页面/任务后验和真实经验晋升 | 现有Mac+ADB真机；MIT代码；模型另计 | **保留主线，先收敛闭环** |
| **DroidRun 当前上游 Mobilerun / 开源Agent框架** | CLI/Python API、动作轨迹录制、macro replay、动作前状态检查，失配可交Agent。[44][45][56] | 最接近“学一次再复用”；仍须我们做任务/到账验证与修复后配方晋升 | Mac+真机/Portal；Python运行时，MIT；远程API路线不要求本地GPU，模型成本待测 | **最值得做学习回放对照，暂不迁移** |
| **Unify-Sign / 开源聚合签到产品** | 淘金币、京豆等现成UI脚本，可视化配置、任务分组、计划与状态面板。[41] | 可借鉴现成路径或替代部分活动执行；未确认等价的统一收益账本，非当前动态任务全量覆盖证明 | 手机端，指定AutoJS.fake/困鱼与内置OCR；GPL-2.0；无已知必需订阅，维护劳动未知 | **现成签到流程的重要对照** |
| **Maestro / 开源测试执行器** | ADB控制Android真机，条件等待、断言、局部重试。[35][33][34] | 可替换确定工作流编排；不会自动解决不可读页面、理解未知任务和业务账本 | Mac+Android真机；Apache-2.0本地CLI；云服务另计 | **借机制，暂不为它迁移** |
| **Appium UiAutomator2 / 开源测试驱动** | 原生/混合App自动化、WebView context等能力。[36] | 更完整的驱动与测试生态；多SDK/服务维护成本，不能假定淘宝任意WebView可调试 | 主机需Android SDK/JDK/驱动等；不要求模型GPU | 现阶段无足够替换收益 |
| **Open-AutoGLM / 开源手机Agent** | PhoneAgent.run/step/reset及逐步结果，适合在动作间插验证。[48] | 中文App第二候选；未确认开箱即用成功轨迹学习/回放/更新闭环 | 电脑Python+ADB；Apache-2.0代码；远程模型API或另部署模型，实际单价待核 | 保留候选，不是免维护替代 |
| **MobileAgent v3.5 / 研究框架** | Mac/Linux ADB及移动端模型endpoint示例，多种模型规模。[54] | 本轮所查移动入口主要是截图动作循环；不能把研究benchmark当签到可靠性 | API或模型服务；MIT代码，权重/服务另核 | 研究参考优于迁移优先级 |
| **Roubao肉包 / 手机端AI助手** | Android原生、Shizuku、VLM API。[55] | 脱离Mac有价值；未建立本平台可调用的稳定任务提交/结果API证据 | Android手机＋模型服务；非完整离线推理 | 暂不适合中央账本直接替换 |
| **青龙 + 签到啦/dailycheckin / 自托管平台** | 青龙调度脚本、环境变量、日志；签到框架已有接口任务、多账号等。[49][50][58] | 可替换成熟接口任务与部分调度；不是“只能网页”，也不会自动提供目标活动维护与收益对账 | 已有主机/容器；青龙Apache-2.0、dailycheckin MIT；签到啦API未声明license | 有确定有效接口的活动再接，无需全平台统一UI |
| **Hamibot / 手机工具＋付费控制服务** | 手机脚本、网页控制台、REST API；存在商业专属版。[57][51] | 可替换设备控制/脚本分发/调度；购买控制平台不等于买到淘宝长期适配 | 专属版￥249/498/1666每月；这是团队版，并非单台必要支出 | 单机项目暂不买团队版 |
| **AutoJs6 / 消费端开源工具** | 无障碍选择器、录制回放、截图图像匹配。[52] | 能做App UI；具体签到流程仍须维护，不能假定兼容Unify-Sign指定运行时 | Android手机；MPL-2.0；无必需模型费证据 | 固定流程可用，但不自动学习业务 |
| **MacroDroid、Tasker/AutoInput / 消费端付费工具** | MacroDroid免费5宏、Pro一次买断；Tasker与AutoInput可组合UI自动化。[53][59][60] | 适合少量固定流程；复杂动态清单、恢复与中央账本需另接 | Tasker美国Play正文$4.49；AutoInput额外权益未知；MacroDroid Pro确切价未知 | 不作为本项目整体替代 |

不采用限时免费、试用额度或促销月卡作为常年成本前提。本轮未找到并验证“付费后长期负责目标App活动适配、账号恢复、统一收益账本”的托管服务；这只说明本轮缺乏证据，不能推断整个市场不存在。云手机主要替换设备常在线环境，目前已有真机，没有优先租赁的依据。

## 4. 最值得看的两个项目，限制也必须说清

### Unify-Sign：已有聚合签到与面板，旧调研应纠正

它的README明确写多App聚合签到，包含淘宝淘金币、京东京豆，且有可视化配置和计划管理；所以“没有签到产品”“签到模型和面板没人做”必须撤回。[41]

但默认分支最近提交在2025-05-31，不能把仓库最近被访问/加星导致的updated_at当源码更新；缺乏维护是风险，不是全部脚本已失效的证明。[42]

实际淘宝现金签到源码有“失败多次，直接标记为成功”的分支。这个入口本身也不在用户长期积分优先范围；这里用它说明：即使采用现成项目，也要独立验证结果，不能把上游success直接当入账。[43]

![Unify-Sign官方仓库历史执行计划界面；截图日期2022-06-01，不代表2026实测成功率](evidence/方案评估-2026-10-30/products/task_schedules.jpg)

图中有任务名、计划时间、执行时间、执行成功/失败/运行中、耗时与手工标记完成；它是任务状态面板，没有展示积分余额或真实收益。截图是历史官方素材，本轮未在手机打开。

### Mobilerun：可以录制回放，但还不是完整自学习系统

它已有动作录制、回放和状态失配接管，值得借用，免得我们自己再造通用录制器。[45][56]

源码中，状态匹配主要看UI节点和package/activity；两边树都空时节点分数取1.0，因此不能单凭state matched确认某个Canvas子页正确。[47]

默认AI接管丢弃divergence/current_state/remaining_actions，重新用整个goal调用Agent，而且save_trajectory="none"。所以它提供“交回AI”，并不自动完成“局部修复→验证→回写新配方”。最后回放返回动作失败计数是否为零，也不是积分到账判断。[46][56]

**我们的价值应集中在业务契约、结果证据和账本；通用动作录制、报告解析、执行节点优先用上游。**Midscene也已提供report-tool及结构化execution JSON，不必继续用HTML正则猜动作最多的片段就是成功链。[37]

## 5. 谁买/用现成的，谁继续自己做

- **继续自己维护：**账号/活动/资产模型、同口径观测、任务与领奖验证、配方版本与验证状态、真实兑换、统一面板。并非这些能力全世界无人做，而是目前没有确认能原样替代本项目要求的产品。
- **直接使用上游：**设备驱动、视觉定位、执行报告、通用工作流运行器；若Mobilerun对照成功，再用它的录制与回放。
- **按活动选择：**可验证且维护稳定的接口脚本、现成UI签到脚本、AI执行器可以并存，统一返回结果契约。统一平台不等于强迫所有活动走同一技术。
- **暂不新增：**第二套常驻调度面板、团队版设备平台、本地大模型部署、多Agent每日层层规划。这些尚无已量化的维护收益。

## 6. 推荐流程与最小验证

```text
实时观察活动页面与清单
  → 已验证配方是否适用？
      是：验证页面前提 → 复用动作 → 验证任务结果
      否：模型读取完整上下文 → 受限探索 → 验证结果 → 候选配方
  → 确认返回页 → 领取确实可领取的奖励
  → 同口径余额观测 → 分别记录流程完成度和实际收益
```

成功经验不能只有“点哪里”：还需保存适用页面、任务要求、动作、完成判据、来源运行和验证次数。名称/坐标/行号只作为目标线索；前后条件不符就失效或重学。

**下一步只做一个有额度的任务对照，不一次重建整个平台。**先补最小验证器与错误状态，以同一任务比较现有Midscene闭环与Mobilerun录制回放；Unify-Sign先核实指定运行时和现有入口是否匹配，匹配才纳入执行对照。记录任务计数、余额读数、返回页、模型调用、耗时、人工修正，不拿当天配额耗尽导致的无增长判框架失败。

建议的验收顺序：

1. 离线未知读数不再变成无任务；生成YAML与运行器节点契约一致。
2. 人工监督跑通一条任务的“进入→执行→计数变化→返回→余额读取”。
3. 独立重入后再次复用，遇到错页/任务变化会停或重新学习。
4. panel与worker分离、并发请求不争抢手机、崩溃可恢复。
5. 建议连续至少7天人工核对运行记录，并记录真实兑换；这些是提议的观察窗口，不是本轮已通过验收。
6. 用户确认跑通后再启用无人值守调度。

扩展架构和数据模型已写在配套设计里，按阶段增加，不要求单任务验证前先实现所有表。

## 7. 成本与价值，不能再混用

本地run #31的已有日志显示13次调用、106426 tokens，准备与执行合计221.599秒，只做一轮后失败。该样本不能代表日均，但足以说明失败恢复也是主要成本来源。

项目原来的“¥2/百万总tokens”只是参考常量。按它机械折算该次为¥0.212852；假设每月30次同量则¥6.38556。这不是供应商当前报价，也未区分输入、缓存与输出；订阅真实边际支出与独立API备用成本必须分别列，不应把该数字称为实际账单。

同样，余额增加不等于现金净利润。现有淘金币0.01折算是项目名义口径，本轮未复核其现行兑换限制。应同时看积分存量、实际抵扣、现金支出、每周人工修正时间；没有实际抵扣记录，不宣称全部存量可按名义金额兑现。
